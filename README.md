# Invest — 台股成交值排行

個人使用的投資研究網頁系統。第一個功能是「個股成交值排行」，用來判斷哪些標的近期正在吸收市場成交值。
族群分類會在串接 Google Sheets 之後加入。

## 目前階段

**階段一：計算引擎與互動網頁**

- 行情資料是**證交所與櫃買中心的真實每日收盤行情**，由 `Infrastructure/MarketData` 逐日下載後快取在本機。
- 排行榜上的每個數字都由原始成交值即時算出，沒有任何預先寫死的結果，公式全部有單元測試釘住。

尚未實作：SQLite / EF Core、Google Sheets API 與族群分類、圖表、60 日期間。

### 關於回補

```bash
dotnet run --project src/Invest.Web -- backfill [交易日數] [起始日期]
```

- 官方 API 一次只給一天，所以回補是「從起始日往回走，每天打兩次請求」。
- 已下載過的日期會直接略過，因此這個指令可以重複執行，中斷後再跑會從斷點繼續。
- 非交易日也會被記錄下來，不會反覆重打同一個沒有資料的日期。
- 每次請求之間有 3 秒延遲，避免被官方網站擋。70 個交易日大約需要 8 分鐘。
- 交易日數的下限取決於要看的期間：成交熱度需要 2N 天，資金加速需要 3N 天。
  20 日 × 資金加速 = 60 個交易日，這也是預設回補 70 天的理由。

快取檔放在 `data/imports/yyyy-MM-dd.json`，不進版控。

```
│   ├── Domain/Stocks/                   跨功能共用的核心模型

│   │   ├── Twse/
│   │   └── Tpex/

│       ├── Models/                      查詢條件、結果模型、顯示格式
│       ├── Pages/                       排行頁
│       └── Services/                    計算器與查詢服務

```

架構原則：單一 Solution、單一 Web Project，以 `Features/` 目錄切分業務功能，不為每個功能建立獨立 `.csproj`。
`Domain/` 只放跨功能共用的核心模型，`Infrastructure/` 只放外部整合，計算邏輯不寫在 Razor 頁面裡。

## 核心指標定義

| 指標 | 公式 |
|---|---|
| 平均每日成交值 | 期間總成交值 ÷ 期間交易日數 |
| 成交值增減率 | （本期平均 − 前期平均）÷ 前期平均 |
| 市場成交比 | 個股期間成交值 ÷ 全市場期間成交值 |
| 排名變化 | 前期排名 − 本期排名（正數代表上升） |
| 期間漲跌 | （期間終點收盤價 − 起點收盤價）÷ 起點收盤價 |

- 「前期」固定採緊鄰的同長度區間（例如近 20 日 vs 再往前 20 日）。
- 市場成交比的分母一律是上市＋上櫃全體，不隨畫面上的市場篩選改變，這樣切換市場時比例才能互相比較。
- 前期平均為 0 時增減率無法計算，顯示 `—` 並排在最後，不會被當成 0%。

## 排行模式

| 模式 | 排序依據 | 回答的問題 | 需要的資料量 |
|---|---|---|---|
| 成交熱度 | 本期平均每日成交值 | 最近哪些標的吸收最多成交值 | 2N 個交易日 |
| 資金加速 | 成交值增減率 | 哪些標的的成交值相較前期快速放大 | 3N 個交易日 |

資金加速需要 3N 是因為它的「前期排名」本身也是一個增減率，前期還需要自己的基期。

畫面上的**成交門檻**預設 5000 萬，主要就是為了資金加速模式：冷門股從幾十萬跳到幾百萬就是好幾倍成長，
不過濾的話排行榜會被這類沒有實際意義的標的佔滿。

## 設計原則

優先順序：計算正確 > 資料可追溯 > 歷史結果穩定 > UI 可查詢 > 視覺效果。

歷史結果必須穩定：日後接上資料庫與族群分類時，每日計算結果會固化保存，
不可因為今天修改了族群成分股，就讓過去幾個月的歷史排名被重新計算而改變。
