# Invest — 台股成交值排行

個人使用的投資研究網頁系統。第一個功能是「個股成交值排行」，用來判斷哪些標的近期正在吸收市場成交值。
盤後與盤中摘要同時顯示加權指數、櫃買指數及漲跌幅；這些是市場狀態資料，不是買賣訊號。
持倉管理由其他工具處理；網站的族群頁只把既有個股行情重新聚合成市場資金流，
不延伸成持倉管理、投資建議或買賣訊號。

最高權限頁籤提供「資產 Dashboard → 帳戶明細」兩層；使用者、帳戶與已確認持倉存於 Supabase。
截圖只在瀏覽器內辨識、不會上傳或保存；辨識後會先列出「覆蓋／新增／移除」差異，
每一項都必須人工核對並勾選才會套用。相同代號直接覆蓋，移除項目預設不勾選。檢視權限不顯示此頁籤；
密碼登入前端已上線；資產資料的匿名 RLS 寫入收權限仍待驗收，限制與下一步見 [TODO.md](TODO.md)。

## 目前階段

**階段一：計算引擎與互動網頁**

- 行情資料是**證交所與櫃買中心的真實每日收盤行情**，由 `Infrastructure/MarketData` 逐日下載後快取在本機。
- 盤後與盤中摘要都帶有**加權指數／櫃買指數及漲跌幅**；盤後使用交易日收盤值，盤中使用 MIS 最新一輪。
- 排行榜上的每個數字都由原始成交值即時算出，沒有任何預先寫死的結果，公式全部有單元測試釘住。

持倉管理不在本網站範圍內；族群分類只用於重組市場成交比、觀察資金流向。SQLite / EF Core 不在目前架構內；目前使用 Supabase PostgreSQL 與 Npgsql。

舊網址 `https://qwe953751.github.io/Investment/` 已收掉內容，整個網域只剩空白頁，
不再對外提供任何排行資料；repo 跟 GitHub Pages 設定本身沒有關掉，純粹是發布腳本不再
往那邊送內容。`admin888/`、`viewer/` 這兩個過渡期用的子路徑網址已一併收掉（2026-09-01
起不再發布內容，改成單一網址＋登入分層）。
檢視模式仍可進入盤中、盤後、自訂、族群，但族群頁只開放「熱度排行」；這是 UI 樣板，
不是登入授權。
「筆記」是個人工作區，只在最高權限樣板顯示；內容直接讀寫 Supabase 的 `notes` 表，任何裝置都能看到同一份資料，
並每 60 秒重讀。檢視權限不顯示此頁籤。這是公開網站的刻意取捨：沒有登入邊界，知道網址的人也可能修改筆記，
密碼登入會在網址下限之上提升權限；在 RLS 收回匿名寫入前，資料表仍沿用公開 anon 模型。

「資產」可在 Dashboard 與帳戶明細間切換、新增使用者／帳戶，並用本機 OCR 讀券商未實現損益截圖。
使用者可一次選最多 20 張，逐張最長辨識 10 秒；完成後會列出和既有持倉的覆蓋／新增／移除差異，
逐項核對並勾選再套用。同代號直接覆蓋，移除預設不勾選；只有確認的持倉數字寫入 Supabase，
原始截圖不會上傳、保存或送往券商。資產頁保留上方主頁籤，方便切回其他功能頁；匿名 RLS 收權限仍待驗收。
深色台股畫面若只有「市值／現價／成本均價／投資成本」，會在總額與單價誤差不超過 0.6% 時補回唯一的
正整數股數；若券商把股數拆成「昨日餘額／今買成交／今賣成交」，則以昨日＋買進−賣出計算。不能通過
這些限制的列保持空白等待人工修正，不以欄位位置硬猜。
持倉表可一鍵批次編輯，但人工可改的欄位只保留「代號／庫存數量／總成本」；名稱由代號名冊帶入，
市值固定以「庫存數量 × 盤中現價或最近收盤價」重算，未實現損益也由重算後的市值與總成本得出，
不再接受人工輸入容易過期的名稱、市值與損益。預設按代號排序，可切換按漲跌幅排序，新增或 OCR
更新後都會重新依代號排序。
輸入已知台美股或 ETF 代號時會帶入名稱；名稱底色與右側漲跌幅在交易日盤中使用當日盤中行情，盤後則使用
最近收盤。休市日不會把上一個交易日留在 `intraday_latest` 的資料誤標為盤中。

帳戶新增與編輯都可選「台股／美股／其他」。美股帳戶的現金、成本、持倉市值與損益以美元顯示；
帳戶資產總值另外顯示「台幣（美元）」。美股市值只採用 Supabase `latest_us_quotes` 的最新收盤價，
資料庫沒有該 ticker 的行情時，該筆持倉市值顯示 `—` 並列出缺少的代號；帳戶與 Dashboard 只加總已有
行情的持倉並明確標記「部分行情」，不會把截圖中的成本冒充市值。USD/TWD 使用期交所每日外幣參考匯率，
由完整盤後流程集中寫入 `exchange_rates`；
這是每日參考匯率，不是銀行現鈔買賣價，`publish-only=true` 不會更新它。

帳戶明細的持倉名稱可開啟截至該市場最新交易日的三個月 K 線。台股沿用還原權息日 K；美股使用
`data/imports-us` 的原始 OHLC，各 ticker 以自己的最新資料日為尾端。沒有回補資料的美股會明確提示先加入
`us_watchlist` 並完成行情回補，不會拿台股日期、成本或只有收盤價的資料偽造 K 棒。
美股回補真的寫入 `imports-us` 後，排程會委派既有 `publish-only=true` 重新輸出這些 K 線與資產名冊；
觀察清單仍由資料庫管理，資產持倉不會自動增加 Alpha Vantage 的 API 額度消耗。

帳戶明細另有多筆「出入金紀錄」：入金成本固定由「入金合計 − 出金合計」計算，
不是帳戶內再存一個容易失真的總數；每筆可記日期、方向、金額與備註。資料表由
`db/030_asset_cash_flows.sql` 建立；正式 Supabase 已於 2026-08-31 套用並查證 RLS、權限與前端表單。
金額欄位的無上限型別、美股最新價前收欄位、日行情 view 權限與資產日快照分別由
`db/032_asset_cash_flows_unbounded_amount.sql`、`db/033_latest_us_quotes_previous_close.sql`、
`db/034_daily_quotes_view_security.sql`、`db/035_asset_value_snapshots.sql` 建立；四支 migration
已於 2026-09-02 依獨立流程套用正式 Supabase 並查證。Dashboard 的「資產變化」折線圖讀取
每日快照；當日總值完整時最多寫一筆，缺行情或匯率時不以成本假裝市值，也不寫不完整快照。

### 個人筆記

最高權限樣板的「筆記」頁籤提供：

- 可分別依「類型」（功能／Bug／待驗證／完成）與「狀態」（待處理／處理中／待確認／已完成）篩選；兩者可交叉使用，並可搜尋標題或內容。
- 筆記篩選列的「類型」與「狀態」上下分列，搜尋欄維持獨立，不會和兩組選項混在同一列。
- 新增、編輯、刪除筆記；每筆保存標題、類型、狀態、內容與最後修改時間。
- 筆記清單顯示資料庫永久編號；編號由 sequence 往後累加，刪除不回收，多裝置同時新增也不重複。
- 編輯器的標題、類型、狀態與內容輸入字體放大，內容區使用較大的行高與可調整高度，方便閱讀長筆記。
- 筆記可附加最多 6 張 JPG／PNG／GIF／WebP 圖片；超過 5 MB 時先在瀏覽器壓縮到約 4.5 MB，再預覽及上傳 Supabase Storage，重新開啟或換裝置仍看得到。HEIC／HEIF 只有在目前瀏覽器能原生解碼時才可轉成 JPEG；不支援時會在選檔階段明確顯示原因。
- 筆記存於 Supabase `notes` 表；正在編輯時背景重讀不會覆蓋草稿。
- 儲存或刪除成功後，較早發出的背景讀取會因清單版本已變更而被捨棄，不會把剛寫入的筆記從清單覆蓋掉；下一輪背景同步仍會取得其他裝置的更新。

`db/023_notes_images.sql` 已套用正式 Supabase；`note-images` bucket、`notes.attachments` 與三條 Storage policy 均已查證存在，匿名上傳／刪除測試皆回 HTTP 200。它沿用目前筆記的公開 anon 模型，請勿上傳含帳號、密碼或敏感金融資訊的原始截圖。

清除網站資料、使用無痕視窗或更換裝置後仍會讀到同一份筆記；要把「網址可編輯」收斂成真正的資料庫權限，仍須完成 [TODO.md](TODO.md) 的 RLS 收權限驗收。

### 關於回補

```bash
dotnet run --project src/Invest.Web -- backfill [交易日數] [起始日期]
```

- 官方 API 一次只給一天，所以回補是「從起始日往回走，每天打一輪請求」。
  一輪包含兩個市場的收盤行情、加權／櫃買指數，加上七份用來扣除非一般交易的報表（詳見下一節）。
- 已下載過的日期會直接略過，因此這個指令可以重複執行，中斷後再跑會從斷點繼續。
- 非交易日也會被記錄下來，不會反覆重打同一個沒有資料的日期。
  但「今天」還沒過完之前不會下這個判斷：收盤行情下午才公布，公布前抓到的空資料
  若被記成休市，那一天就永遠補不回來了。
- 每次請求之間有 3 秒延遲，避免被官方網站擋。70 個交易日大約需要 15 分鐘。
- 交易日數的下限取決於要看的期間：成交熱度需要 2N 天，資金加速需要 3N 天。
  最長的 60 日 × 資金加速 = 180 個交易日，再加上 120 個可選基準日，所以 300 天才夠全部組合都算得出來。
- **行情資料只增不減**：回補只會新增缺少的日期，不會刪掉已經下載過的行情。

快取檔放在 `data/imports/yyyy-MM-dd.json`，不進版控。
檔案裡的 `schemaVersion` 記錄成交值的定義版本，定義改變時舊檔會被回補指令視為過期並自動重下，
避免新舊定義混在同一份排行裡。`marketIndexSchemaVersion` 與 `marketIndices` 保存當日兩個市場指數；
升級後再次執行 `backfill` 會只補抓缺少的指數，不重算既有個股成交值。

日 K 的開盤、最高、最低、收盤另外以 `dailyBarSchemaVersion` 管理。既有快照只缺這些欄位時，
用下面的命令補齊 300 個交易日：這會涵蓋靜態站最近 120 個可選檢視日及各自往前三個月所需的日 K；它只補價格欄位，不改成交值、成交量、成交筆數或既有收盤價：

```bash
dotnet run --project src/Invest.Web -- backfill-bars 300
```

版本 2 起，上櫃行情依官方 `fields` 欄名找開／高／低，不再假設固定位置；若出現最高價低於開盤／收盤或最低價高於開盤／收盤等不可能的 OHLC，該日不會被標成完成。舊版快取會由同一個 `backfill-bars` 指令重新抓取。

新日期則由一般 `backfill` 直接帶入日 K。官方端點回傳不完整時該日期不會被標記成完成，
重跑同一命令即可繼續補。

指數來源是官方公開資料：TWSE 的 `MI_INDEX`／`FMTQIK` 價格指數資料與
[TPEx OpenAPI](https://www.tpex.org.tw/openapi/) 的櫃買指數歷史資料；盤中指數則與個股一起讀 MIS 的 `tse_t00.tw`、`otc_o00.tw` 頻道。

### 成交值只計一般交易

官方「每日收盤行情」的成交金額註明**含一般、零股、盤後定價、鉅額交易**，
但市場上看到的成交值排行（玩股網、籌碼K）只算一般交易。兩者差距在高價股上特別大——
2026-08-07 的台積電就差了 59 億，足以改變名次。

因此回補時會另外抓下列報表，逐檔扣除：

| 市場 | 扣除項目 | 報表 |
|---|---|---|
| 上市 | 盤中零股 | `afterTrading/TWTC7U` |
| 上市 | 盤後零股 | `afterTrading/TWT53U` |
| 上市 | 盤後定價 | `afterTrading/BFT41U` |
| 上市 | 鉅額交易 | `block/BFIAUU` |
| 上櫃 | 盤中零股 | `afterTrading/oddQuote` |
| 上櫃 | 盤後零股 | `afterTrading/odd` |
| 上櫃 | 鉅額交易 | `blockTrade/quote` |

上櫃的每日收盤行情標題就寫著「不含定價」，所以上櫃不需要扣盤後定價。

排行只收**一般股票**：代號為四位數字且不以 0 開頭。ETF、權證、受益證券、特別股都排除在外。

## 發佈成靜態網站

排行頁是 Blazor Interactive Server，每次點按鈕都要回伺服器算，本機不開就看不到。
為了在手機上隨時查看，`export` 指令會把所有篩選組合先算好，輸出成一份純靜態網站：

```bash
dotnet run --project src/Invest.Web -- export "$(pwd)/publish/site"
```

**路徑一定要給絕對的。** `dotnet run --project` 會把工作目錄切到專案資料夾，
所以相對路徑會落在 `src/Invest.Web/publish/site`，而 `publish-gh-pages.sh`
預設讀的是 repo 根目錄的 `publish/site`——兩邊對不上時，發佈出去的是上一次的舊快照，
而且指令不會報錯。

產出最近 120 個可選交易日 × 5 種期間，也就是最多 600 個排行 JSON，另以 `data/kline/{ticker}.json` 逐檔保存日 K，
加上 `index.html` / `site.css` / `site.js`，
整包約 131 MB，但單頁只載入其中一個約 460 KB 的檔案。20 MB 的原始行情不會上網。

一個檔案就是一份**完整名單**：全市場近兩千檔，不篩市場、不設門檻、不截斷筆數，
每一列同時帶著兩種排行模式要用的數字。市場、門檻與模式由前端就地篩選與排序，
所以成交門檻可以是自己輸入的任意金額，不必事先為每個金額各存一份檔案。

檔案裡只寫數字，顯示文字由前端套格式。原本連文字都先算好，但那樣單檔將近 1 MB，
交易日一多整包就撐不住；只留數字後單檔剩下約四分之一。

交易日只輸出最近 120 天：每多一天就是五個期間各一份全市場名單（約 2.2 MB）。
上限定義在 `RankingDates.SelectableTradingDayCount`，排行頁與靜態網站共用同一份日期清單，
月曆上不在清單裡的日子一律反灰不能點。

每次發佈的版本號會寫進 `manifest.json`，並在匯出時直接改寫 `index.html`，
把 `site.css` / `site.js` 與資料檔的網址都帶上 `?v=`。
GitHub Pages 的快取是十分鐘且無法改標頭，靠網址變動才能讓手機立刻拿到新版；
萬一瀏覽器仍拿著舊的 `site.js` 去要已經不存在的檔名，前端會比對 manifest 版本自動重載一次。

`manifest.json` 另外保存每個可選交易日的 `marketIndices`；切換盤後交易日時，摘要的指數會跟著交易日切換，
不會誤用最新一天的指數。

排行表的**標的名稱可以點擊**：名稱旁會開啟一個小型浮動日 K 視窗，不插入表格列、不改動原排行版面。
圖表顯示點擊檢視日往前三個月的官方開高低收；盤中與盤後共用這份已完成的日 K 歷史，
盤中另外把 MIS 當日開高低與最新現價接成尚未收盤的當日 K 棒，隨盤中資料輪次更新。

「自訂」頁重用單日排行檔裡的完整名單，但不顯示名次：預設依股票代號遞增，
每頁顯示 100 檔，可用上一頁／下一頁或頁碼切換。成交值下限是所選交易日的單日成交值，
與盤後排行的平均每日成交門檻分開保存；營收增減沿用排行頁的 YOY／MOM 格式，
點擊儲存格即可開啟營收彈窗，不另設外部營收年月控制。

**計算只有一份**：exporter 直接呼叫 `TradingValueRankingQueryService`，
所有指標都是 C# 算的；前端只做「篩選、排序、編號、套顯示格式」這幾件事，不重寫任何公式。
這幾件事的結果可以拿舊版由 C# 事先算好的檔案逐格比對驗證，確認兩邊完全一致。

發佈到 GitHub Pages 用 `gh-pages` 分支，每次用一個全新的 orphan commit 覆蓋整個分支，
不保留歷史——一份快照就一百多 MB，累積下來會讓 clone 變成災難：

```bash
GH_PAGES_REMOTE=https://x-access-token:$(gh auth token)@github.com/frank-invest/frank-invest.github.io.git \
GH_PAGES_PUBLISH_ROOT=1 \
scripts/publish-gh-pages.sh publish/site
```

網址：<https://frank-invest.github.io/>（單一網址，訪客模式為預設，監控者／最高權限登入後才拿得到）

不帶 `GH_PAGES_REMOTE` 時預設推去 `origin`（`qwe953751/Investment`）；不帶
`GH_PAGES_PUBLISH_ROOT` 時，整個網域只會發一頁看不到任何內容的空白頁——這是刻意
的預設值，`qwe953751.github.io/Investment/` 就是這樣被收掉內容的。手動在其他裝置
發布內容時，兩個環境變數都要記得帶，漏帶 `GH_PAGES_PUBLISH_ROOT` 就會把
新網址也發成空白頁。詳見 [Doc/開發環境.md](Doc/開發環境.md) 的「發布到新網址」。

前端抓 `data/*.json` 時會帶上 `manifest.json` 裡的版本號（發佈時間的 Unix 秒數）當查詢字串，
`manifest.json` 本身則以 `cache: 'no-store'` 讀取。重新發佈後版本號一變，所有資料檔的網址跟著變，
瀏覽器手上的舊快取自動失效，不必手動清快取。

標題旁的**檢查更新**按鈕做的就是這件事：重讀 `manifest.json`，版本號有變就帶著新版本號重載整頁，
表格的數字跟著換成新的；沒變就回報目前的資料日期。手機上不必再手動清快取或改網址。

## 每天自動更新

`.github/workflows/daily-snapshot.yml` 每個交易日台北時間 18:00 在 GitHub 上跑一輪
「回補 → 重算 → 發佈」，本機不用開機。也可以到 Actions 頁面手動觸發。

行情快取放在同一個 repo 的 **`data` 分支**（`imports/yyyy-MM-dd.json`），
開跑前取下來、回補完推回去，所以每天只會下載新增的那一天。
快取不放進 `main` 是因為它每天都在長，塞進原始碼的歷史裡會讓 clone 越來越重。

`data` 分支**只增不減**：推之前會檢查有沒有檔案被刪除，有的話整個流程直接中止，
寧可停在那裡，也不要把「刪掉歷史」推上去。

排在 18:00 是因為收盤行情大約下午三點才公布。真的跑在公布之前，兩個市場都會回空的，
這種情況下**不會**把當天記成休市——非交易日一旦寫進快取就不再重試，
記錯了那一天就永遠補不回來，所以「今天」這個日期還沒過完之前一律不下這個判斷。

## 出事的時候網站會自己講

頁面右上角有一個 ⚠ 鈴鐺。自動流程紅燈時它會出現並亮紅點，點開看得到每一則異常：
時間、哪個流程、訊息，以及連到那次 Actions 執行的連結。
流程下一次跑成功就自動收掉，那一則轉成灰色的「已恢復」；全部沒事時整個鈴鐺不出現。

```bash
dotnet run --project src/Invest.Web -- alert 每日排行快照 error "訊息" "https://github.com/..."
dotnet run --project src/Invest.Web -- alert-clear 每日排行快照
```

兩支 workflow 各有一步 `if: always()` 在呼叫它們：綠燈就 clear、紅燈就記一則。

**警報寫進 Supabase（`site_alerts`），不寫進 `manifest.json`。**
最需要被通知的情況正是「靜態網站沒發佈成功」——那時候線上的 HTML 與 manifest
都還是舊的，任何塞進快照裡的訊息都永遠送不出去。這件事 2026-08-21 真的發生過。

- 同一個流程同時只留一則未解除的警報：連壞五天不需要五個鈴鐺，
  需要的是「還在壞，從那天開始」。保留 90 天。
- 寫警報那一步**自己不會讓 workflow 紅掉**：連不上資料庫只印訊息，
  否則會蓋掉前面真正的錯誤。
- 訊息裡的連結只有開頭是 `https://github.com/` 時才做成 `<a>`，其餘一律當純文字。

## 資料放在哪裡

| 層 | 放什麼 | 保留多久 |
|---|---|---|
| `data` 分支 `imports/` | **盤後行情的權威來源**，只增不刪 | 無限 |
| `data` 分支 `snapshots/` | Supabase 原生資料的備份 | GFS 15 份，約半年 |
| Supabase | 原生資料的權威；盤後行情只是查詢副本 | 300 個交易日 |
| `gh-pages` | 靜態網站 | 可選基準日 120 天 |

正確性的順序是**交易所 → `imports` → Supabase**。兩邊對不起來時以 `imports` 為準，
所以要復原盤後行情一律從 `imports` 重灌，不從備份還原。

## 資料表定義

`db/` 底下的 SQL 依編號套用，`000` 要最先跑。每份都可以重複執行，重跑不會壞。

套用的管道是 Supabase Management API（需要 `SUPABASE_ACCESS_TOKEN`）：

```bash
curl -X POST "https://api.supabase.com/v1/projects/<專案 ref>/database/query" \
     -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
     -H "Content-Type: application/json" \
     -d "$(jq -Rs '{query: .}' db/004_intraday_curve.sql)"
```

新增市場指數前先套用 `db/007_market_indices.sql`。它只在 `intraday_runs` 增加四個可為空的欄位，
並更新 `intraday_latest` view；舊盤中輪次沒有指數時會顯示 `—`，不會補造歷史值。

盤中日 K 需要再套用 `db/008_intraday_kline.sql`。它在 `intraday_quotes` 保存 MIS 的當日開、高、低，
並把三個欄位接到 `intraday_latest`；舊盤中輪次沒有這些欄位時，前端只顯示已完成的盤後日 K。

營收彈窗需要 `db/009_revenue_history.sql`。它新增公開唯讀的 `revenue_history`，
原始 `monthly_revenue` 仍然不對 anon 開放；套用後要再執行一次 `revenue`才會產生 20 個月摘要。

市場熱絡需要 `db/011_market_heat.sql`。它只在 `intraday_runs` 新增可為空的熱絡欄位，
並重建 `intraday_latest` view。一般盤中收集會在每一輪以 `MarketHeatCalculator` 寫入；
若 migration 晚於最新快照才套用，可回填該輪，**不會重抓或重寫個股明細**：

```bash
dotnet run --project src/Invest.Web -- backfill-intraday-heat
```

公司網路無法直連 PostgreSQL 時，才明確使用下列受控路徑。它由正式網站公開的唯讀 API
讀取快照、仍由 C# 計算、再以 Management API 精準更新同一個時間戳；需要
`SUPABASE_ACCESS_TOKEN`，不能用於一般日常收集。公開 manifest 固定讀實際發布的
`https://frank-invest.github.io/manifest.json`；舊 `qwe953751.github.io/Investment/` 根目錄已刻意收掉內容，不能再當回填來源：

```bash
dotnet run --project src/Invest.Web -- backfill-intraday-heat --via-management-api
```

不用寫入用的那組連線字串，是因為 `invest_writer` 沒有建表權限，也不該有——
它的密碼放在 GitHub Secrets，給了 DDL 權限等於讓 CI 有能力改結構。

每份的最後一行會把自己記進 `schema_migrations`，`verify` 與 `status`
開跑前會比對 `db/` 裡的檔名跟這張表，少貼哪一份就直接把檔名印出來。
沒有這層比對的話，漏貼的症狀是幾天後某個指令突然說 `relation ... does not exist`，
那時候已經很難想起來少貼了什麼。

## 盤中量能曲線

盤中明細不再由每日盤後 `sync` 先刪除。它會留到下一個較新交易日的有效快照成功寫入，
再在同一筆 transaction 刪除舊日期；休市、重大災害放假、MIS 失敗或資料倒退都不會先把舊資料清空。


## 盤中成交金額對照（暫時的）

```bash
dotnet run --project src/Invest.Web -- turnover-audit          # 對一輪，然後印進度
dotnet run --project src/Invest.Web -- turnover-audit --loop   # 整場每 5 分鐘一輪
```

盤中的成交金額是「現價 × 累計成交量」推算的——MIS 只給累計量，不給累計金額。
股價一路往下走時，早盤那些量其實是用更高的價格成交的，用當下的價回乘就會少算。

這個指令每輪**同時**問 MIS 與玩股網（`investrue/all-quote-info`，那邊給的是真正的累計金額），
把兩邊的差異寫進 `turnover_audit_rounds` 與 `turnover_audit_outliers`。
兩邊要併發抓，否則量到的是時間差不是算法差。
只存每輪的摘要與最多 50 檔離群值，不存全市場逐檔（逐檔六天約 65 萬列）。

**這只是量測，不會改變盤中收集器的任何行為**，前端也不讀這兩張表。
排程在 `.github/workflows/turnover-audit.yml`，每個交易日自己跑。
不加 `--loop` 會印出每個交易日收了幾輪、還差幾天。

收滿 6 個完整交易日、盤中來源換好之後，這整套要刪掉：
`db/011_turnover_audit.sql`（檔頭有刪表指令）、
`src/Invest.Web/Infrastructure/TurnoverAudit/`、
`tests/Invest.Web.Tests/TurnoverAuditTests.cs`、
那支 workflow，以及 `Program.cs` 裡的指令與 DI 註冊。

## 備份與還原

```bash
scripts/backup-supabase.sh [快照目錄]        # 預設 data/snapshots
```

備份的是**原生資料**——族群、編輯、筆記這類只存在於資料庫、別的地方生不回來的東西。
`daily_quotes` 與 `intraday_*` 只備份結構、不備份內容：它們的權威在 `imports`，
備份裡留一份三個月前的行情，還原時就有機會拿舊資料蓋掉正確的，這是正確性問題而不是省空間。
還原完直接跑 `sync` 就會補滿。

每天跟著盤後流程跑，寫成 `snapshots/yyyy-MM-dd.sql.gz`（約 24 KB），
保留最近 5 份、每週 4 份、每月 6 份，共 15 份涵蓋約半年。
輪替掉的檔案只是從目錄消失，git 歷史裡永遠找得回來。

`.github/workflows/restore-test.yml` 每週日把最新的備份**真的還原一次**，
目標是當場開、跑完就丟的 postgres 容器，碰不到 Supabase。
除了確認能還原，也會檢查行情表是不是空的——不是空的就代表排除清單失效了。

**真正要還原回 Supabase 永遠是人工的**：先列出差異、經過確認才執行，不做成自動流程。

## 核心指標定義

| 指標 | 公式 |
|---|---|
| 平均每日成交值 | 期間總成交值 ÷ 期間交易日數 |
| 成交值增減率 | （本期平均 − 前期平均）÷ 前期平均 |
| 市場成交比 | 個股期間成交值 ÷ 全市場期間成交值 |
| 排名變化 | 前期排名 − 本期排名（正數代表上升） |
| 日漲跌幅 | （所選交易日收盤價 − 前一個有效收盤價）÷ 前一個有效收盤價 |
| 當週漲跌幅 | （目前價格 − 本週開始前最後有效收盤價）÷ 本週開始前最後有效收盤價 |
| 指數漲跌幅 | （當日指數 − 前一交易日收盤指數）÷ 前一交易日收盤指數 |

- 「前期」固定採緊鄰的同長度區間（例如近 20 日 vs 再往前 20 日）。
- 市場成交比的分母一律是上市＋上櫃全體，不隨畫面上的市場篩選改變，這樣切換市場時比例才能互相比較。
- 前期平均為 0 時增減率無法計算，顯示 `—` 並排在最後，不會被當成 0%。
- 日漲跌的基準是前一個有效收盤價；當週漲跌的基準是週一之前最後一個有效收盤價，通常是上週五。
  盤中以最新現價計算、盤後以所選交易日收盤價計算；缺少基準或目前價格時顯示 `—`。點擊欄名排序固定看日漲跌。
- **除權息交易日的基準會換成除權息參考價**（基準收盤價 × 還原因子），不是前一天的原始收盤價。
  交易所當天就是用參考價當競價基準、也用它報漲跌，所以這樣算出來的數字同時對得起
  券商 App／新聞，以及同一列點開的向前還原日 K。詳見 [Doc/日K還原權息.md](Doc/技術文件/日K還原權息.md)。

觀察期間可選 **前一交易日 / 5 / 10 / 20 / 60 日**，預設 5 日。
**交易日**是觀察期間的最後一天，預設最新的交易日；往回選一天，該日之後的行情就完全不列入計算，
因此看到的會是當天收盤後的排行。點按鈕會跳出月曆，週末、假日與尚未回補的日子反灰不能點，
月份切換也會停在有資料的範圍內；月曆兩側的 `‹` `›` 可以直接跳到前後一個交易日。
期間越長需要的歷史越多（成交熱度 2N、資金加速 3N），資料不足時該組合會顯示還差幾個交易日。

## 盤中排行

畫面左上角切到**盤中**，看的是當天到目前為止的累計成交額。收集器每兩分鐘先把已成功
寫入資料庫的完整輪次輸出為不可覆寫的 `intraday-YYYYMMDD-HHmm-runN.json`，再更新極小的
`latest.json` 指標；瀏覽器只輪詢後者，run id 改變才從 CDN 下載完整快照。完整快照包含全市場
所有個股、指數、市場熱絡與同一輪的族群熱度，前端再做篩選與排序，因此不是「固定前一百檔」
而是完整、可重現的排行。

完整快照採不可變檔名，但 Storage 只保留最近 30 份（約 60 分鐘）；`latest.json` 與未知檔案
不會被清理。這避免每兩分鐘一份 JSON 無限制累積並耗盡 Storage 額度，同時保留足夠時間讓
已讀到上一個指標的瀏覽器安全完成下載。

這條 CDN 路徑只在選擇盤中資料時啟用：**盤中排行、自訂資料瀏覽→盤中、族群→熱度排行→盤中、
族群→族群列表→盤中**（以及列表中展開的盤中個股 K 線）。筆記、資產、提醒、營收、盤後排行、
非盤中的族群頁面都維持原本的資料來源與更新方式。使用者端僅在台股 09:00–13:35、頁面在前景時
輪詢；同瀏覽器分頁以 `BroadcastChannel` 共用輪詢結果，舊分頁每十分鐘檢查網站版本。

摘要區的加權與櫃買指數，以及已展開標的的當日 K 棒，都取自這一輪 MIS 快照，
同一個計時器同步更新；盤後則取所選交易日的官方收盤資料。

盤中的**觀察期間**按鈕不是「本期多長」，而是「今天要跟過去多長的期間對照」，
交易日選擇器則收起來（盤中永遠是今天）。對照用的是**市場成交比**：

| 指標 | 公式 |
|---|---|
| 盤中市場成交比 | 個股今日累計成交額 ÷ 全市場今日累計成交額 |
| 成交比變化 | 盤中市場成交比 − 過去 N 日的市場成交比（百分點） |
| 排名變化 | 過去 N 日的排名 − 今日盤中排名（正數代表今天名次比平常前面） |
| 預估收盤 | 今日累計成交額 ÷ 時段進度 |

排名變化和成交比變化盯的是同一件事，只是一個看順序、一個看比例：
兩份名次都在**同一批候選**上算（今天這批股票在過去那段期間各排第幾），
所以名次差純粹是順序變動，不會混進「有些股票只出現在其中一邊」的雜訊。
名次是相對的，「今天只走了半天」不影響——這和市場成交比能開盤就看是同一個道理。
對照期間查無此股（新上市、或那段期間完全沒成交）就顯示 `—`。

比例比得起來、金額比不起來：半天的量拿去比人家一整天的量一定小。
先把今天推估成全日再比也不行，那會把準確度整個綁在還沒校正的線性預估上。
市場成交比的分子與分母取自**同一輪**，時段進度會自己約掉，所以 09:05 就能看。

因此**排行一律以實際累計成交額或成交比變化為準**，預估收盤只是參考欄，**不開放排序**：
它的分子帶有預估值的誤差，排序等於變相鼓勵拿失真的數字排名次。
09:27（時段進度 10%）以前分母太小，預估欄一律顯示 `—`。

### 手機上怎麼知道畫面是不是真的在動

摘要的「資料時間」後面會跟一句「（N 分鐘前）」，它自己會走，不必等抓到下一輪。
抓不到的時候正是最需要看到它一直往上加的時候。收盤後不顯示。

前端刻意不用 `setInterval`：手機把分頁凍住時計時器整個停擺，解凍之後是
「從凍住的地方接著跑」而不是「補上錯過的那幾次」，畫面可以停在好幾分鐘前而看不出來。
改成每次自己排下一次，並且一律拿牆上時鐘判斷該不該抓；
喚醒事件接了 `visibilitychange`、`focus`、`pageshow`、`online` 四個，
各家瀏覽器發的不一樣（iOS 從 bfcache 還原只發 `pageshow`），少接一個就漏掉一種情況。

### 颱風假

台北市宣布停班就不開盤，是當天清晨才宣布的，證交所的年度休市日曆不會有。
收集器不去讀停班公告：休市時 MIS 照樣回應、只是日期停在上一個交易日。
到 `CollectionSchedule.IntradayGiveUp`（10:00）為止一輪都沒收到當日資料、
而且沒有任何一輪失敗或被丟掉，就判定沒開盤、提早收工，不空轉到 13:35。
有失敗就分不出休市與故障，寧可繼續跑完整場。

## 交易限制標記

名稱**左邊**掛的標記講的是這一檔**目前**受到的交易限制，兩個標記由上往下疊：

```
[處] 個股名
[全]
```

標記那一格的寬度是固定保留的，沒有標記的列也一樣，所以整欄的名字都從同一個位置起算，
不會因為有標記就被往右推。

| 標記 | 意思 | 為什麼會壓低成交值 |
|---|---|---|
| 處（紅） | 處置期間 | 撮合被改成人工分盤（現在每 2 分鐘一次，115/08/10 之前第一次處置是每 5 分鐘） |
| 全（紫） | 變更交易方法（全額交割） | 買賣都要先付足款券、不能融資融券，願意接手的人本來就少 |

兩個標記都是淡底彩字：要看得到，但不能比股名還搶眼。全額交割不用橘色，
因為橘跟處置的紅太近，兩個疊在一起會分不出來。

兩者都讓成交值不是自由競價的結果，所以這一列的名次不能照字面讀。滑鼠停上去會顯示細節。

**注意股不標**：注意股既不改撮合方式，也不改交割條件。

資料在 export 時抓，寫進 `manifest.json`，盤中與盤後共用同一份：

| 標記 | 市場 | 來源 |
|---|---|---|
| 處置 | 上市 | `twse.com.tw/rwd/zh/announcement/punish` |
| 處置 | 上櫃 | `tpex.org.tw/openapi/v1/tpex_disposal_information` |
| 全額 | 上市 | `openapi.twse.com.tw/v1/exchangeReport/TWT85U`（整份都是變更交易方法的標的） |
| 全額 | 上櫃 | `tpex.org.tw/openapi/v1/tpex_cmode`（還混著分盤與管理股票，只收 `AlteredTrading` 是全形「Ｙ」的） |

四個來源都只回「現在誰被限制」，沒有歷史查詢，所以往回選基準日時這些標記講的仍然是現在的狀態。
撮合頻率不在欄位裡，只出現在公告內文的「約每 N 分鐘撮合一次」，上市寫國字、上櫃寫阿拉伯數字，
兩種都得 parse——不能寫死成 5 或 20 分鐘，規則改過。
抓不到時就不標記，不會讓整份匯出失敗。

## 月營收

排行榜最右邊兩欄。上市櫃公司依規定要在每月 10 日前申報上個月的營收。

```bash
dotnet run --project src/Invest.Web -- revenue              # 抓最新一期並重算摘要
dotnet run --project src/Invest.Web -- revenue --backfill 66  # 連同歷史一起回補
```

| 欄位 | 內容 | 算法 |
|---|---|---|
| 營收增減 | 上下兩行，YOY 與 MOM | 跟去年同月比、跟上個月比。點表頭以 **YOY** 排序；點儲存格開啟營收彈窗 |
| 創高月數 | `N` 或 `N+`，沒創高是 `—` | 從當月往回數，連續幾個月都沒有比它高的（含當月自己） |

**「上個月」的定義只有一個地方說了算**：今天是 8 月，就只認 7 月。
7 月還沒公告就顯示 `—`，**不會退回去拿 6 月的數字頂替**——那會讓人拿舊營收當新的看。
程式裡沒有任何往回找的路徑，只查「上個月」那一格；前端還會再比對一次月份，
跨月當下資料庫還沒重算完也不會顯示錯的。

`N+` 代表往回數到手上的歷史用完都沒有更高的，也就是「至少 N 個月」。
中間缺一個月也會停在那裡：沒看過的月份不能當成比它低。

**增減率一律由我們自己的營收歷史算**，不抄來源報表上已經算好的欄位。
那些欄位遇到公司更正營收時會跟我們手上的歷史對不起來，變成畫面上兩個數字互相打架。
基準月沒有資料、或基準月營收是 0（除以 0）時顯示 `—` 而不是 0%——那兩件事意思完全不同。

點擊任一檔的營收增減儲存格，會開啟不改動原表格排版的浮動視窗：
上層顯示最近 20 個月的月營收柱狀圖與 YoY 折線，下層列出最近 5 個月的月營收／MoM／YoY。
上層圖表與下層列表的高度固定是 `3:2`，也就是 1.5 倍。

資料來源兩條，金額都是千元，寫入前一律乘開成元：

| 用途 | 來源 | 一次拿到 |
|---|---|---|
| 最新一期 | `openapi.twse.com.tw/v1/opendata/t187ap05_L`、`tpex.org.tw/openapi/v1/mopsfin_t187ap05_O` | 全部公司的最新已公告月份，含 KY |
| 回補歷史 | `mopsov.twse.com.tw/nas/t21/{sii\|otc}/t21sc03_{民國年}_{月}_{0\|1}.html` | 指定月份，一個月四個檔案（上市／上櫃 × 國內／外國企業） |

最新一期回傳的月份**不保證同一個月**：每月 1~10 日之間，先公告的已經是上個月、
還沒公告的仍停在上上個月，所以月份跟著每一列走。

觀測站那份報表是 Big5，但我們用 Latin1 讀整份檔案再用 regex 抓 ASCII 結構：
Big5 的次位元組落在 `0x40~0x7E` 與 `0xA1~0xFE`，不含 `<`、`>` 與數字，
所以中文字不可能假裝成標籤或數字。公司名稱會是亂碼，但我們只取代號與金額，名稱來自每日行情。

**營收不進靜態快照**，網頁直接讀 Supabase 的 `revenue_latest` 與 `revenue_history`：
公告期內整天都會多出幾家，靜態站一天只重算一次（18:00），中間公告的就要等隔天才看得到。
跟 `market_flags` 同一個理由、同一種做法。因此[月營收 Action](.github/workflows/revenue.yml)
只寫資料庫、不重新發佈網站：

`revenue_latest` 只有當月儲存格；`revenue_history` 每檔最多 20 列，只有點開彈窗才查詢該標的。
兩張表在同一筆資料庫 transaction 整批替換，YoY／MoM 也都來自同一個 C# 計算器；
前端只繪圖與格式化，沒有第二份公式。

| 期間 | 頻率 | 台北時間 |
|---|---|---|
| 每月 1–10 日（公告期） | 每 2 小時 | 09、11、13、15、17、19、21 點 |
| 每月 11 日之後 | 每天一次 | 19 點 |

`monthly_revenue` 的內容**不進備份**（結構有）：權威在觀測站，掉了重跑 `--backfill` 就補得回來，
每天塞十萬列進 git 只會讓 clone 越來越重。

## 排行模式

| 模式 | 排序依據 | 回答的問題 | 需要的資料量 |
|---|---|---|---|
| 成交熱度 | 本期平均每日成交值 | 最近哪些標的吸收最多成交值 | 2N 個交易日 |
| 資金加速 | 成交值增減率 | 哪些標的的成交值相較前期快速放大 | 3N 個交易日 |

資金加速需要 3N 是因為它的「前期排名」本身也是一個增減率，前期還需要自己的基期。

畫面上的**成交門檻**是「平均每日成交值」的下限，可選 不限 / 1 億 / 10 億 / 100 億，預設 1 億，
旁邊的輸入框也可以直接填任意金額（單位億元，清空代表不過濾）。
單位就是表格上那一欄「平均每日成交值」，可以直接對照；期間長度不影響門檻，
換期間時排除的標準不會跟著跑掉。

門檻主要是為了資金加速模式：冷門股從幾十萬跳到幾百萬就是好幾倍成長，
不過濾的話排行榜會被這類沒有實際意義的標的佔滿。

## 鎖定

輸入股號按 `＋` 可以把個股**鎖定**，鎖定的標的會列在篩選列上並顯示目前名次，
出現在排行榜上時整列標成藍底。單顆膠囊上的 `×` 取消一檔，`✕` 一次清空整份清單。

名次是「通過目前市場與門檻篩選後的完整名次」，不受畫面只顯示前 100 名的限制，
所以掉出榜外也看得到現在排第幾；被門檻或市場篩掉時顯示「未入榜」，而不是給一個假的數字。
靜態網站會把鎖定清單存在瀏覽器裡，下次打開還在。

## 設計原則

優先順序：計算正確 > 資料可追溯 > 歷史結果穩定 > UI 可查詢 > 視覺效果。

歷史結果必須穩定：日後接上資料庫與族群分類時，每日計算結果會固化保存，
不可因為今天修改了族群成分股，就讓過去幾個月的歷史排名被重新計算而改變。
