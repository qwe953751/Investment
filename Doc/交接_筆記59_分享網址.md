## 1. 結論摘要

有 **3 個獨立缺陷疊在一起**，必須**三個全部修好**才會通。缺任何一個，分享連結依然失效。

| # | 位置 | 缺陷 | 影響 |
|---|---|---|---|
| **A（主因）** | `supabase/functions/access-share/index.js:178` | `generateAuthToken` 讀 `body.properties.hashed_token`，但 GoTrue REST 回應是**扁平**的、沒有 `properties` 這層 | **100% 失效**：任何分享連結兌換一律回 `502 auth_link_failed` |
| **B** | Supabase Edge Function 部署狀態 | `access-share` 線上還停在 **v1（2026-09-09）**，commit `449da439`（2026-09-12）從未部署 | 永久→悄悄變 1 天；不限次數→悄悄變 1 次；1 個月→`400`；分享清單→`404` |
| **C** | `public.access_share_redeem` RPC | `db/050` 只把新的 WHERE 條件寫成**註解**，沒有真的 `create or replace function` | 永久／不限次數的連結在 RPC 這關被擋 → `410 invite_expired_or_used` |

**附帶問題 D**：`fortune@investment.local` 缺 `app_metadata.access_role`，導致「財神」帳號無法建立分享連結（`handleCreate` 要求 `accessRole(user) === 'admin'`）。`db/050` 的那段 `update auth.users` 沒生效。`monitor@investment.local` 也缺，但影響較小（前端按 email 判 tier，且目前沒有 RLS policy 參照 `'monitor'`）。

**前端不需要任何修改** — 見第 4 節（已實測驗證）。

## 2. 證據（已在 production 實測，可不必重跑）

### 2.1 主因 A

線上 `access-share` v1／本機 HEAD 都是這段：

```js
// supabase/functions/access-share/index.js:167-185
async function generateAuthToken(request, share) {
    const response = await fetch(`${SUPABASE_URL}/auth/v1/admin/generate_link`, { ... });
    if (!response.ok) return null;
    const body = await response.json();
    const properties = body?.properties;                       // ← 永遠 undefined
    if (!properties?.hashed_token || !properties?.verification_type) return null;   // ← 永遠 return null
    return { tokenHash: properties.hashed_token, type: properties.verification_type };
}
```

直接打 production 的 `POST /auth/v1/admin/generate_link`（service_role key），HTTP **200**，回應長這樣：

```json
{"id":"b6b2e373-…","email":"holdings@investment.local","app_metadata":{"access_role":"holdings",…},
 "action_link":"https://…/auth/v1/verify?token=…&type=magiclink&redirect_to=http://localhost:3000",
 "email_otp":"92825422",
 "hashed_token":"a6c2c7f14cdba91ae1b6566fd8036aeb93f6d106eed57773e8324c81",
 "verification_type":"magiclink","redirect_to":"http://localhost:3000"}
```

**沒有 `properties` 這一層**。`properties` 只存在於 `supabase-js` SDK 的 `auth.admin.generateLink()` 回傳值（SDK 會把回應重組成 `{ data: { properties, user } }`），直接打 REST API 沒有。

端對端實測：在 production 插一筆**完全有效**的連結（1 小時後過期、`max_uses=5`、未撤銷），呼叫
`POST https://dehzxlxyfvtnylwgbmqy.supabase.co/functions/v1/access-share?action=redeem`
→ 回 `{"error":"auth_link_failed"}`（HTTP 502）。
同一時刻的 Supabase auth log 顯示那次 `generate_link` 是 `level:info / msg:"request completed"`（**成功**）。
也就是說 Auth 完全正常，是我們自己把成功的回應判成失敗。（測試資料已刪除。）

**旁證**：`access_share_links` 全部 5 筆的 `use_count` 都是 **0**、`last_used_at` 都是 `null` —— 這功能上線以來**從來沒有一次兌換成功過**。

### 2.3 缺陷 C

`db/050` 確實已套用（`schema_migrations.applied_at = 2026-09-12 07:22:28+00`），欄位也確實改成 nullable
（`expires_at` / `max_uses` 的 `is_nullable` 都是 `YES`）。**但** `db/050` 第 50-52 行只寫了：

```sql
-- access_share_redeem() 的 where 條件改為：
--   (expires_at is null or expires_at > now())
--   and (max_uses is null or use_count < max_uses)
```

是**註解**，不是 SQL。線上函式定義現在還是舊的：

```sql
CREATE OR REPLACE FUNCTION public.access_share_redeem(p_token_hash text)
 RETURNS TABLE(id uuid, role text, target_email text, expires_at timestamptz)
 LANGUAGE sql SECURITY DEFINER SET search_path TO 'public','pg_temp'
AS $function$
    update public.access_share_links
    set use_count = use_count + 1, last_used_at = now()
    where token_hash = p_token_hash
      and revoked_at is null
      and expires_at > now()          -- 永久連結 expires_at 是 null → NULL，不成立
      and use_count < max_uses        -- 不限次數 max_uses 是 null → NULL，不成立
    returning id, role, target_email, expires_at;
$function$
```

權限是對的，不用改：`proacl = {postgres=X/postgres, service_role=X/postgres}`。

> ⚠️ 三項有順序相依：**先改程式 → 再套 DB → 再部署 Edge Function → 最後驗證**。

### 步驟 1：修 `generateAuthToken`（主因 A）

檔案：`supabase/functions/access-share/index.js`，函式在第 167-185 行。

把：
```js
    const body = await response.json();
    const properties = body?.properties;
    if (!properties?.hashed_token || !properties?.verification_type) return null;
    return {
        tokenHash: properties.hashed_token,
        type: properties.verification_type
    };
```

改成：
```js
    const body = await response.json();
    // GoTrue 的 REST 端點 /auth/v1/admin/generate_link 直接把 hashed_token／verification_type
    // 放在頂層；`properties` 那層只存在於 supabase-js SDK 重組後的回傳值。這裡兩種都收，
    // 免得未來換成 SDK 呼叫時又壞掉。2026-09-14 查 #59 時發現：原本只讀 properties，
    // 導致每一次兌換都在 generate_link 成功後被自己判成失敗（502 auth_link_failed）。
    const properties = body?.properties ?? body;
    if (!properties?.hashed_token || !properties?.verification_type) return null;
    return {
        tokenHash: properties.hashed_token,
        type: properties.verification_type
    };
```

**不要動** `redirect_to`。GoTrue 會因為 `https://frank-invest.github.io` 不在 Auth 的 Redirect URLs 白名單裡而退回成 `http://localhost:3000`，但這**完全無害** —— 我們只用 `hashed_token` 自己打 `/auth/v1/verify`，從來不使用 `action_link`。

### 步驟 2：新增 `db/056_access_share_redeem_nullable.sql`（缺陷 C + D）

```sql
-- 2026-09-14：筆記 #59 —— access_share_redeem 補上 null-safe 條件。
--
-- db/050 把 access_share_links.expires_at／max_uses 改成 nullable（null = 永久／不限次數），
-- 但新的 WHERE 條件只寫成註解，函式本體從未更新。結果：
--   expires_at is null  → `expires_at > now()`   為 NULL → 不成立
--   max_uses   is null  → `use_count < max_uses` 為 NULL → 不成立
-- 永久或不限次數的連結因此永遠兌換不了，回 410 invite_expired_or_used。
--
-- 順便補 db/050 沒生效的那段：fortune@investment.local 的 admin access_role
-- （沒有它，「財神」帳號按分享連結會被 handleCreate 擋成 403）。

create or replace function public.access_share_redeem(p_token_hash text)
returns table(id uuid, role text, target_email text, expires_at timestamptz)
language sql
security definer
set search_path to 'public', 'pg_temp'
as $$
    update public.access_share_links
    set use_count = use_count + 1,
        last_used_at = now()
    where token_hash = p_token_hash
      and revoked_at is null
      and (expires_at is null or expires_at > now())
      and (max_uses is null or use_count < max_uses)
    returning id, role, target_email, expires_at;
$$;

revoke all on function public.access_share_redeem(text) from public, anon, authenticated;
grant execute on function public.access_share_redeem(text) to service_role;

-- 財神也要能建立分享連結。
update auth.users
set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb)
    || jsonb_build_object('access_role', 'admin')
where lower(email) = 'fortune@investment.local';

insert into schema_migrations (filename) values ('056_access_share_redeem_nullable.sql')
on conflict (filename) do nothing;
```

## 5. 驗證步驟（修完後照做）

### 5.1 自動化驗證腳本

```bash
source ~/.zshrc
python3 - <<'PY'
import json, os, urllib.request, urllib.error, secrets, hashlib
tok = os.environ['SUPABASE_ACCESS_TOKEN']
REF = 'dehzxlxyfvtnylwgbmqy'; URL = f'https://{REF}.supabase.co'
MGMT = f'https://api.supabase.com/v1/projects/{REF}'

def sql(q):
    r = urllib.request.Request(MGMT + '/database/query',
        data=json.dumps({'query': q}).encode(),
        headers={'Authorization': 'Bearer ' + tok, 'Content-Type': 'application/json'})
    return json.load(urllib.request.urlopen(r))

def post(u, h, b):
    r = urllib.request.Request(u, data=json.dumps(b).encode(), headers=h)
    try:    return 200, json.load(urllib.request.urlopen(r))
    except urllib.error.HTTPError as e: return e.code, json.loads(e.read())

def mgmt(path):
    return json.load(urllib.request.urlopen(urllib.request.Request(
        MGMT + path, headers={'Authorization': 'Bearer ' + tok})))

ANON = next(k['api_key'] for k in mgmt('/api-keys?reveal=true') if k['name'] == 'anon')

# 1) 版本檢查
v = next(f['version'] for f in mgmt('/functions') if f['slug'] == 'access-share')
print('access-share version =', v, '(應該 >= 2)')

# 2) 永久 + 不限次數的連結，兌換兩次都要成功
token = secrets.token_hex(32)
h = hashlib.sha256(token.encode()).hexdigest()
row = sql(f"""insert into public.access_share_links
    (token_hash, role, target_email, expires_at, max_uses, created_by)
    select '{h}','holdings','holdings@investment.local', null, null, id
    from auth.users where email='admin@investment.local' returning id;""")
rid = row[0]['id']
try:
    for i in (1, 2):
        c, b = post(f'{URL}/functions/v1/access-share?action=redeem',
                    {'Content-Type': 'application/json',
                     'Origin': 'https://frank-invest.github.io'}, {'token': token})
        print(f'  第 {i} 次 redeem HTTP {c}', 'tokenHash OK' if b.get('tokenHash') else b)
        assert c == 200 and b.get('tokenHash'), '❌ 兌換失敗'
        c2, s = post(f'{URL}/auth/v1/verify',
                     {'apikey': ANON, 'Content-Type': 'application/json'},
                     {'token_hash': b['tokenHash'], 'type': b.get('type', 'magiclink')})
        print(f'     verify HTTP {c2} email =', (s.get('user') or {}).get('email'))
        assert c2 == 200 and (s.get('user') or {}).get('email') == 'holdings@investment.local'
    print('  use_count =', sql(f"select use_count from public.access_share_links where id='{rid}';"))
    print('✅ 永久 + 不限次數連結可重複兌換')
finally:
    sql(f"delete from public.access_share_links where id = '{rid}';")
    print('  測試資料已清除')
PY
```

### 5.2 手動 UI 驗證（必做，使用者最在意這段）

1. 用 admin（或財神）登入 `https://frank-invest.github.io/`。
2. 分享列選「持股」+「**1 個月**」→ 按分享 → 應成功複製網址（修好前會 `400`）。
3. 分享列選「監控」+「**永久**」→ 按分享 → 應成功（修好前會變成 1 天 1 次）。
4. 按「分享清單」→ 面板應列出剛剛兩筆，時效欄顯示「30 天」「**永久**」，次數欄顯示「0 / **不限**」（修好前面板是空的，因為 `list` 回 404）。
5. **開無痕視窗**貼上持股分享網址 → 應直接進入**持股權限**，不是訪客模式；網址列的 `?invite=` 會自動消失。
6. 同一條網址**再開一次**無痕視窗 → 因為是不限次數，應**再次**成功（這證明 `db/056` 的 null-safe 生效）。
7. 回 admin 視窗按「分享清單」→ 對應那筆的「已使用」欄應該有次數與時間（修好前永遠是 `0 / 未使用`）。

## 7. 可能踩到的坑

- 本機**沒有** `supabase` CLI，一律用 `npx supabase`。
- DDL 不要嘗試用 `psql`；本專案慣例是 Supabase Management API 的 `/database/query`。
- Management API 的 `/database/query` 用 JSON body，**SQL 裡的單引號在 shell 裡很難跳脫** ——
  請像本文件一樣用 `python3 - <<'PY'` heredoc 送出，不要硬用 `curl -d` 拼字串。
- 測試時若要直接 `insert` 進 `access_share_links`，記得 `created_by` 是 NOT NULL，
  要 `select id from auth.users where email='admin@investment.local'`。
- **測完一定要把測試用的 row 刪掉**，不要留在正式表裡。
- `.cs` / `.js` 的契約測試一律用 `.ReplaceLineEndings("\n")` 正規化再比對；
  斷言字面不要寫死 `\r\n`，否則本機全綠、Linux CI 會紅。
