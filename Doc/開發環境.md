## 裝置分工

**這台 Mac 是主力機**，其他裝置是輔助。原因不是偏好，是有幾件事只在這台做過：

| 只在 Mac 上有的東西 | 為什麼重要 |
|---|---|
| `~/.zshrc` 裡的 `SUPABASE_DB_URL` 與 `SUPABASE_ACCESS_TOKEN` | 沒有這兩個就不能同步、備份、貼資料表定義 |
| GitHub 的 SSH key | `origin` 用的是 `git@github.com:` |
| 已經回補好的 `data/imports/`（328 天，約 20 MB） | 新裝置可以從 `data` 分支取，不必重抓 |

**好消息是：日常運作完全不需要任何裝置開機。**
每天的回補、同步、備份、發佈都在 GitHub Actions 上跑。
輔助裝置要做的只有「改程式碼」跟「看網站」。
所以接手時**先確認「是不是真的需要在本機跑」**：多數故障只要在 Actions 上重跑就解決了，
那條路完全不需要下面任何一個套件。

### `libpq` 的兩個雷（都已經在腳本裡處理掉了）

1. **它是 keg-only**，`brew install libpq` **不會**把 `pg_dump` 放進 `PATH`。
   主力機跑 `which pg_dump` 是找不到的，但備份照樣能跑——
   [backup-supabase.sh:21](../scripts/backup-supabase.sh#L21) 會自己去 `/opt/homebrew/Cellar/libpq/*/bin/` 撈。
   要指定別的路徑就設環境變數 `PG_DUMP`。
2. **`pg_dump` 的版本不可以比伺服器舊。** Supabase 是 PostgreSQL **17.6**，
   主力機是 18.6（比較新，可以）。用 16 會直接 `exit 1`，不是警告。
   GitHub Actions 的 runner 內建 16，所以 workflow 裡有一步專門裝 17。

### Windows 的 PATH

Windows 若 `C:\Program Files\dotnet\dotnet.exe` 排在 PATH 前面，可能會先找到 .NET 8，
即使使用者帳號已安裝 .NET 10。新開 PowerShell 後執行：

```powershell
dotnet --version
```

結果必須是 `10.x`。若仍是 `8.x`，把使用者 PATH 的
`%LOCALAPPDATA%\Microsoft\dotnet` 放到目前 shell 的 PATH 最前面，或直接使用該目錄內的 `dotnet.exe`。
不要為了這個 repo 改掉整台機器的 Machine PATH；這個專案的 `global.json` 已經負責 SDK 選擇，
shell 只需要先找到能看見 .NET 10 SDK 的 host。

那台 Windows 的 PowerShell 7 與 Windows PowerShell 5.1 都已設定使用者 profile，
會將上述目錄放到 PATH 最前面；目前使用者的 execution policy 是 `RemoteSigned`，
而 `LocalMachine` 仍維持 `AllSigned`。新開任一種 PowerShell 後，`dotnet --version` 都應是 `10.x`。

若在另一台 Windows 需要同樣設定，請在該使用者自己的 PowerShell 執行：

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

### 盤中 CDN 啟用（只影響盤中資料）

在 Supabase Dashboard 的 **Storage** 建立 bucket `intraday-snapshots`，設為 **Public**，並限制內容類型為
`application/json`、單檔上限至少 10 MB。這個 bucket 只能放公開行情、指數與由同一輪行情導出的族群熱度；
絕不能放筆記、資產、使用者資料、資料庫備份或任何權杖。

接著到 GitHub repository 的 **Settings → Secrets and variables → Actions** 新增 repository secret
`SUPABASE_STORAGE_SECRET_KEY`。它只會傳入 `.github/workflows/intraday.yml` 的收集器，以及
`daily-snapshot.yml` 的靜態匯出判斷；不會寫入 `manifest.json`、網站 JavaScript 或 Actions log。

預期結果是收集器每一輪先上傳不可覆寫的 `intraday-YYYYMMDD-HHmm-runN.json`，再更新很小的
`latest.json`。若 Actions 顯示「CDN 快照發佈失敗」，請提供該次 run URL、失敗步驟與 HTTP 狀態碼；
不要貼出 secret。啟用後下一次成功的 daily export 會把 `intradayCdn` 寫入 manifest，只有盤中排行、
自訂盤中、族群熱度／族群列表盤中模式會改走 CDN，其他功能維持原本 Supabase 資料流。

`IntradayCdn:RetainedSnapshotCount` 預設為 `30`，收集器只會清理超出數量的
`intraday-*.json` 舊版本檔（約 60 分鐘）。`latest.json`、未知檔案與其他 bucket 一律不動；
清理使用 Storage API，不直接刪 `storage.objects`，避免留下孤兒檔案。

`~/.zshrc` 裡的東西**只有互動式 shell 讀得到**。非互動指令（很多 agent 預設如此）要用 `zsh -ic '...'`，
否則會拿不到變數而誤判成「沒設」。

**這兩個值不在 repo 裡，也永遠不要放進 repo。**
`appsettings.json` 裡那組 Supabase URL 與 anon key 是**故意公開的**：
anon key 只有 select 權限（見 `db/001_intraday.sql` 的 RLS），
而且它會被發佈到 gh-pages，任何人都看得到，藏起來沒有意義。

`SUPABASE_ACCESS_TOKEN` 約 **2026-09-15** 到期（TODO 6 在追）。


**Contents RW**（推程式碼）、**Actions RW**（觸發／重跑 workflow）、
**Metadata R**（必選）、Pull requests RW（只有要開 PR 才需要）。
classic token 則是 `repo` + `workflow` 兩個勾。

### Supabase Edge Function secrets

跟上面「主力機／CI 環境變數」是不同層——這些只存在 Supabase 專案本身
（`supabase secrets set NAME=value --project-ref dehzxlxyfvtnylwgbmqy`），Edge Function
執行時才讀得到，**不會出現在 repo、CI log 或前端**。目前用到：

| 名稱 | 給哪支 function 用 | 缺了會怎樣 |
|---|---|---|
| `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | 全部 function（Supabase 平台自動注入，不用自己設） | 打不到 PostgREST，function 直接 500 |
| `OCR_CLEANUP_SECRET` | `ocr-jobs`（保護 `?action=cleanup` 端點） | 該端點永遠回 403，不影響一般 OCR 流程 |
| `GH_ACTIONS_PAT` | `us-watchlist-dispatch`（見下） | 只是不觸發即時回補，隔天排程仍會照常跑 |

**`GH_ACTIONS_PAT`**：新增美股持倉後，即時觸發 `us-daily-snapshot.yml` 用的
fine-grained PAT，範圍限定在 `qwe953751/Investment` 這個 repo、只勾
**Actions RW**、**Metadata R**（不用 Contents，這支 function 只觸發 workflow、不推程式碼）。
跟 `gh auth login` 那組個人 OAuth token是分開的一組憑證，故意縮到最小權限，
就算外洩也只能觸發／取消這個 repo 的 workflow，不能讀寫程式碼或其他資料。

### 美股新持倉即時觸發（`asset_holdings` trigger）

實作**不是**用 Dashboard 的「Database Webhooks」UI（這個專案從沒開過那個功能，
`supabase_functions` schema 一直不存在），而是直接用專案本來就有的 `pg_net` extension
（`net.http_post`）手刻一個 trigger function，2026-09-07 透過 Management API
（`POST /v1/projects/{ref}/database/query`，跟套用 `db/*.sql` 同一支 API）直接下 DDL 建立：

```sql
create or replace function public.dispatch_us_watchlist_webhook()
returns trigger
language plpgsql
security definer
set search_path = public
as $func$
begin
  perform net.http_post(
    url := 'https://dehzxlxyfvtnylwgbmqy.supabase.co/functions/v1/us-watchlist-dispatch',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'Authorization', 'Bearer <service_role key，見下方取得方式>'
    ),
    body := jsonb_build_object(
      'type', 'INSERT',
      'table', 'asset_holdings',
      'record', to_jsonb(new)
    ),
    timeout_milliseconds := 5000
  );
  return new;
end;
$func$;

drop trigger if exists asset_holdings_us_watchlist_dispatch on public.asset_holdings;

create trigger asset_holdings_us_watchlist_dispatch
after insert on public.asset_holdings
for each row
execute function public.dispatch_us_watchlist_webhook();
```

`security definer` 讓這個 function 用建立者（Management API 呼叫時的高權限身分）的權限執行
`net.http_post`，不受觸發它的角色（`anon`）影響。payload 形狀故意比照 Supabase 官方 Database
Webhook 的慣例（`{type, table, record}`），`us-watchlist-dispatch/index.ts` 的解析邏輯兩種來源
通用，之後想改回官方 Dashboard Webhook 也不用動 function 程式碼。

**這段 SQL 沒有、也不能進 `db/*.sql`**：函式本體字面內嵌了 service_role key（拿 anon key 沒用，
`us-watchlist-dispatch` 會擋掉非 service_role 的呼叫，見下方安全性說明），比 `SUPABASE_DB_URL`／
`SUPABASE_ACCESS_TOKEN` 更敏感，**復原資料庫時要記得用上面樣板手動重建**，`<service_role key>`
現查現填：

```bash
curl -s "https://api.supabase.com/v1/projects/dehzxlxyfvtnylwgbmqy/api-keys" \
  -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  | python3 -c "import json,sys;print([k['api_key'] for k in json.load(sys.stdin) if k['id']=='service_role'][0])"
```

驗證方式：`select id, status_code, content from net._http_response order by id desc limit 5;`
（Management API 查詢），新增一筆測試持倉後應該看到一列 `status_code=200`、
`content` 是 `{"dispatched":true,"ticker":"..."}` 或 `{"skipped":"...原因"}`。
2026-09-07 已用假持倉（ticker `TSLA`，測完立刻刪除）實測整條鏈路：insert → trigger →
`net.http_post` → Edge Function → 觸發 `us-daily-snapshot.yml`（run `34053447753`）成功。

## 各裝置做得到什麼

| 裝置 | 改程式碼 | 本機跑網頁 | 本機備份 | 觸發／重跑 workflow | 看網站 |
|---|---|---|---|---|---|
| 主力 Mac | ✅ | ✅ | ✅ | ✅ | ✅ |
| 公司電腦 / 其他 Mac、Windows、Linux | ✅ 裝好 .NET 10 就行 | 需要行情快取 | 需要 `SUPABASE_DB_URL` + `pg_dump` ≥ 17 | 需要 GitHub 權限 | ✅ |
| iPhone / iPad | 只能用 GitHub 網頁編輯器改文字檔 | ❌ | ❌ | ✅ 用 Safari 開 github.com | ✅ |

**改完程式碼要記得的事：** 只要動到畫面或計算，
就得重新 `export` 並發佈，否則手機上看到的還是舊的。
不想在本機做的話，推上 `main` 之後到 Actions 手動觸發 `每日排行快照`
（`workflow_dispatch`，可以指定只回補幾個交易日）也會順便重新發佈。
若今日行情尚未公布、只需要把已推送的畫面修正發布出去，手動觸發時可勾選
`publish-only`；它只使用 `data` 分支現有快取重新 export／發布，不回補今日行情、不同步 Supabase，
也不改動 `data` 分支。這個選項不能取代收盤後的完整快照流程。

### 發布到新網址（正式網址 frank-invest.github.io）

平常都靠 GitHub Actions（`daily-snapshot.yml`）自動發布，不用手動做這件事；
以下是任何一台裝置想**手動**重新發布時要知道的事。

正式網址是 `https://frank-invest.github.io/`，單一網址，內容直接發在根目錄。
打開就是**訪客模式**，監控者／最高權限要在頁首右上角用密碼登入才能拿到
（2026-09-01 起收掉過渡期用的 `admin888/`、`viewer/` 這兩個子路徑網址，不再靠
路徑當防線）。

舊網址 `https://qwe953751.github.io/Investment/` 也只剩空白頁，不再更新內容，
不用管它。`scripts/publish-gh-pages.sh` 的行為是：**不帶
`GH_PAGES_PUBLISH_ROOT` 就只發空白頁**，這是刻意的預設值，避免哪天漏設環境變數
就把內容洩漏到根目錄。手動發布到正式網址一定要帶兩個環境變數：

```bash
dotnet run --project src/Invest.Web -- export "$(pwd)/publish/site"

GH_PAGES_REMOTE=https://x-access-token:$(gh auth token)@github.com/frank-invest/frank-invest.github.io.git \
GH_PAGES_PUBLISH_ROOT=1 \
scripts/publish-gh-pages.sh publish/site
```

`gh auth token` 拿的是目前這台裝置 `gh` 登入帳號的 token，這個帳號要對
`frank-invest/frank-invest.github.io` repo 有寫入權（目前是 CI 用的
`FRANK_INVEST_PAT` 那組個人 token 對應的帳號，本機 `gh auth login` 用同一個
GitHub 帳號登入即可）。沒有寫入權會在 `git push` 那步被拒絕，不是腳本本身的錯。

發布完先看終端機印出的「已發佈快照…到網域根目錄」那行確認有帶到內容，
再去 `https://frank-invest.github.io/` 實際點開確認版本號跟預期一致——
不要只看指令有沒有報錯，指令成功不等於發布到對的位置（漏帶環境變數也會顯示
「已發佈空白頁」但不會報錯，是正常結束）。

## 常見雷

| 症狀 | 原因 |
|---|---|
| `找不到環境變數 SUPABASE_DB_URL` | 沒設、設在別的 shell profile，或是在非互動 shell 裡跑（要用 `zsh -ic`） |
| `pg_dump: server version mismatch` | 本機 `pg_dump` 比 Supabase（17.6）舊 |
| 排行頁一片空白、說資料不足 | 沒有行情快取，先取 `data` 分支或 `backfill` |
| 手機上看到舊資料 | 沒有重新發佈；或按一下標題旁的「檢查更新」 |
| 改了 `CollectionSchedule` 的時間但排程沒變 | cron 寫在兩支 YAML 裡，讀不到 C#，要手動改（TODO 8 未決） |
| `dotnet test` 找不到 SDK | 裝的是 .NET 8/9，這個專案要 10 |
| push `.github/workflows/*.yml` 被拒 | token 少了 `workflow` scope |
