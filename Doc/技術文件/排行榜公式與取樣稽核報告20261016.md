# 排行榜公式與取樣稽核（2026-10-16）

狀態：**調查證據保留；五項問題已依後續授權完成實作及本機驗證，待本輪發布**。原稽核輪僅新增本報告，後續實作／驗證／發布狀態見[交接方案第13節](排行榜公式與歷史資料修正實作交接方案20261017.md#13-2026-10-17-實作與驗證紀錄)。盤中估算成交額與盤後官方成交額的差異不列為本輪問題。

**2026-10-17 使用者定案**：表頭只整理原榜前 100 檔，保留既有設計；盤中成交熱度對照失敗時，畫面仍視為載入完成，背景自動重試，不顯示錯誤彈窗或要求使用者按重試。後續完整契約以[實作交接方案](排行榜公式與歷史資料修正實作交接方案20261017.md)為準；本報告的重現證據不代表這些問題已修正。

## 1. 結論

不能認定「全部公式與取資料方式都正確」。已驗證成交熱度的基本日期窗口、加總、均值、成交比與增減率在本次樣本中正確，但另有五項可重現缺陷：

1. 盤中資金加速的基準跟隨觀察期間 N，與 C# 固定 20 日中位數的規格不同。
2. 歷史排行的市場別採最新股票資料，造成回看歷史時套用未來的市場分類。
3. 量比先取四位小數再由前端排名，會改變原本不同的分數順序與排名變化。
4. 盤中成交熱度的對照檔讀取失敗後，沒有可靠的背景自動補齊；「畫面先完成」已由使用者確認保留。
5. 同一交易日當日缺收盤價時，收盤價欄可能隨觀察期間改變；價格沿用邏輯未完整接入輸出。

另外有三個現行設計容易被誤認為計算錯誤，見第 5 節：表頭排序只重排原榜前 100 檔、排名數字不隨表頭改排、前期排名採本期候選集合。

## 3. 已驗證正確的部分

### 3.1 日期窗口

以 D=2026/10/16、N=60 為例：

| 檢視 | 本期 | 比較期 |
|---|---|---|
| 盤後／區間 | 7/22～10/16，60 個交易日 | 4/24～7/21，前一段 60 個交易日 |
| 盤後／單日 | 10/16，1 個交易日 | 7/21～10/15，之前 60 個交易日 |
| 盤中 | 快照交易日當日累計 | 快照日期以前的 60 個交易日，7/21～10/15 |

C# 先截取 D 以前的日期，再切本期與前期；盤中對照日嚴格早於快照交易日，沒有把 10/16 收盤拿來與 10/16 盤中自己比較。本次 40 組日期標示與實際窗口一致。

### 3.2 基本算術與輸出

| 欄位 | 實際規則 |
|---|---|
| 區間日均成交值 | 該段總成交值 ÷ 該段市場交易日數；個股缺交易列不縮短分母 |
| 單日成交值 | 所選交易日的單日值，N 只控制比較期 |
| 較前期增減 | （本期日均值－前期日均值）÷ 前期日均值；前期為零時為空值 |
| 市場成交比 | 個股該期總成交值 ÷ 全市場該期總成交值 |
| 成交比變化 | 本期市場成交比－前期市場成交比，顯示為百分點 |
| C# 資金加速 | （本期日均值+k）÷（本期前 20 日個股中位數+k） |
| k | 0.25 × 上市櫃普通股正值基準中位數的中位數 |
| 資金加速流動性門檻 | 上市櫃當期成交值中位數 × 0.6；興櫃不參與校準 |

全市場成交比分母包含上市、上櫃、興櫃普通股，不隨畫面市場／成交門檻縮小，不含 ETF 與 TDR。

驗證結果：

- C# 與公開 JSON：556,080 個欄位比較，在既定匯出四捨五入規則下 **零差異**。
- 獨立逐日算術與 C#：1,018,160 個數值比較 **零差異**。
- 前端篩選／排序：640 組成交熱度案例，與未縮減精度的 C# 數值排序 **零差異**；資金加速的精度問題另列於 4.3。

這些結果證明基本算術與目前資料的輸出一致；不會替第 4 節的錯誤市場分類或其他輸入問題背書。

### 3.3 取檔路徑

- 盤後區間：`data/{N}-{D}.json`。
- 盤後單日：`data/1-{D}.json` 的當日值、價格與成交比，合併 `data/single-{N}-{D}.json` 的前期值、增減率、量比與成交比變化。
- 盤中：已接受 raw 快照，加上嚴格早於快照交易日的 `data/{N}-{referenceDate}.json`。
- 盤後市場結構按 D 取檔，不跟著 N 改成 N 日結構；市場熱絡與大盤日／週漲跌也以 D 為日期基準。

本次未發現上述正常成功路徑拿錯期間檔；失敗路徑另見 4.4。

## 4. 已確認缺陷與處理方向

### 4.1 盤中資金加速的基準定義不同（高優先）

位置：`site.js` 的 `loadIntradayResult`；C# 的 `TradingValueRankingCalculator.Calculate`／`Preceding`／`Medians`。

- 盤後分母固定取「本期之前 20 個交易日」的個股成交額中位數。
- 盤中分母取所選 N 日對照檔的 `past.share`，它是 N 日總額占全市場 N 日總額的比例。
- 中位數與 N 日加總比例不是同一種統計量；同一式子的分子分母分別除以不同市場總額，也不能以「尺度無關」證明等價。
- 盤中前期排名直接借用對照區間的 `volumeRatio`，仍不是盤後單日 `previousVolumeRatio` 的同一口徑。
- 已固定相同官方當日輸入、排除盤中估算差異後測試：60 日資金加速前 100 名只有 75 檔相同、相同名次位置為 0。

**方向**：先以最新需求與 C# 權威規則定義唯一的盤中指標，再輸出可追溯的基準與排序資料；需要保留盤中市場成交比指標時，必須明確定義它與固定 20 日成交額中位數指標的關係。不能只把 N 改成 20，或宣稱改用 20 日平均成交比就等同 20 日成交額中位數。須經指標契約確認後實作。

### 4.2 回看歷史卻套用最新市場別（高優先）

位置：`TradingValueRankingQueryService.ToDataSet` 逐日覆蓋 `stocks[ticker]`；`TradingValueRankingCalculator.EnsureIndex` 使用這份最新股票資料處理所有查詢日期。

| 股號 | 歷史日 | 當日 imports 市場 | 公開歷史排行市場 |
|---|---|---|---|
| 2938 床的世界 | 2026/09/15 | Emerging | tpex |
| 5236 凌陽創新 | 2026/07/15 | Tpex | twse |
| 2237 華德動能 | 2026/08/07 | Emerging | twse，名稱亦為最新的華德動能-創 |

這不是金額加總錯誤，是歷史查詢的市場篩選與分類輸入不正確；也可能影響歷史上市櫃校準集合及 k。不能因金額不變就忽略。

**方向**：股票市場別／種類／名稱需有生效日期，歷史查詢使用不晚於 D 的有效資料。明確規範多日區間以 D 的市場身分，或逐日市場身分分組；不得用 D 之後的分類。保留轉板前後、分類及校準集合的回歸案例。

### 4.3 量比四捨五入後再排名，順序會變（中優先）

位置：`StaticSiteExporter.RoundRatio` 保留 4 位小數；前端 `rankRows` 再用 `volumeRatio`／`previousVolumeRatio` 重新排名。

實例：10/16、10 日區間、資金加速、上櫃、門檻 5 億：

| 股號 | 原始量比 | 匯出量比 | 未截精度名次 | 前端名次 |
|---|---:|---:|---:|---:|
| 8299 | 0.925414158… | 0.9254 | 68 | 69 |
| 7717 | 0.925374182… | 0.9254 | 69 | 68 |

不同分數在前端變成同分，改以股號排序。前期量比也會發生相同問題，影響名次變化。

1,280 組篩選／排序中，111 組出現名次或名次變化差異，全部在資金加速；44 組實際位置改變，本次每組最多兩個位置，候選數均一致。這是可重現的精度問題，不是整份榜單大風吹的充分解釋。

**方向**：顯示精度與排序精度分離。可保留未縮減的排序值，或由 C# 輸出不受篩選影響的本期／前期排序序位，再讓前端篩選後編號；驗證邊界同分及前期第 200 名顯示上界。不能只用「畫面顯示四位已足夠」合理化排序值截斷。

### 4.4 成交熱度對照失敗後缺少背景自動補齊（中優先）

位置：`loadIntradayResult` 只有資金加速會檢查 `referenceByTicker.size === 0`。

受控重現：目前選 60 日、讓 `fetchPeriod` 返回 null，實際 loader 仍提交 current，`referencePeriod` 為「資料不足」，成交比變化全為 null；摘要已重畫，`ranking-status` 隱藏。因此成功看到排行不代表 60 日對照已成功載入。

**方向（2026-10-17 使用者定案，取代原先錯誤提示／手動重試建議）**：今日排行照常顯示，畫面載入完成；內部另外記錄比較資料是否完整，背景自動重試並就地補齊。不新增錯誤彈窗、失敗橫幅或手動重試要求。尚無正確比較時使用既有空值，不填 0、不借其他 N／日期；同 key 已成功的比較可重用。區分真的歷史不足與可重試故障，完整排程、失效與提交防護見實作交接方案。

### 4.5 同日切換 N，當日缺收盤價的價格欄跟著改變（中優先）

位置：計算器雖呼叫 `PricePerformanceCalculator.Calculate(... carryForward: true)`，輸出的 `ClosePrice` 仍取 `candidate.Current.EndClose`，未取已統一沿用規則的 `price.Close`。

公開資料實例（D=2026/09/16）：

| 股號 | 1 日檔 close | 5／10／20／60 日檔 close |
|---|---|---|
| 1423 利華 | null | 35.25 |
| 1541 錩泰 | null | 20.75 |

兩檔的日漲跌均為 null、週漲跌不隨 N 改變；只有收盤價取值受本期範圍影響。183,680 個同日跨 N 的價格欄位比較中，8 個差異均為這兩檔的 close；不是所有日／週漲跌都有錯。

**方向**：收盤價取值與日／週漲跌共用 D 的統一價格結果，必要時帶來源日期及沿用標記；同日只改 N 不應改變價格來源。個股當日沒成交或沒收盤價，不能拿更長區間才偶然找得到的價格冒充當日收盤。

## 5. 現行設計：容易覺得排行榜怪，但不宜直接當公式 bug

### 5.1 表頭排序只在原榜前 100 檔內重排

`rankRows` 先按模式挑前 100；`sortedRows` 再按表頭重排那 100 檔。

10/16、單日、60 日、成交熱度、全市場、1 億門檻：全市場合格候選的「成交比變化前 100」有 46 檔不在原成交熱度前 100，所以不會因點該表頭而出現。

例如 6715 嘉基的成交比變化約 +0.12711 個百分點，在全候選依成交比變化排序是第 37，但成交熱度排名第 105，因此表格看不到。這個例子不代表目前表頭排序程式算錯，是它只整理原榜的範圍。

**產品決策已定案（2026-10-17）**：使用者明確指定「只整理原榜前 100」，這正是原始設計。保留現行行為，不再列為問題或待確認事項，不擴大成全市場依表頭重新選榜。

### 5.2 排名數字與顯示列位置不同

排名欄始終是成交熱度／資金加速模式的名次。點「成交比變化」後，列可以變成排名 1、2、4、8、5…，並非列順序從 1 重編。若需行號，應另設呈現，不能用它覆蓋指標名次。

### 5.3 前期排名採本期候選集合

本期先套市場、成交門檻及資金加速流動性門檻，再以同一批候選回排前期。因此排名變化是「今天這批候選在前期各排第幾」，不是讀取前一期已發布排行榜上原本的名次。市場／門檻改變，名次變化也可能變。

這與現行 README 的同候選集合規格一致。若要跨日固定母體或比較前期獨立榜單，是另一個產品定義，應先決定再改。

### 5.4 單日／盤中成交熱度切換 N，不改今日成交額排行

當 D、模式、市場與門檻固定時，單日成交熱度的當日值不因 N 改變；N 改的是比較期、成交比變化及排名變化。區間成交熱度的本期本來就有 N 天，所以切 N 才會改變日均成交值及名單。不能只憑單日名單不變判定 N 沒作用。

## 6. 文件與畫面說明的錯誤

- README「排行模式」仍把資金加速寫為成交值增減率、資料量 3N；實際 C# 已是固定 20 日中位數的收縮量比。
- `MODES.singleDayHint` 寫成相較前 N 日平均的量比，與實際固定 20 日中位數不同。
- `MODES.hint`／`TradingValueRankingResult.InsufficientData` 的「3N」或「再前 N 日」說明，與實際 `2N+20`（區間）／`1+N+20`（單日）判斷不同。
- `VOLUME_RATIO_HINT` 對缺基準／長期停牌說「算不出來顯示 —」，但 `AccelerationRules.ShrunkRatio` 明確把個股缺基準視為 0、仍以 k 計算；只有全市場 k 無法建立才返回 null。
- README 某些舊段落仍稱市場分母只有上市＋上櫃；最新範圍與實作含興櫃。

文件須跟隨已確認的唯一公式一起修正，不能讓提示與計算各自代表不同規則。
