### 2.2 盤後整區消失：已在正式頁面重現

### 2.3 下載與快取：已驗證

以下為本機對正式 Pages 使用 gzip 的有限抽測，不是手機效能保證，也不是完整 P95：

## 5. 載入與提交契約

### 5.1 分清三種狀態

| 狀態 | 意義與內容 |
|---|---|
| 目前選擇 | 使用者最新想看的頁面、日期、期間、比較方式、模式、市場與門檻；可以先於新資料更新。 |
| 載入工作 | 開始載入時取得的不可變上下文、遞增工作識別及目標資源 key。 |
| 已提交畫面 | 實際顯示的資料及其日期、期間、模式、來源輪次、版本；只在完整驗證後一起替換。 |

不能只用全域 `state` 解釋尚未替換的舊資料；也不能把 `JSON.stringify(state)` 當唯一防護。排序、鎖定、外觀等純顯示變化不應讓正確的資料下載永遠無法提交。

建議有兩層識別，名稱由實作者決定：

- **意圖世代**：離開／進入頁籤，或改日期、期間、比較方式、模式、市場、門檻時立即失效舊意圖；A→B→A 也必須是不同世代。市場切換入口亦需檢查。
- **工作識別與來源版本**：處理同一意圖的多次載入、自動更新與 raw 前進。相同工作應合併；新來源取代舊工作，舊工作不能提交。

最晚在第一個 await **之前**固定本次選項。參與資料選擇／候選與排名的計算全部用這份上下文，不在下載後重新偷讀已變動的全域選項。

### 5.2 盤中資料流

1. 建立本次意圖／工作上下文；呼叫既有快照確保流程。
2. await 回來先確認仍屬於有效意圖，再同步取得同一份 raw、summary 與來源識別。
3. 對照日嚴格取 `dates` 中小於該快照交易日的最後一天，不能固定取今天或 dates 最後一天。
4. 固定對照 key：本次期間＋對照日；取得資料後再次驗證意圖、工作與 raw 來源。
5. 使用既有映射、候選、門檻及排序公式建構結果；以同一個同步提交動作更新 current、顯示上下文、摘要、表格及鎖定列。
6. 市場結構另外非同步補上，僅能寫回這次提交的物件與來源；不阻塞排行。

任何舊工作不得更新 current、`nameByTicker`、錯誤／載入提示、busy 狀態、市場結構、延後表格列或可見摘要。`finally` 清除 busy 也要驗證自己仍是目前工作。

raw 來源至少以「被接受快照的本地遞增 revision＋tradeDate＋capturedAt＋實際來源」識別。CDN 同輪保留其 run/hash 驗證；不要深複製數千列，只需確保來源物件不被原地修改。

**fallback 注意事項**：目前 `intradaySnapshotRunId` 可能保留先前 CDN run，作為拒絕倒退的水位。該水位不能冒充新一輪 DB fallback 的實際 run。新顯示上下文要分開記來源實際 run（可能為 null）與防倒退水位；無同輪證據時依既有契約顯示結構未取得，不能借用別輪結構。

若等待對照時 raw 已前進，舊結果不得提交；必須確保已安排「目前選擇＋最新 raw」的一次後續工作，避免只丟棄舊結果、卻永遠留在載入中。可重用已下載的對照檔，不另打 DB。

手動選擇、自動輪詢、前景喚醒、兄弟分頁廣播、檢查更新都走同一套提交規則。同意圖同來源的重複觸發要合併，避免每次喚醒都使進行中的工作失效而餓死；force 更新的要求仍須確實執行，可合併成一次待處理更新。

### 5.3 跨頁與延後回呼

盤中／盤後／自訂／ETF 共用 current。僅修盤中最後一行仍可能被別頁較晚完成的工作覆蓋。所有相關 loader 在提交前核對 owner；離開排行 host（族群、筆記、資產或其他市場）時撤銷舊工作的顯示資格。

保留 `pendingTableRows` 的物件身分防護，並補上已提交畫面識別；離開頁籤或新畫面提交時，舊的 requestAnimationFrame／setTimeout 不可補列或觸發舊跳轉。營收／分類／停牌等背景補充重畫也不能將舊 current 按新選項重新解釋。

盤後結構晚回來只補同日、同一 current 物件的摘要；盤中結構還要符合實際同輪來源及既有 hash 校驗。不可只比日期或保留的 run 水位。

## 6. 局部載入、成功與失敗 UI

本輪不要直接改變全站 `showNotice()` 的所有呼叫語義。新增排行切換專用的載入／錯誤狀態，逐一替換盤中與盤後相關入口；登入、筆記、資產等既有錯誤流程保持原意。

| 情況 | 要呈現的行為 |
|---|---|
| 首次進站、無已提交排行 | 可顯示骨架或載入文字；可用選項不因排行尚未下載而整區消失。 |
| 同頁換日／換期間 | 選項即時反映新選擇；保留布局與目前結果，顯示「正在讀取…；目前仍顯示…」的實際日期／期間。 |
| 新資料到位 | 一次替換對應的摘要、表格、已顯示期間與鎖定資訊；移除 busy。 |
| 新資料失敗 | 清楚說明「新選擇尚未載入；目前保留的是哪份資料」，提供針對目前選擇的重試；不得自動退成 1 日。 |
| 舊請求失敗或完成 | 不改目前畫面、不跳警告、不清掉新工作的 busy。 |
| 市場結構較慢／失敗 | 排行照常可用，結構卡片顯示自己的等待／錯誤與重試。 |
| 純模式／市場／門檻改變且資源已在記憶體 | 就地重算篩選與排序，不隱藏整區，不重新下載同份資源。 |

保留舊結果時不得讓它看起來已套用新選擇。舊表的依資料操作（排序、K 線、族群連結、跳轉等）需綁定已提交上下文，或在切換等待時暫停；採較小且可驗證的方案。新意圖的操作選項必須仍可使用。

使用適當的 `aria-busy`／`role=status`，狀態文字可被讀屏理解。不要只靠半透明或 pointer-events 處理鍵盤操作。保留表格高度／操作區位置，避免焦點遺失與滾動跳到頁首；跨不同頁籤則顯示該頁自己的內容或骨架，不把舊盤中表冒充盤後。

慢速提示可於等待約 3 秒後顯示「仍在載入」，只改狀態文字，不阻擋操作。**本輪先保留目前 30 秒與一次重試政策**，不要為了縮短體感逾時而讓行動網路更常失敗；解決長等待的方法先是可取消的顯示資格、保留畫面及去除冗餘請求。

## 7. 資源快取與預抓

### 7.1 已完成快取與下載中請求分開

建議保留 `fetchPeriod(key)` 對既有呼叫端「資料或 null」的契約，內部增加下載中 Map。資源識別包含網站版本與完整 key；一般排行與 `single-` 檔不能撞 key。

| 狀態 | 呼叫時的處理 |
|---|---|
| 已完成且同版本 | 從記憶體回傳，前景使用時更新 LRU。 |
| 同版本同 key 正在下載 | 共用同一個 Promise；前景加入時將它視為前景需求，不再發第二次請求。 |
| 尚未下載 | 先註冊下載中 Promise，再啟動／等待實際下載；一次請求與重試由該資源工作統一管理。 |
| 成功 | 放入已完成快取、清除該資源錯誤，再依身分清理下載中紀錄。 |
| 失敗 | 不快取 null／失敗 Promise；保留可辨識錯誤，清理後允許下次重試。 |

必須在 finally 以紀錄身分確認清理，避免較舊工作刪掉同 key 後來的新工作。內部統一處理 rejection，所有 fire-and-forget 預抓也必須消化錯誤。

維持已完成排行／單日比較合計約 12 份的限制；正在下載紀錄另計。當前顯示與當前必要資源暫時保護，預抓優先淘汰，不讓連續預抓擠掉目前需要的資料；工作完成或離開後解除保護並收斂回上限。不要以放大成無上限 Map 解決問題。

來源資料視為不可變，篩選／排名／補充欄位使用副本。可在測試凍結樣本抓原地修改，正式站不必對每份大資料做昂貴深層凍結。

驗證一般排行回傳 `key` 與請求一致、rows 為陣列；單日比較沿用 `periodDays` 檢查並保留請求 URL／key 的來源身分。現行 single JSON 沒有獨立的機器可讀 tradeDate 欄，不要假設它存在，也不要藉此改匯出 schema。缺少個別股票對照時沿用既有缺值規則，不能補另一期間。

### 7.2 預抓前景優先

本輪保留「同期間前一交易日」方向，不一次預抓所有期間或 120 天資料。

1. 用可撤銷的意圖世代管理 idle callback／fallback timer；日期、期間、比較方式、頁籤、所處市場、網站版本改變後，未開始的舊預抓失效。
2. 只有目前必要排行／比較資料完成，沒有前景關鍵下載、仍在盤後、頁面可見且未啟用 saveData 時，才啟動背景預抓。
3. 背景網路同時最多一份資源；需要排行、single 與結構多份時依序排隊，每份開始前重新核對意圖。
4. 前景需要同 key 時加入現有共用 Promise；不同 key 的新前景需求到來後停止排後續背景資源。
5. 已發出的背景請求可完成快取，但不能更新畫面；最小安全實作不強行 abort 正被前景共用的下載。

`requestIdleCallback` 只代表 CPU 目前空閒，不能單獨當作網路空閒判斷。`resolveCloseMarketStructure()` 已有 Promise 共用，保留其正確行為；調整預抓排程時也要將結構下載列入背景上限。

若實作者選擇進一步 abort 實際網路，必須同時處理共用消費者與重試取消；目前 `fetchJsonAttempt()` 自建 controller 會覆蓋傳入 signal，不能只把 signal 傳進去就宣稱已中止。這項較大變更不列為本輪必要條件。

## 9. 必要測試矩陣

優先用真實 loader 函式搭配受控 I/O；不能 mock 掉 `loadIntraday`／`load` 的核心後只測自己寫的代理函式。受控回應以 deferred Promise 排序，不靠幾秒的真實 sleep。以下每列是一項行為要求，可合理合併測試但不能省略邊界。

| 編號 | 情境 | 必須成立 |
|---|---|---|
| R1 | 1 日慢、20 日快，1 日最後成功；heat／accel 各測 | 最後仍顯示 20 日資料與期間；不得與 1 日整份相同。 |
| R2 | 1 日慢、20 日快，1 日最後失敗 | 沒有舊錯誤、沒有清除 20 日 busy／內容。 |
| R3 | 1→20→1，第一個 1 日最後完成 | 最後一次意圖及最新來源有效，不能僅憑選項相同接受舊工作。 |
| R4 | 連點五個期間、混合快取命中與下載 | 最後選擇勝出，所有欄位同一上下文。 |
| R5 | 改模式、市場或門檻時舊對照仍在下載 | 候選、排名、名次變化與摘要一致，不混讀新全域 state。 |
| R6 | 等待對照時新 raw 到達；含 broadcast／自動刷新 | 舊 raw 不提交，最新 raw 最終一定可見；不重抓已完成對照。 |
| R7 | 同意圖同來源被喚醒事件反覆觸發 | 合併工作，不無限使自己失效；force 更新沒有被吞掉。 |

| R10 | 假日仍顯示前一交易日的快照 | 對照日嚴格早於快照交易日，沒有跟自己收盤比。 |

## 10. 瀏覽器與效能驗收

在同一裝置、瀏覽器、網站版本及資料集先量基線再量修正後，記錄冷載入與暖快取各至少 10 次的中位與 P95；手機及桌面分開，不能把 Python HTTP 抽測當手機 UI 時間。

記錄：點擊→選項／載入狀態更新、點擊→前 30 列正確、點擊→全表完成、實際資源 key／次數／壓縮流量，以及有無文件導覽。必要時分清網路、解析、排序、DOM 建立與版面時間。

必過條件：

- 固定版本一般切換的文件導覽次數為 0；不重抓 HTML／JS／CSS。
- 每個同版本同 key 的重疊下載只有一個資源請求鏈（真正失敗後既有重試另計）。
- 切換時操作區與摘要不整區隱藏，沒有把舊資料標成新期間。
- 使用者輸入後立即更新狀態，目標在正常測試裝置 100 ms 內；超過時記錄原因，不假稱已達標。
- 暖記憶體命中不新增必要網路請求，不能等待市場結構或預抓才出排行；以前 30 列在 300 ms 內為優化目標，超出需提供剖析與後續判斷。
- 冷下載受網路限制，不承諾固定一秒內完成；關鍵路徑不得多等待前一日預抓、營收、分類或市場結構。下載慢時仍能看懂目前狀態並改選。
- 最終顯示選擇、對照期間、行情時間、排行與市場結構來源一致；快速連點與失敗案例零錯覆蓋。

100／300 ms 是本方案提出的驗收目標，尚未在修正後量測。若目標裝置無法達標，需附同機前後差異與瓶頸，不能事後把真實數據省略或任意放寬。
