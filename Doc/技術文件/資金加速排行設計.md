# 資金加速排行：量比、鳥量股門檻與盤中盤後架構

## 1. 本次調整記錄

本文件記錄「資金加速」排行模式從量比指標到鳥量股門檻的完整設計，涵蓋 2026-08-30 這一輪的兩項修正：

- `TradingValueRankingCalculator` 加上 `accelerationBaselineFloor`：資金加速模式下，平常一天成交值低於「全市場 20 日基準中位數 60%」的股票直接排除，不再進入候選名單（`efce8cf4`）。
- 發現靜態網站的匯出架構固定用 `RankingMode.TradingHeat` 匯出，資金加速的實際排序是由 `site.js` 在瀏覽器端重新排序完成，所以上面的 C# 門檻不會直接反映到已發佈的網站；在 `site.js` 的 `rankRows()`（盤後）補上同一套門檻邏輯（同樣是 `efce8cf4`）。
- 進一步發現盤中（`loadIntraday()`）的候選名單完全沒有套用成交門檻 `state.threshold`，鳥量股光靠成交比雜訊就可能衝進盤中排行——這正是筆記 #10「盤中排行變化異常，名次從 1900+ 跳動」的成因之一，已補上與盤後一致的門檻篩選（`ff66b99b`）。

資料流有三條獨立路徑，這是本文件要說清楚的重點：

```text
本機 Razor 開發頁：TradingValueRankingQueryService → TradingValueRankingCalculator（依實際模式計算，含鳥量股門檻）
靜態網站盤後：     StaticSiteExporter（固定用 TradingHeat 匯出全量資料）→ data/*.json → site.js rankRows()（前端依模式重新排序＋門檻）
靜態網站盤中：     Supabase intraday_latest → site.js loadIntraday()（前端計算 shareChange 並排序＋門檻）
```

三條路徑各自要維護自己的門檻邏輯，不是改一個地方就三邊同步生效，這也是筆記 #10 拖了兩輪才完整處理的原因。

## 2. 指標定義

### 2.1 量比（盤後：期間比較、單日比較）

```text
量比 = 本期日均成交值 ÷ 20 日基準中位數
```

其中「20 日基準中位數」是該股票在本期第一天之前、往回 20 個交易日的每日成交值取中位數（`TradingValueRankingCalculator.Medians`）。量比回答的是「這檔股票現在的成交值，是平常的幾倍」。

分母固定 20 個交易日，不隨使用者選的觀察期間（N 日）變動。原始碼裡的設計註解記錄了為什麼：

```text
早期資金加速的分母跟著觀察期間一起變，1 日分頁時分母只剩「前一天」，
指標退化成一階差分——實測跨日排名 Spearman 相關是負的（−0.21 ~ −0.33），
數學上保證每天大風吹。分母固定 20 日後轉為 +0.50。
60 日分母更穩（+0.65），但前十名每天只換 0.3 檔，榜單幾乎不動就失去意義；
20 日每天換約 1 檔，而且只回看一個月，不會被三個月前的舊常態綁住。
```
（`TradingValueRankingCalculator.cs:16-25`）

前期排名同樣要用「前期的量比」才能比較增減，所以資金加速模式所需的歷史天數是：

```text
requiredDays = 本期天數 + 前期天數 + 20（基準）
```

比成交熱度模式（只需要 `本期天數 + 前期天數`）多出一段 20 日基準。

### 2.2 鳥量股門檻（`accelerationBaselineFloor`）

```text
門檻 = median(全市場所有股票的 20 日基準中位數) × 0.6
```

資金加速模式下，任何一檔股票只要算得出 20 日基準（回看滿 20 天），且該基準低於門檻，就從候選名單剔除，不計入排行、也不計入 `RankedStockCount`：

```csharp
if (accelerationBaselineFloor is { } floor && baseline is { } knownBaseline && knownBaseline < floor)
{
    continue;
}
```

60% 這個係數不是隨意選的，是量出來對應「排除後段四成」個股（依使用者指示：「用 20 日平均的 60% 當門檻，排除後面 40%」）。門檻金額本身不寫死，每天依當天全市場的 20 日基準中位數重新計算，隨大盤成交量水位自動調整。

回看不滿 20 天算不出基準的股票（例如新上市）**不會**被這個門檻排除——這是「確定很小」與「量不出來」的區別，後者維持原本沉到排行最後、但仍顯示的規則，不誤殺新股。

### 2.3 盤中的成交比變化（`shareChange`）——與量比不同的指標

盤中畫面**不是**用量比排序，而是用「成交比變化」：

```text
成交比 = 個股本輪累計成交值 ÷ 全市場本輪累計成交值
成交比變化 = 今日盤中成交比 − 對照期間（前 N 日）平均成交比
```

原始碼註解說明了為什麼盤中不能沿用量比：

```text
資金加速看的是成交比變化，不是預估值：分子分母同一輪，早盤也不會失真。
```
（`site.js`，`loadIntraday()` 內）

量比的分子是「本期日均成交值」，在盤中只交易半天時必須靠 `估計值 = 累計成交值 ÷ 時段進度` 推估全天量，越早盤估計誤差越大。成交比變化把分子分母都換成「同一輪的市場佔比」，半天的佔比一樣可以跟另一段完整期間的平均佔比比較，不受盤中進度影響。

代價是這是完全不同的兩個指標，量比是「倍數」，成交比變化是「百分點差」，兩者之間沒有換算關係，鳥量股門檻的算法也不能直接套用（見第 4.4 節）。

## 3. 三條資料路徑的門檻與篩選現況

| 檢視 | 程式位置 | 排序依據 | 成交門檻 `state.threshold` | 鳥量股門檻 |
|---|---|---|---|---|
| 本機開發頁（Razor） | `TradingValueRankingCalculator.Calculate` | 量比 `VolumeRatio` | 由 `RankingQuery.MinimumAverageDailyTradingValue` 控制 | 有，`accelerationBaselineFloor` |
| 靜態網站．盤後（期間／單日） | `site.js` `rankRows()` | 量比 `row.volumeRatio` | 有 | 有，`baselineOf()` + `median()` 還原 20 日基準 |
| 靜態網站．盤中 | `site.js` `loadIntraday()` | 成交比變化 `row.shareChange` | 有（本次補上） | 無（`row.volumeRatio` 欄位在盤中資料裡不存在，無法還原基準，見 4.4） |

匯出端固定用 `RankingMode.TradingHeat`、不篩市場、不設門檻、不截斷筆數，原始碼註解說明了原因：

```text
完整名單：不篩市場、不設門檻、不截斷。模式固定成成交熱度，
因為兩種模式的差別只在排序，而排序交給前端做。
```
（`StaticSiteExporter.cs:145-146`）

也就是說 `data/*.json` 對「成交熱度」與「資金加速」兩種模式共用同一份完整資料，量比欄位（`volumeRatio`／`previousVolumeRatio`）在匯出時就已經算好、原封不動放進 JSON，差別只在瀏覽器依目前選的模式決定要用哪個欄位排序、以及是否套用鳥量股門檻。這個設計省下一半的匯出檔案數，但也代表：**C# 端 `accelerationBaselineFloor` 只對本機開發頁生效，靜態網站的門檻必須在 `site.js` 另外維護一份等價邏輯**，這正是本輪要補齊的部分。

## 4. 設計理念與取捨

### 4.1 為什麼要有鳥量股門檻

量比是一個倍數，分母（20 日基準）越小，同樣的成交值波動換算出來的倍數就越誇張。一檔平常一天成交幾十萬元的殭屍股，只要today忽然有一張大單成交到幾百萬元，量比可能瞬間衝到幾十倍甚至上百倍，直接洗到排行榜最前面，但這種波動對多數使用者沒有參考價值——不是資金真的在加速流入一檔活躍股票，只是分母太小造成的數字放大。門檻把這類「平常量不到全市場一半」的個股排除，讓資金加速排行聚焦在原本就有一定成交規模、量比放大才有意義的股票。

### 4.2 為什麼是全市場中位數的 60%，不是固定金額

固定金額（例如「日均成交值低於 500 萬排除」）在多頭、空頭、量縮量縮的市場狀態下代表的意義完全不同：大盤量縮時，500 萬可能已經是中段股票的正常水準，門檻太鬆；大盤量增時，500 萬可能只排到最末段，門檻太嚴。用「全市場中位數的比例」讓門檻隨大盤水位自動移動，60% 這個比例是回推使用者要求「排除後段四成」得到的係數，不是憑感覺訂的門檻。

### 4.3 為什麼靜態網站的匯出永遠是成交熱度模式

如果匯出時依模式分開產生兩份資料（成交熱度一份、資金加速一份），使用者切換模式時看到的候選股票、前期排名基準都可能不一致，而且匯出檔案數直接翻倍。既然資金加速跟成交熱度的差別「只在排序」（量比 vs. 成交值），匯出一份不篩選、不排序的完整資料，把排序與門檻邏輯留給前端，就能保證兩種模式看到的是同一份底層資料，只是排列順序不同。缺點是前端因此背負了跟後端同一套業務邏輯（門檻計算），這是本次踩到的坑：新增或修改門檻邏輯時，C# 與 `site.js` 兩邊都要記得改，忘記其中一邊就會出現「本機測得到、網站上看不到」的落差。

### 4.4 為什麼盤中沒有鳥量股門檻（目前的限制，非疏漏後的最終狀態）

`baselineOf(row) = row.value / row.volumeRatio` 這個還原 20 日基準的技巧，依賴匯出資料裡已經算好的 `volumeRatio` 欄位。但盤中資料來自 Supabase `intraday_latest`，經 `mapIntradayRows()` 轉換後的欄位只有 `value`、`estimate`、`priceChange`、`close`、`liveKLine`，完全沒有 `volumeRatio`，因為盤中排序用的是成交比變化而不是量比（見 2.3 節），匯出鏈路裡也就沒有計算或攜帶這個欄位的必要。

這代表現有的鳥量股門檻機制**無法原封不動套用到盤中**：要做同等保護，得另外設計一套適用於「成交比變化」這個指標的門檻（例如同樣用成交門檻擋掉小型股，但門檻的統計基礎需要是盤中的市場佔比分布，而非日成交值中位數）。本次只先補上遺漏的 `state.threshold` 篩選（見第 5 節），這是目前唯一在盤中生效的候選過濾機制。

## 5. 驗證與限制

- 盤後 `rankRows()` 門檻：以 2026-08-28 快照做 Python 獨立驗算，候選數從 1955 降到 1114，與程式碼邏輯完全一致；並透過瀏覽器 Preview 實際載入靜態網站確認排行榜結果一致。
- 盤中 `loadIntraday()` 門檻：透過瀏覽器 Preview 對正在執行的靜態網站呼叫 `loadIntraday`，確認候選數從補丁前的 1972 檔（全部股票，無門檻）降到補丁後的 476 檔（僅 `value >= state.threshold` 的股票），與獨立重算的「高於門檻股數」完全吻合；`preview_console_logs` 確認無執行期錯誤。
- **已知限制／尚未處理**：
  - 盤中目前只補了成交門檻，尚未有等同「鳥量股門檻」的保護；`shareChange` 對極小成交值股票仍可能因為分子分母都趨近 0 而產生排序雜訊，不排除筆記 #10 的部分症狀仍會出現，只是規模比補丁前（完全無門檻）小很多。
  - `site.js` 的 `MODES` 陣列（約 180-193 行）裡，資金加速的 `hint`／`singleDayHint` 說明文字仍寫著「依成交值增減率排序」「需要 3N 個交易日」，是量比指標上線前的舊文案，跟目前實際的「依量比排序」「需要 2N + 20 天」不一致，屬於待更新的顯示文案，不影響排行邏輯本身。
  - C# 端 `accelerationBaselineFloor` 與 `site.js` 端 `baselineOf`/`median` 是兩份手動同步的等價邏輯，日後調整門檻比例（目前 60%）或基準天數（目前 20 日）時，兩邊都要一併修改，否則本機開發頁與已發佈網站會出現不一致。

## 6. 結論

資金加速排行實際上是三套獨立實作：本機開發頁走 C# 全端計算，靜態網站盤後把排序與門檻邏輯搬到前端、共用一份不篩選的匯出資料，靜態網站盤中則因為早盤估計值失真的限制，改用完全不同的「成交比變化」指標，也因此暫時無法沿用同一套鳥量股門檻。三者的核心目的一致——排除因分母太小而失真的鳥量股，讓排行反映真正有意義的資金流動——但因為底層資料與指標定義不同，門檻的實作细節無法直接複製貼上，這是本文件記錄的主要理由，也是後續要補上盤中專屬門檻機制時的起點。
