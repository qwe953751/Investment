## 2. 指標定義

### 2.1 收縮量比（盤後：期間比較、單日比較；盤中：即時比較）

```text
量比 = (本期 + k) / (基準 + k)
k = ShrinkageCoefficient × 全市場基準中位數
```

- **盤後／本機開發頁**：本期＝本期日均成交值，基準＝該股票 20 日基準中位數
  （`TradingValueRankingCalculator.Medians`），全市場基準中位數＝當日所有股票
  20 日基準中位數的中位數。
- **盤中**：本期＝今日盤中市場成交比 `row.share`，基準＝對照日的市場成交比
  `past.share`，全市場基準中位數＝對照日全市場 `share` 的中位數。分子分母
  單位不同（成交值 vs. 成交比），但公式結構完全一樣——量比是尺度無關的倍數，
  換成同樣單位的分子分母公式依然成立。

`ShrinkageCoefficient`（`c = 0.25`）與「20 日基準分母固定不隨觀察期間變動」是
兩個獨立的設計決策，後者原始碼裡的設計註解記錄了為什麼：

```text
早期資金加速的分母跟著觀察期間一起變，1 日分頁時分母只剩「前一天」，
指標退化成一階差分——實測跨日排名 Spearman 相關是負的（−0.21 ~ −0.33），
數學上保證每天大風吹。分母固定 20 日後轉為 +0.50。
60 日分母更穩（+0.65），但前十名每天只換 0.3 檔，榜單幾乎不動就失去意義；
20 日每天換約 1 檔，而且只回看一個月，不會被三個月前的舊常態綁住。
```
（`TradingValueRankingCalculator.cs:16-25`）

前期排名同樣要用「前期的量比」才能比較增減，所以資金加速模式所需的歷史天數是：

```text
requiredDays = 本期天數 + 前期天數 + 20（基準）
```

比成交熱度模式（只需要 `本期天數 + 前期天數`）多出一段 20 日基準。

### 2.2 為什麼分母要收縮（`k`）

量比是一個倍數，分母（基準）越小，同樣的成交值波動換算出來的倍數就越誇張。
一檔平常一天成交幾十萬元的殭屍股，只要今天忽然有一張大單成交到幾百萬元，未收縮的
量比可能瞬間衝到幾十倍甚至上百倍，直接洗到排行榜最前面，但這種波動對多數使用者
沒有參考價值。`AccelerationRules.ShrunkRatio` 用 `k = c × 全市場基準中位數` 當
「虛擬底量」加進分子分母：

```csharp
public static decimal? ShrunkRatio(decimal current, decimal? baseline, decimal? marketMedianBaseline)
{
    if (marketMedianBaseline is not > 0m)
    {
        return null;
    }

    var k = ShrinkageCoefficient * marketMedianBaseline.Value;
    var denominator = (baseline ?? 0m) + k;

    return denominator > 0m ? (current + k) / denominator : null;
}
```

大型股 `k ≪ 基準`，`(cur+k)/(base+k) ≈ cur/base`，倍數幾乎不受影響；
迷你股 `k ≫ 基準`，倍數被壓回 `1` 附近，這是**非對稱阻尼**，不是把冷門股踢出候選
——踢出候選是另一件事（見 2.3 節的當期流動性門檻），兩者一起做才不會互相取代：
單獨收縮，殭屍股仍會擠進候選名單只是倍數不再誇張；單獨設門檻，「平常沒量、今天
爆量」的訊號會被誤殺（因為門檻篩的是「過去」）。

**基準未知時當作零計算，不是回傳 null**：新上市、長期停牌等回看不到基準的股票，
`baseline` 傳 `null`，分母直接退化成 `k`，算出一個被 `k` 收縮過、但仍然是有限值的
量比，而不是直接判定「算不出來」。這樣「平常沒量、今天爆量」的個股才留得在榜上
——這正是資金加速要抓的訊號，不該因為「過去沒有基準」就被規則本身濾掉。只有當
**全市場的基準中位數本身**不是正數（極端邊界：全市場都算不出基準）才回傳 `null`，
避免除以零。

### 2.3 當期流動性門檻

```text
門檻 = median(全市場所有股票的「當期」成交值) × CurrentLiquidityFloorRatio(0.6)
```

資金加速模式下，任何一檔股票只要**當期**成交值低於門檻，就從候選名單剔除，不計入
排行、也不計入候選數：

```csharp
if (currentLiquidityFloor is { } floor && stats.AverageDailyTradingValue < floor)
{
    continue;
}
```

跟第一輪（2026-08-30）的差別只有一個字，但語意完全相反：舊規則篩的是「過去」
（`baseline < floor`），新規則篩的是「當期」（`current < floor`）。舊規則會誤殺
「平常沒量、今天爆量」的股票——那正好是資金加速要抓的訊號，也是榜單退化成
成交熱度的第二個原因（第一個原因是 2.2 節說的排序鍵本身沒有收縮）。

60% 這個係數不是隨意選的，沿用第一輪「用 20 日平均的 60% 當門檻，排除後面 40%」
的使用者指示，只是統計基礎從「過去基準」換成「當期成交值」。門檻金額本身不寫死，
每天依當天全市場的當期成交值中位數重新計算。

### 2.4 排名變化上界（`rankChange` 顯示上界）

資金加速的候選有上千檔，`rankChange = 前期排名 − 本期排名` 這個差值在候選集合尾端
基本上是隨機數（例如從第 1850 名跳到第 12 名，數字很大但沒有訊號價值）。
`AccelerationRules.MaxPreviousRankForDisplay = 200`：前期排名超過 200 名的股票，
`rankChange` 一律顯示「—」，不是顯示一個真實但無意義的數字。這個上界只在資金加速
模式生效，成交熱度模式不受影響（候選數天生就受 `state.threshold` 限制，尾端沒有
同樣的雜訊問題）。

## 4. 設計理念與取捨

### 4.1 為什麼盤中原本的「成交比變化」會退化成成交熱度

盤中原本的排序鍵是 `shareChange = row.share − past.share`（絕對百分點差）。
`share` 本身跟成交值等比例，同樣的資金流入，大型股的 `share` 變動天生就比小型股
大一個數量級（台積電的成交比可以動 ±2pp，小型股只動 ±0.01pp）。用絕對差排序，
數學上幾乎等價於直接用成交值排序——這就是使用者回饋「跟成交熱度結果差不多」的
根本原因，而不是門檻沒設好。實測用正式資料庫 6 個交易日、1,152 檔（當日成交值
≥ 1,000 萬）驗證，跟「成交熱度」前 20 名的重疊度：

| 排序方式 | 與成交熱度前 20 重疊 |
|---|---|
| 絕對 `shareChange`（原盤中做法） | 12 / 20 |
| 相對量比 `today/ref`（原盤後做法，未收縮） | 0 / 20 |
| 相對量比＋收縮分母（本輪做法） | 0 / 20 |

但**單純換成未收縮的相對量比會把最原始的症狀叫回來**：實測未收縮量比前 20 名
幾乎都是冷門股（迷你分母把倍數炸開）。所以「換成倍數」跟「收縮分母」兩件事要一起做，
單做其中一項都會倒向另一個極端——這也是為什麼 2.2／2.3 節的兩條規則缺一不可。

### 4.2 為什麼收縮係數是 0.25，不是憑感覺挑的

`k = c × 全市場基準中位數`，`c` 用 286 個交易日、約 55 萬列的正式歷史資料回測，
掃過 `c ∈ {0.25, 0.5, 1.0}` 三個候選值，對照下面三條合格線：

| 檢驗項目 | 合格線 | `c = 0.25` 實測 |
|---|---|---|
| 與成交熱度前 20 名重疊度 | ≤ 3/20 | 均值 0.71/20，遠低於現行（收縮前）12/20 |
| 前 20 名當日成交值 ≥ 全市場中位數 60% | 全數通過 | 20/20 |
| 相鄰交易日前 20 名留存率 | 40–70%（太高＝榜單不動，太低＝又在大風吹） | 均值 0.43，落在目標帶內 |

三條線同時通過，確定 `c = 0.25`。

### 4.3 為什麼靜態網站的匯出永遠是成交熱度模式

如果匯出時依模式分開產生兩份資料（成交熱度一份、資金加速一份），使用者切換模式時看到的候選股票、前期排名基準都可能不一致，而且匯出檔案數直接翻倍。既然資金加速跟成交熱度的差別「只在排序」（量比 vs. 成交值），匯出一份不篩選、不排序的完整資料，把排序與門檻邏輯留給前端，就能保證兩種模式看到的是同一份底層資料，只是排列順序不同。缺點是前端因此背負了跟後端同一套業務邏輯（門檻計算），這是持續要注意的坑：新增或修改門檻邏輯時，C# 與 `site.js` 兩邊都要記得改，忘記其中一邊就會出現「本機測得到、網站上看不到」的落差——這也是這一輪把係數收斂進 manifest 的動機：手動同步兩份常數容易漏改，讀同一份 manifest 就不會有兩邊不一致的問題。

### 4.4 盤中現在有完整的當期流動性門檻了（取代原本的已知限制）

第一輪文件在這裡記錄的是「盤中沒有鳥量股門檻，因為匯出資料沒有 `volumeRatio`
欄位可以還原基準」。這個限制在 2026-09-05 這一輪解除了，原因是門檻的統計基礎
從「還原 20 日基準」換成「當期成交值」——`row.value`（今日累計成交值）本來就是
盤中資料原生就有的欄位，不需要靠 `volumeRatio` 反推任何東西。`loadIntraday()`
現在跟 `rankRows()` 共用同一個 `currentLiquidityFloor(values)` 函式：

```js
function currentLiquidityFloor(values) {
    if (!accelerationCoefficients) {
        return null;
    }

    const sorted = values.filter(value => !missing(value)).sort((a, b) => a - b);
    return sorted.length === 0 ? null : median(sorted) * accelerationCoefficients.currentLiquidityFloorRatio;
}
```

盤中的量比計算則需要 `share` 尺度的「全市場基準中位數」，用對照日
（`referenceByTicker`）的 `share` 分布現算：

```js
const marketMedianShare = median([...referenceByTicker.values()]
    .map(pastRow => pastRow.share)
    .filter(value => !missing(value))
    .sort((a, b) => a - b));
```

`pastSortKey`（前期排名依據）則直接借用對照日匯出資料裡**已經算好**的
`volumeRatio` 欄位，不必在前端重算一次「比例的比例」——這是因為對照日的
`volumeRatio` 本來就是伺服器端 `AccelerationRules.ShrunkRatio` 算出來的正確值
（見第 3 節「關鍵事實」），可以直接複用。

## 6. 結論

資金加速排行實際上是三套獨立實作：本機開發頁走 C# 全端計算，靜態網站盤後把排序
與門檻邏輯搬到前端、共用一份不篩選的匯出資料，靜態網站盤中則因為分子分母尺度
不同（成交比 vs. 成交值）需要前端另外現算量比。三者在 2026-09-05 這一輪收斂到
同一套核心規則——收縮量比 `(cur+k)/(base+k)` 排序、當期流動性門檻、rankChange
顯示上界——唯一的定義處是 C# 的 `AccelerationRules`，係數透過 manifest 推到前端，
`site.js` 兩處呼叫共用同一組輔助函式。跟第一輪比較，這次修正的不只是「補一個門檻」，
而是先確認排序鍵本身在數學上有沒有鑑別度，再讓門檻與收縮兩件事一起生效——這是
第一輪「修法打錯位置、症狀還在」的教訓。
