## 3. 唯一計算契約

### 3.1 日期窗口與 N 的作用

D 是實際選取的交易日；盤中 D 必須來自已接受快照的 tradeDate，不取電腦今天日期。N 是觀察期間，交易日依有效行情日曆，不以日曆日或空的假日匯入檔計數。

| 檢視 | 本期 | 前期 | 資金加速本期基準 |
|---|---|---|---|
| 盤後區間 | 結束於 D 的 N 日 | 本期之前的 N 日 | 本期開始前的 20 個交易日 |
| 盤後單日 | D 一日 | D 之前的 N 日 | D 之前的 20 個交易日 |
| 盤中 | D 的同輪累計成交額 | D 之前的 N 日 | D 之前的 20 個交易日 |

前期資金加速使用「前期日均額」與「前期開始前 20 日基準」，不得把本期基準拿去算前期。

以 D=10/16、N=60 為例：區間本期 7/22～10/16、前期 4/24～7/21；單日與盤中的比較期為 7/21～10/15。只在基準真正滿 20 日時建立該段全市場中位數；個股缺基準與整個市場歷史不足必須分開。

固定 D、來源輪次、市場與門檻時：

- 盤中／盤後單日成交熱度，本期值與原榜名次不隨 N 改變；比較值、成交比變化與前期排名可以改變。
- 盤後單日／修正後盤中資金加速，本期量比與本期原榜名次不隨 N 改變；前期比較與名次變化可以改變。歷史不足導致比較不可用，不得順便改掉已可計算的本期。
- 盤後區間兩模式，本期窗口隨 N 改變，名單與名次可以改變。
- 依比較欄位重排前 100 後，列順序可能隨 N 改變，這符合設計。

### 3.2 成交熱度與市場分母

- 日均成交值＝窗口內成交值總和 ÷ 窗口市場交易日數；個股缺一日資料，不縮短分母。
- 市場成交比＝個股窗口總額 ÷ 同窗口全市場總額。
- 成交比變化＝本期成交比－前期成交比，單位為百分點。
- 全市場為上市、上櫃、興櫃普通股，不含 ETF、TDR；不隨畫面篩選或成交門檻縮小。
- 前期為零時的增減率、前期無有效成交值時的名次比較，保留既有空值規則。

### 3.3 資金加速

~~~text
本期量比 = (本期日均成交值 + k) / (本期前20日個股成交值中位數 + k)
k = 0.25 × 上市櫃普通股「正值個股20日基準」的中位數
當期流動性門檻 = 0.6 × 上市櫃普通股當期成交值中位數
~~~

興櫃參與排行，使用同一組 k 與絕對門檻，但不參與兩項市場校準。保留現有 C# Medians 的缺日補 0、正值基準篩選、個股基準為 null 時按 0 收縮、全市場基準不可建立才回傳 null 的規則，不自行改係數。

盤中本期使用現有 raw 的累計 turnover，與成交熱度目前使用的值相同；**不改成全日預估額、不引入新的曲線校正**。這是「累計成交額相對完整交易日常態」的量比，盤中未走完全日時可以低於收盤後的量比；本輪不保證不同時間或不同來源的數值相等。提示應如實描述。

公式與窗口實作集中於 C# 計算服務。前端消費計算值、篩選、排序、編號與格式化，不再另外維護 share 版資金加速公式。不能只把 N 改成 20，也不能用 20 日平均成交比冒充 20 日成交額中位數。

### 3.4 歷史身分與可追溯性

選定方案：**排行列名稱、市場、種類及市場篩選，以不晚於 D 的最後有效官方身分為準；多日區間也以 D 的身分歸類整列，不拆成多列。** 同次查詢的校準集合依這份 D 身分決定，不讀 D 之後的名單。

成交額歷史保留每日原始行情的市場與種類證據，只把當時普通股行情納入普通股計算；不得因為某股票後來轉板、更名或改種類，就改寫先前每日行情的資格。缺某日行情可沿用此前已知身分，不能從未來倒填。第一次出現晚於 D 的標的，不得出現在 D 的集合中。

選 D 後改 N，市場身分不變。D 日盤中已確認的官方身分可供 D 日計算，不反向覆蓋 D 以前的歷史結果。新增未來行情後重算舊 D，結果應保持相同（正式修正舊原始資料另須有來源紀錄）。

同一 ticker、同日若出現互相矛盾的市場／種類，保留證據並讓匯出驗證指出衝突，不能以最後一筆覆蓋。不要把「當日沒有報價」直接判為下市。

### 4.2 自動重試政策

重試由資源工作統一管理，不是每列、每次 render、每個輪詢事件各開一個 timer。

- 重試 key 至少含網站版本、計算規則版本、D、N、對照日期與資源種類；涉及快照計算結果時另含實際 run／raw revision。
- 現有 fetchPeriod 的下載中 Promise 合併、成功 LRU 與「失敗不快取 null」必須保留。整個 key 同時最多一個請求與一個待執行 timer。
- 一次資源讀取失敗後，建議退避為 1、3、10、30 秒，再每 60 秒一次，加入小幅抖動；延遲從前次嘗試結束後起算。既有 fetchJson 的內層重試仍算同一次資源工作，禁止兩層重試同時放大請求。
- 頁面離開目標檢視、N／D／模式／來源／網站版本改變後，取消舊排程與提交資格。已被其他前景共用的下載可完成快取，不強行中斷。
- 離線或分頁隱藏時暫停 timer；online／回前景時合併成一次立即補齊，不把錯過的 timer 全數補跑。
- 成功即停止該 key 重試。真的歷史不足不是下載錯誤，不每分鐘重抓同一份不會變的檔；新交易日、資料版本或新的可用快照再觸發。
- 逾時、網路錯誤、HTTP 5xx／429、必要資源 404、空檔或格式不符，不能永久負快取。針對 404／格式錯誤採上述有上限的頻率，內部記原因，不在畫面要求使用者處理。
- 不為了重試繞去逐股查資料庫，不增加無上限快取、全期間預抓或跨分頁廣播風暴。

### 4.3 舊回應防護

沿用筆記 #89 的不可變選擇、意圖世代、工作 ID、raw revision、已提交畫面身分。每個 await、timer、finally 與局部補齊前重新驗證。

背景補齊必須有自己的工作身分與生命週期；每次重試建立綁定目前意圖／來源的補齊工作，不重用已結束前景工作的 active 判定。前景完成後不能因此讓所有補齊永遠失去提交資格；背景工作也不能重新打開前景 busy、清掉新畫面的狀態或使另一個前景工作失效。

若等比較時 raw 已前進，舊快照結果不得提交；應將已下載的「不含快照」歷史比較資源套給最新工作重新計算，或等待最新快照的 C# 計算欄位，不能混合兩輪結果。必須安排最新工作，避免只丟棄舊工作卻永遠不補齊。A→B→A 不能讓第一個 A 復活。

這個「先完成」定案限於今日熱度已有有效 raw 的情況。資金加速若缺必要計算基準，不得以成交熱度順序冒充：有同一有效來源的本期資金加速可先顯示、比較待補；連本期資金加速也無法建立時，沿用正確上下文的最後可用畫面或一般準備狀態，系統自行重試，不新增手動排錯流程。

## 6. 工項 C：排序精度由 C# 保留

選定方案：**保留畫面量比既有顯示精度，另外輸出本期／前期的資金加速排序序位。** 序位在 C# decimal 的原始分數上建立，空值最後，真正同分按 ticker 的 Ordinal 升冪；使用連續且唯一的整數，不把四捨五入後的同分當成真正同分。

序位代表全量資料的相對先後，不是前端最終名次。前端仍先按目前市場、成交門檻與當期流動性門檻選候選，再按序位排序，最後重編模式名次；同一候選集合以「前期序位」重排，算出前期名次與排名變化。不能直接拿全市場序位相減。

修改位置：

- C# 計算／投影服務：產生全量本期及前期序位，保留量比 null／可比較的判定資訊。
- StaticSiteExporter 的 RowExport、SingleComparisonRowExport、ToExport、ToSingleComparisonExport：增加機器用序位欄位及規則版本。一般 N-D 檔與 single-N-D 檔都要有，不可只修其中一種。當期流動性門檻亦由 C# 以未取整的當期值算好輸出到結果頂層，前端只套門檻，不再依匯出取整後的值重建中位數。
- site.js rankRows：資金加速的本期／前期改讀對應序位；applySingleDayComparison 必須合併前期序位。本期單日序位沿用 1-D 的同日資料，不被 N 日比較檔覆蓋。
- sortedRows 的表頭量比排序也應尊重原始量比順序，仍只排原榜前 100。不能模式排名修好，點量比表頭又按四位小數排回錯序。
- 鎖定榜外 rankByTicker、200 名上界、空值最後與同分 tie-break 一併驗證。

不要只把四位改成八位就宣稱完全解決；C# decimal 與 JavaScript Number 精度仍可能不同。序位欄缺失不得在新規則版本下悄悄回退四位量比排序。新舊版本的相容處理須有明確規則與驗證，不混用兩版資料。

固定樣本：2026/10/16、10 日區間、上櫃、5 億門檻，8299 的原始量比 0.925414158… 應排在 7717 的 0.925374182… 之前，即使兩者顯示同為 0.9254。

### 7.2 服務與資料流

1. 將 TradingValueRankingCalculator 內需要共用的窗口、Aggregate／Medians、校準、收縮量比計算，整理成可由盤後與盤中共同呼叫的 C# 服務。不要只複製一份同名公式；保留既有 public API 與已驗證正常行為。
2. 新增 IntradayRankingProjection（名稱可調整），接收已接受的完整 IntradaySnapshot、capturedAt 與 D 之前的官方歷史。以盤中同輪累計額作為 D 的本期；不得同時混入已存在的 D 日收盤額。
3. 按第 3 節算出全量普通股的本期量比、當期流動性門檻、當期成交比，以及 1／5／10／20／60 日各自的前期值、成交比、前期量比與排序序位。今日熱度所需的無歷史數值可獨立完成，不被歷史準備失敗一起丟掉。
4. 歷史基準、N 日比較與身分索引可依「歷史來源版本＋D＋規則版本＋當日有效身分」預先準備；每輪只代入最新本期值。不得每兩分鐘為每檔股票各自重新下載歷史或反覆向資料庫查詢。
5. Program.cs 的現有 ToMarketHeatHistory 回傳 Stocks=[]，不能直接拿來當作完整排行資料集。應共用有歷史身分的 builder，仍從 data/imports 取得權威歷史，不額外依賴即時外部權息 API 才能算成交額量比。
6. 比較期的前期量比應經共享服務建立。舊 reference.volumeRatio 的窗口在一般情況可能與單日前期相同，不能只憑欄位名稱斷言一定錯；但它的身分／校準截止日可能是 D-1，必須驗證與本次 D 契約一致，尤其轉板日。最終以 D 查詢的 C# 結果為準。

### 7.3 快照契約與相容性

優先在既有不可變 raw 快照中增加可選的 ranking 區塊，不另開公開資料庫查詢路徑。下面是語意要求，欄位實際命名依目前 DTO 整合：

| 內容 | 必要資訊 |
|---|---|
| 身分 | schemaVersion、rankingRulesVersion、tradeDate、capturedAt、發布後 runId；與 raw 同輪 |
| 歷史證據 | 歷史截止日／來源版本、所用 20 日範圍、各 N 的實際起訖日與完整性 |
| 本期 | 各股 value、share、volumeRatio、資金加速排序序位；全市場本期流動性門檻 |
| 各 N 比較 | 各股 previousValue、previousShare、shareChange、previousVolumeRatio、前期排序序位、可比較狀態 |

1. 不刪改既有 raw 欄位；舊前端可以忽略新增區塊。新前端先驗規則版本、日期、run、筆數／ticker 連結與必要欄位，再使用。
2. IntradaySnapshotPublisher 既有「先完整檔、再 latest、不可變路徑、hash 校驗」保留。增加的計算資料必須在同一序列化結果內，不能從另一輪拼上來。
3. 前端 applyIntradaySnapshot、CDN 正規化、兄弟分頁廣播及快照快取都要完整保留／驗證新區塊，不能只有網路第一個接收入口看得到。
4. site.js loadIntradayResult 改消費 C# 欄位，不再呼叫 share 版 shrunkVolumeRatio。流動性門檻優先使用 C# 算好的值，不以篩選後名單重算。若現有基本熱度欄位仍由舊 adapter 準備，應一併接到同一 C# 投影，避免新增公式分支。
5. 新快照已附所選 N 的完整比較時，換 N 就地切換資料，**不再額外下載沒有用途的 N 日檔**。工項 A 的自動補齊仍適用於需要下載的比較資源與新計算區塊尚未到位時。
6. 若歷史／投影準備失敗，不阻斷現有 raw 報價保存與發布。無歷史的本期熱度欄仍可用，內部比較標為 pending 或 insufficient；下一輪在來源恢復後由 C# 自動補算。
7. 不可變快照不能在原路徑覆寫補欄位。瀏覽器遇舊版／不完整計算區塊，應按工項 A 的退避重新檢查 latest，等新有效快照；不要永遠重抓同一個不會改變的檔案。
8. 目前直接 DB 備援沒有這些新計算欄位，**本輪不新增 DB migration**。備援可維持 raw 熱度；沒有同輪 C# 分數時不可恢復舊 JS 資金加速公式。用正確上下文的最後可用資金加速或一般準備狀態、自動恢復即可；驗收報告必須記錄此限制，不能宣稱 DB 備援已提供完整新資金加速。
9. 計算例外獨立捕捉並留下去機密的原因；不要為提高可用性傳假值。日初準備與每輪代入都要量測，不能破壞兩分鐘收集節奏。若同步投影量測不能達標，先共用索引／快取；仍不達標時才在同一進程內用有界工作處理，且保留 run 綁定與上述契約，不新增外部常駐服務。

新增的是公開行情計算欄位，不能包含筆記、資產、帳號、token 或 Storage secret。沿用既有 Storage 權限與上傳方法，不為本工項擴大匿名寫入權限。
