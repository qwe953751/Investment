## 1. 事實查核（已驗證，不必重查）

### 1.1 日股停在 09/18 —— 正確行為，不是 bug

JPX 2026 年 9 月連休五天：

| 日期 | 原因 |
|---|---|
| 09/19 六、09/20 日 | 週末 |
| 09/21 一 | 敬老の日 |
| 09/22 二 | 国民の休日（夾在兩個國定假日中間自動放假） |
| 09/23 三 | 秋分の日 |

`MarketHolidayCalendar.cs:22-23` 已正確登錄 `jp` 的 09/21、09/22、09/23。
Workflow log 也印出「成交排行 jp 略過：09/23/2026 是交易所休市日（國定假日／市場假日）」。

**結論**：資料端完全正確，缺的是「畫面沒告訴使用者為什麼停住」→ 工項 D。

### 1.2 韓股成交排行停在 09/21 —— 真缺陷

`imports-turnover/kr/` 最後一筆是 `2026-09-21.json`，09/22、09/23 都沒生出來。
盤後（`asia-market-overview-daily`）與盤中（`asia-market-overview-intraday`）兩條管線
每一輪都拋同一個例外：

```
Invest.Web.Infrastructure.MarketData.Turnover.MarketTurnoverDataIncompleteException:
Yahoo screener kr 來源日期為 2026-09-18, 2026-09-23, 2026-09-16, 2026-09-22, 2026-09-17，
不是要求的交易日 2026-09-23；拒絕發布舊排行。
  at YahooScreenerMarketTurnoverClient.EnsureSourceDateMatches(...) line 417
```

09/22 是一模一樣的錯（來源日期 2026-09-22, 09-18, 09-16, 09-21, 09-17）。

**根因**：`EnsureSourceDateMatches`（`YahooScreenerMarketTurnoverClient.cs:405-420`）要求候選池裡
**每一檔**的 `regularMarketTime` 都等於目標交易日。Yahoo screener 的候選池會混進當天沒有成交的
冷門股，它們的時間戳停在上一次成交日。只要有一檔落後，整批 400+ 檔就被丟掉。
這是「全有全無」的檢查，對這個資料源必然失敗。

**這道檢查是新的**：`6764492de fix: guard non-TW market snapshots by trading dates`
（2026-09-22 16:01）同時加入休市日閘門與這道來源日期檢查。上線後韓股每一輪都失敗；
日股因為 09/21～09/23 連休被跳過，**到 2026-09-24 為止還沒有在真正的交易日跑過這道檢查**。
兩個市場共用同一支 client 與同一段邏輯，日股預期會出現相同失敗。

前端靠 `MarketTurnoverProjection.cs:17` 的 `ToleranceDays = 5` 容忍窗退回顯示 09/21。
韓股下一個交易日是 09/28（09/24～09/25 中秋休市、09/26～09/27 週末），
屆時容忍窗變成 09/23～09/28，09/21 落在窗外，**成交排行會整個變空白**。

## 2. 工項

### 工項 A（P0）：排行來源日期檢查改成「過濾 + 門檻」

**檔案**：`src/Invest.Web/Infrastructure/MarketData/Turnover/YahooScreenerMarketTurnoverClient.cs`

**現況**（`GetAsync`，約 line 55-60）：

```csharp
EnsureSourceDateMatches(normalizedMarket, tradingDate, byVolume.Concat(byPrice));
var ranked = RankPool(normalizedMarket, byVolume, byPrice);
```

**改成**：先把時間戳不是目標交易日的個股從排名候選中剔除，再用「剩下多少」判斷這一輪
是不是真的抓到了正確的一天。

#### A-1 新增過濾

```csharp
internal static IReadOnlyList<ScreenerQuote> FilterToTradingDate(
    IReadOnlyList<ScreenerQuote> quotes, DateOnly tradingDate)
    => quotes.Where(quote => quote.SourceTradeDate is null || quote.SourceTradeDate == tradingDate).ToArray();
```

`SourceTradeDate is null` 必須放行：舊版 Yahoo 回應沒有 `regularMarketTime` 欄位，
現有註解（line 51-54）明確說這種情況要保留相容性、由休市日閘門當第一層防線。

`SourceTradeDate` 的來源是 `regularMarketTime` 經 `ToMarketDate(market, unixSeconds)`
轉成**市場當地日期**（line 368-370），跟 `MarketTurnoverCollector.ToMarketDate`（line 76-86）
同一套時區基準，兩者可以直接比較，**不要再自己做時區換算**。

#### A-2 用 `EnsureFreshCoverage` 取代 `EnsureSourceDateMatches`

刪掉 `EnsureSourceDateMatches`，改成：

```csharp
/// <summary>候選池中「時間戳確實是目標交易日」的比例門檻。低於這個值代表整批抓到了別的一天。</summary>
internal const decimal MinimumFreshRatio = 0.5m;

internal static void EnsureFreshCoverage(
    string market,
    DateOnly tradingDate,
    IReadOnlyList<ScreenerQuote> byVolume,
    IReadOnlyList<ScreenerQuote> byPrice,
    IReadOnlyList<ScreenerQuote> freshByVolume,
    IReadOnlyList<ScreenerQuote> freshByPrice)
```

判定規則（任一條不成立就丟 `MarketTurnoverDataIncompleteException`）：

| # | 規則 | 用意 |
|---|---|---|
| 1 | `freshByVolume.Count >= RequiredRowCount` 且 `freshByPrice.Count >= RequiredRowCount` | 兩軸都要有足夠的當日資料才排得出前 20 |
| 2 | 聯集後 `fresh / total >= MinimumFreshRatio` | 整批都是舊的 → 今天根本沒開盤或抓早了，必須拒絕 |

例外訊息要同時帶出「新鮮/總數」與被剔除的日期分布，例如：

```
Yahoo screener kr 2026-09-23 候選池 412 檔中只有 137 檔是當日資料（門檻 50%）；
落後日期分布：2026-09-22 ×180、2026-09-18 ×61、2026-09-17 ×34；不發布排行。
```

**為什麼是 50%**：這個門檻要擋的是「整批抓到別的一天」（休市日、盤前搶跑），不是
「有幾檔冷門股沒成交」。韓股 09/23 實際新鮮比例遠低於 100% 但顯然是有開盤的，
真正抓錯天的情況新鮮比例會趨近 0。門檻抽成 `internal const` 方便測試與日後調整。

#### A-3 `RankPool` 要同時吃「過濾後」與「原始」兩組池

**這是本工項最容易做錯的地方。**

`RankPool`（line 76-131）做兩件事：排名、涵蓋證明。

- **排名**（`pool` 聯集 → `OrderByDescending(Turnover)` → `Take(20)`）→ 用**過濾後**的池。
- **涵蓋證明**（`minVolumeInPool = byVolume.Min(Volume)`、`minPriceInPool = byPrice.Min(Price)`）
  → 必須用**原始未過濾**的池。

理由：涵蓋證明的命題是「任何**沒有被 screener 頁面回傳**的個股，成交量必然 ≤ 量軸池的最小量、
股價必然 ≤ 價軸池的最小價」。這個上界是相對於「Yahoo 實際回傳了什麼」成立的，
過濾只是我們自己不採用某些列，並不改變 Yahoo 回傳的範圍。用過濾後的最小值會把 bound 抬高，
產生假失敗。

簽章改成：

```csharp
internal static IReadOnlyList<MarketTurnoverRow> RankPool(
    string market,
    IReadOnlyList<ScreenerQuote> rankByVolume,   // 過濾後，用來排名
    IReadOnlyList<ScreenerQuote> rankByPrice,    // 過濾後，用來排名
    IReadOnlyList<ScreenerQuote> boundByVolume,  // 原始，用來算涵蓋證明下界
    IReadOnlyList<ScreenerQuote> boundByPrice)   // 原始，用來算涵蓋證明下界
```

並在方法的 XML 註解裡寫清楚上面那段理由，避免日後有人「順手」統一成同一組參數。

#### A-4 已知殘留風險（寫進註解，不要在本次處理）

時間戳落後的冷門股仍然**佔用了 screener 頁面的名額**，理論上可能把一檔當日真的有量的個股
擠出候選池。目前 `VolumePages`／`PricePages` 設定的餘裕加上涵蓋證明會擋下這種情況
（bound >= cutoff 就會拋例外）。若日後涵蓋證明開始頻繁失敗，解法是調大
`VolumePages`／`PricePages`，不是放寬涵蓋證明。

#### A-5 測試

`tests/Invest.Web.Tests/YahooScreenerMarketTurnoverClientTests.cs` 既有的
`EnsureSourceDateMatches` 相關案例要改寫，並新增：

| 測試 | 期望 |
|---|---|
| 候選池 100% 當日 | 通過，排名與現行行為一致 |
| 候選池 70% 當日、30% 落後數天（重現 kr 09/23） | **通過**，落後的個股不出現在前 20 |
| 候選池 100% 落後（重現休市日抓到舊資料） | 拋 `MarketTurnoverDataIncompleteException` |
| 候選池 30% 當日（低於 50% 門檻） | 拋例外 |
| 過濾後某一軸不足 20 檔 | 拋例外 |
| 全部 `SourceTradeDate` 為 null（舊版回應） | 通過，維持相容 |
| 涵蓋證明用原始池最小值 | 構造一個「過濾後最小值會讓 bound >= cutoff、原始最小值不會」的案例，斷言通過 |

**驗收**：改完直接手動觸發 `asia-market-overview-daily`（`workflow_dispatch`，
`skip-wait=true`），在日股／韓股都是交易日的當天跑，log 要出現
「成交排行 jp 已完成 20 列」與「成交排行 kr 已完成 20 列」，
且 `data/imports-turnover/{jp,kr}/{當日}.json` 產生。

### 工項 B（P1）：日韓盤後跑完自己觸發發布

**問題**：`asia-market-overview-daily` 只 commit 到 `data` 分支，日韓資料要等
`daily-snapshot` 的 export 才會上站。兩條流程的時間相依沒有被明確保證——
`daily-snapshot` 在 run 開頭 checkout `data`，若它比日韓那條早開跑，export 讀到的就是舊快取。
09/23 是靠執行順序剛好對才沒出事。

**做法**：在 `.github/workflows/asia-market-overview-daily.yml` 的「保存日韓市場總覽快取」
步驟成功且**確實有新 commit** 之後，加一步：

```yaml
- name: 觸發網站重新發布
  if: steps.save.outputs.committed == 'true'
  env:
    GH_TOKEN: ${{ github.token }}
  run: |
    gh api --method POST "repos/$GITHUB_REPOSITORY/actions/workflows/daily-snapshot.yml/dispatches" \
        -f ref=main \
        -f 'inputs[publish-only]=true'
```

需要同時：
- 保存步驟加 `id: save`，並在「有 commit」與「沒有新資料」兩條分支各自 `echo "committed=..." >> "$GITHUB_OUTPUT"`。
- workflow 的 `permissions` 從 `contents: write` 增加 `actions: write`。

**注意**：一定要用 `publish-only=true`。完整流程會改 `data`、Supabase 與備份，
且 `daily-snapshot` 內有「擋下盤中啟動的完整流程」的守門（line 215-225），
非 publish-only 的 dispatch 會被擋掉。`publish-only` 走獨立的 concurrency group
（`daily-snapshot-publish`），不會跟完整流程互卡。

**驗收**：日韓盤後 commit 後 5 分鐘內，`daily-snapshot`（publish-only）自動出現一筆 run，
線上 `market-overview.json` 的 jp／kr `asOf` 更新到當日。
