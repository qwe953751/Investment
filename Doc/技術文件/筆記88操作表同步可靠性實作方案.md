## 3. 範圍、保留行為與方案取捨

本次必要工作：前端保存序列、同步結果與畫面讀取分離、匯入原子提交、後端版本衝突保護、操作追蹤與寫入結果不確定時的對帳、必要的測試與文件。

必須保留：

1. Google Sheet 是人工資料主檔；Supabase 是鏡像、版本與草稿。
2. 族群身份依 UUID metadata，不依名稱；兩個「導線架」必須保持不同身份。
3. 只有 E:AZ 的 48 個族群欄會做整欄移動；網站固定欄位的相對位置按既有規則保留。
4. B:C、族群勾選及標的增刪仍依既有草稿／匯出規則；第 4 列模板、尾列刪除守衛及 compaction marker 保留。
5. D 欄營收創高維持既有 V／X／- 規則，不匯入、不納入人工資料 hash；D 差異仍是警告，不擅自改成整筆失敗。
6. A 欄、統計公式、標題、格式、checkbox 驗證、凍結列及其他分頁的保護不放寬。
7. 管理者確認後才可用 Google 覆蓋草稿；cron 遇草稿不覆蓋。
8. 不影響行情、排行公式、OCR、資產持倉資料或其他市場。

替代方案比較：

| 方案 | 評估 |
|---|---|
| 只加等待時間／debounce | 只能降低同時請求機率，不能阻止舊請求晚提交，也不能處理多分頁 |
| 只做前端 Promise queue | 可修同一頁的 R1，但跨分頁、cron、匯入部分完成及回應遺失仍未處理 |
| 本方案：前端序列＋資料庫版本／交易＋小型操作紀錄 | 涵蓋已重現問題與既有同步流程的失敗邊界；保留原本單一批次 Google 寫入 |

不承諾跨 Google 與 PostgreSQL 的分散式原子交易。兩個系統之間以操作紀錄、同批 Google 標記及回讀對帳銜接；不確定時停止後續寫入。

## 5. 一致性與版本契約

新增獨立的 `settings_revision bigint not null default 0`，放在 `asset_operation_settings`；目前的 `sync_state.version` 繼續代表資料／草稿版本。兩者不可混用。

- 排序保存只改設定及 settings revision；實際順序未變時可回傳原 revision，必須有 no-op 測試。
- 匯入在同一交易內更新快照、資料、族群定義、排序及其 revision。
- 無草稿匯出維持不替換標的資料、不增加資料／草稿版本；成功後可更新對帳基準、族群位置鏡像、操作紀錄與時間。
- 有草稿匯出固定使用請求開始時確認的 pending snapshot；不能在執行中改抓另一份「最新草稿」。

在 sync state 新增 nullable `base_google_structure_hash`，並明確記錄雜湊契約版本，例如 `google_fingerprint_version`。新的結構 hash 包含固定欄 metadata 位置及依位置排序的 48 個 `{id, columnIndex, header}`，不含 D 資料值或會自動重算的統計值。

沿用原資料 hash 作為 `dataHash`；新增 `structureHash`。兩者必須使用 deterministic canonical serialization；群組 flags 依 UUID key 排序，不能因物件 key 插入順序產生假差異。標題字串的正規化方式須明訂並前後一致，不以合併同名欄或過度 trim 隱藏身份／結構變動。

原有資料列不得用空字串、假 hash 或舊物理位置硬補新基準。`base_google_structure_hash` 為 null 時，先做一次成功匯入建立基準，再允許新版匯出，畫面提示「請先匯入一次，建立欄位同步基準」。migration 不自行讀寫正式 Google Sheet。

## 6. 前端實作

### 6.1 欄位保存控制器

以目前 account 為範圍保存以下狀態，名稱可依現有風格調整：

- 最新使用者排序與 `desiredGeneration`。
- 目前已確認的 settings revision／排序。
- 唯一的進行中保存 Promise，以及尚未送出的最新排序。
- 頁面／帳戶操作世代 `operationEpoch`。
- 保存錯誤或結果待確認狀態。

規則：

1. 每次拖曳立即更新畫面，但只允許一個保存請求進行中。
2. 網路呼叫送出的是當次不可變的排序副本；等待期間的新拖曳只更新待送的最新副本，可合併中間變更。
3. 前次成功取得 revision 後，才以它送下一次保存。舊完成事件不覆蓋較新畫面、提示或另一帳戶的狀態。
4. `flushColumnOrder()` 必須等到呼叫時所要求的 generation 已被確認；不是再平行發一筆相同保存。
5. 保存失敗就停止自動送下一筆，保留本機排序並顯示可恢復狀態。版本衝突須重新讀取／由使用者決定，不自動改成強制覆蓋。
6. 不以 AbortController 或丟棄 response 當作取消伺服器寫入；舊請求可能已提交。
7. 返回持倉、切換帳戶或重新載入資料時隔離世代，避免舊保存 callback 回寫新畫面。再次進入後先取得完整一致的伺服器狀態。

### 6.2 匯入／匯出前的屏障

- 開始同步後立即禁止拖曳、編輯、重複同步；拖曳 handler 與 `assetExcelMoveColumn()` 本身都要檢查，不能只停用按鈕。
- 先 drain 已送出的排序請求。可將最新本機排序 flush 完成，再開始匯入；匯入完成後以 Google 順序取代它。
- 匯出固定捕捉最新排序、資料版本、settings revision、pending snapshot ID，等待 flush 後更新預期 revision，再送出固定輸入。
- 同步後不讓原先排隊的保存請求重新覆蓋匯入結果。
- pending 草稿確認維持既有 UX；後端回 `draft_pending` 才補問時，第二次請求具有新的 operation ID 及重新取得的版本／草稿識別，避免沿用已定案的冪等請求改參數。

### 6.3 同步結果與畫面讀取分離

採用可明確辨識的狀態：`idle`、`saving_order`、`syncing`、`refreshing`、`succeeded`、`refresh_failed`、`conflict`、`result_unknown`。

先記住後端同步結果，再獨立處理畫面資料讀取。建議文案：

| 情境 | 畫面行為 |
|---|---|
| 同步及讀取成功 | 顯示匯入／匯出成功與必要摘要 |
| 同步已成功、讀取失敗 | 「已匯入／匯出成功，畫面更新失敗」＋「重新載入資料」；不再送同步寫入 |
| 寫入請求斷線／逾時、結果不明 | 「同步結果確認中」；查詢同一 operation ID，不顯示確定失敗 |
| Google 內容或欄位結構衝突 | 指出衝突類型，保留本機／草稿並提示匯入 |
| Google 已寫入、後續對帳未完成 | 「Google 已寫入，對帳未完成」；阻止新匯出，提供查詢／對帳入口 |
| 另一筆同步執行中 | 顯示進行中；不自動重送寫入 |

畫面讀取失敗時保留已顯示資料並標示尚未刷新；編輯及新的同步待一致狀態取得後才恢復。只允許安全的唯讀重試。更新狀態須有適當 `aria-live`／busy，維持原來精簡工具列。

HTTP 200 也要驗證回應格式、operation ID、契約版本與成功終態；缺失或 JSON 解析失敗不能直接當成功，應查詢操作結果。

## 7. 後端 v2 請求／回應

延用現有 action 名稱，新增契約版本與操作欄位。以下是邏輯契約，實作者須以型別／驗證器明確表達；ID 與版本值不可由伺服器任意忽略。

寫入請求的共同欄位：

| 欄位 | 規則 |
|---|---|
| `protocolVersion` | 新瀏覽器為 2 |
| `operationId` | 使用者一次操作的 UUID；同一操作查詢／傳輸重試沿用 |
| `accountId` | 仍由服務端驗證為授權的 Frank／台股操作帳戶 |
| `expectedVersion` | 資料／草稿版本；匯入、匯出、save-draft 必要 |
| `expectedSettingsRevision` | 排序保存、匯入、匯出必要 |
| `columnOrder` | 保存及匯出採完整、唯一、合法的固定排序副本 |
| `expectedPendingSnapshotId` | 匯出明確指出有草稿 ID 或 null；不接受狀態悄悄切換 |
| `overwriteDraft` | 僅手動匯入使用，仍依服務端驗證的管理者身份判斷 |

`save-draft` 的既有 rows／groups／allowEmpty 契約保留，但也進入相同帳戶的互斥及 operation ID 流程。

伺服器驗證完整 52 個可顯示欄位；未知 UUID、重複或缺少族群應明確回 validation error，避免靜默補成不同排序。舊 `actions` 鍵在升級正規化階段移除，所有合法新請求都採 canonical 完整排序。

成功結果至少包含：`ok`、`protocolVersion`、`operationId`、`action`、`outcome=succeeded`、資料版本、settings revision、已確認排序、rowCount 與既有營收／刪列摘要。

錯誤／待確認結果至少包含：`operationId`、`code`、`stage`、可理解的 `message`、`googleWriteState`、下一個安全動作。`googleWriteState` 使用 `not_started`、`unknown`、`confirmed` 三值，不能用布林 false 代表「不知道」。

新增 `operation-status` 唯讀 action；查同一帳戶與 operation ID 的持久結果。`status` 或一致性讀取則回目前作用中的操作摘要。

## 8. 資料庫交易、互斥與操作紀錄

### 8.1 用短交易，不跨 HTTP 保持資料庫鎖

Google 網路呼叫在交易外。帳戶互斥使用持久操作紀錄／唯一約束；交易內可用 row lock 或 transaction advisory lock 保護 claim／commit。

**禁止用一個 PostgREST RPC 取得 session advisory lock，期待下一個 RPC 或另一 Edge instance 還持有同一 session。**不要把 Google API 等待放進長資料庫交易。

新增最小操作表，例如 `asset_operation_sync_operations`：

| 欄位群 | 內容 |
|---|---|
| 身份 | operation ID、account ID、action、經驗證的 actor kind／actor ID、protocol version |
| 輸入識別 | canonical request hash、captured 資料版本／settings revision／pending ID、目標排序 |
| 對帳資訊 | 預期前後 data／structure hash、必要的受保護結構摘要、快照參照；不要複製完整資產／股票資料到 log |
| 狀態 | `running`、`succeeded`、`failed`、`conflict`、`reconcile_required`；stage、Google write state |
| 結果 | 精簡結果 JSON、error code、經清理的訊息、started／updated／completed 時間 |

同一帳戶在 `running`／`reconcile_required` 只能有一筆作用中操作，用 partial unique index 或同等原子約束保證。這是實際復原紀錄，不是只有一列布林 busy 的暫存旗標。

一般排序保存／草稿保存可在單一短 RPC 內完成 claim、版本檢查、變更及操作成功紀錄；匯入／匯出才拆為 begin 與 finalize。所有 action 共用同一套帳戶檢查與互斥，包含 cron 及會改 metadata／尾列的維運 action。

相同 operation ID、相同 canonical request：已成功就回原結果；進行中就回狀態，不重跑。相同 ID、不同參數回 `idempotency_key_reused`。確認覆蓋草稿或更新基準後重新操作，應使用新的 ID。

### 8.2 匯入原子提交

新增或版本化受控 RPC，例如 `commit_asset_operation_import_v2`。在同一交易內：

1. 鎖定並驗證帳戶、作用中的 operation ID、資料版本與 settings revision。
2. 再次驗證 pending 草稿及覆蓋資格；不可只依 Edge 先前讀到的 dirty 判斷。
3. 寫入匯入快照、active rows、族群 metadata／display_order。
4. 按 Google 族群順序更新網站 column_order，保留固定欄位相對位置，更新 settings revision。
5. 僅將此次確認覆蓋的 pending 草稿 supersede；全部保留歷史，不刪除。
6. 更新 sync state、data／structure 基準、版本與匯入時間。
7. 同交易保存操作成功結果並釋放帳戶的作用中限制。

任一步失敗，以上業務變更全部回滾；交易外另記該操作的失敗／待確認狀態。對「RPC 回應遺失」先查同一 operation ID 是否已成功，不能直接把操作改成 failed。

不再於 RPC 成功後用獨立 REST PATCH／POST 作廢草稿或保存排序。

### 8.3 一致的畫面資料讀取

用一個唯讀、`STABLE`、`SECURITY INVOKER` SQL RPC 回傳 rows、groups、settings、sync state 與必要 pending 摘要，透過同一 SQL statement 的 MVCC snapshot 取得一致資料。

不要以四個互不相干的 REST 成功回應宣稱它們是同一版本。完整資料驗證通過後再一次提交前端狀態；舊 epoch 的讀取結果丟棄。沿用 authenticated allowlist／RLS，不改其他一般 anon 查詢 helper。

### 8.4 權限

- 新表啟用 RLS。authenticated 只可讀原本具有操作表管理權限的帳戶；anon 無權限。
- 寫入 RPC 由 Edge 的既有 service role 呼叫，預設 `SECURITY INVOKER`、固定 search_path；撤銷 PUBLIC／anon／authenticated 的寫入 RPC execute。
- 不以 `user_metadata` 判斷管理者，不擴張一般資料寫入帳號的 DDL 或任意 RPC 權限。
- 唯讀 RPC 的 execute 與底層 SELECT 權限需明確設定；不要用 SECURITY DEFINER 繞過缺少的 RLS。
- 所有 begin／finalize／recover 都檢查 operation 所屬帳戶與狀態，不能用別人的 ID 完成或解鎖。
- 索引至少包含 operation ID、帳戶作用中唯一約束及帳戶最近操作時間；歷史清理政策另案決定，本次不刪舊快照。

## 9. Google 讀取、匯出及驗證

### 9.1 讀取一致性

保留 `readSheet` 的資料驗證，但優先用一個 Sheets 回應取得目標分頁所需的 metadata、effective values、user-entered formulas 與 grid properties。實作時核對最新 API fields／metadata location 規格，並測量回應大小。

如果受 API 契約限制必須拆讀，至少做 metadata／結構前後重讀，確認讀取過程中位置及身份一致；有變動就丟棄整次結果，再做有限次唯讀重讀。不能把舊 metadata 套在新欄位值上後直接建立快照。

這項改善降低混合狀態風險，不據此宣稱 Google 具有跨多請求的原子快照或已證明存在 Google 快取缺陷。

### 9.2 匯出流程

1. begin 操作，檢查並固定資料版本、settings revision、草稿 ID、目標排序及其 request hash。
2. 讀取 Google 一致狀態；檢查 metadata、48 個 UUID、E:AZ 範圍、資料與結構基準。
3. Google 自上次匯入後的資料或欄位順序／標題有變動，回明確 conflict，不寫 Google。
4. 依請求固定排序產生 move 計畫，不在中途另讀可變的 settings 當輸入。
5. 在 Google 寫入前完成營收資料及尾列刪除安全檢查，保存預期結果與受保護結構摘要到操作紀錄。
6. 先將操作記為可能進入 Google 寫入階段，再送出單一 batchUpdate。整欄移動、既有資料／D 值寫入、必要列整理及本次 operation marker 同批。
7. 回讀驗證資料 hash、族群 UUID 順序、標題、列數、既有公式、A 欄、凍結列、compaction marker 與 operation marker。D 差異沿用 warning。
8. 驗證成功後呼叫短 finalize RPC。**有草稿**才把該 pending snapshot 轉 active、更新 rows／資料版本；**無草稿**僅更新基準、族群位置鏡像、操作紀錄等，不替換 rows／增加資料版本。
9. 成功結果與資料 finalize 同一交易保存；瀏覽器收不到回應時仍可查回原結果。

新 operation marker 要與舊 compaction marker 分開，或以明確不同 metadata key/value 表達；不能因清掉操作標記而破壞「尾列不重複刪除」保護。標記以 sheet scope 儲存，避免混入 48 個欄位身份；累積量須有上限，同批維持最後一次操作標記即可，歷史由資料庫保存。

### 9.3 驗證與重試界線

- 保護公式時依欄位身份與合法的移動後位置驗證；Google 可能調整公式參照，不能把所有公式字串的任何變化都當毀損，也不能只檢查「有等號」就宣稱公式正確。依真實版型建立針對移動、插列、刪列的回歸案例。
- 唯讀逾時／暫時 429／5xx 可有限重試，初始最多 3 次，含退避、Retry-After 與整體時間預算；權限、結構、版本錯誤不重試。
- 送出 Google 寫入後的逾時、斷線或不明 5xx：結果未知，不能直接重送 moveDimension、deleteDimension 或整筆匯出。
- 回讀不一致可再做有限次唯讀確認；持續不同就保留差異與警告，不循環重寫到「看起來一樣」。
- Google 的 batch 原子性只涵蓋那次 Google 請求；無法鎖住 Google 網頁的人工編輯。人工修改落在 preflight 與 batch 之間仍有競爭窗口，尤其完整覆寫可能覆蓋該窗口的人工變更。操作表同步期間應避免同時人工修改；本次不能宣稱完全消除外部競爭窗口。

## 10. 不確定結果與復原

新增受控 `reconcile` 流程；一般使用者介面可觸發「確認同步結果」，後端仍驗證原有管理者與帳戶。先唯讀查明，只有下列可證明狀態才完成資料庫 finalize。

| 狀態 | 安全處理 |
|---|---|
| operation 已 succeeded | 回原結果，畫面只重新讀取 |
| 匯入 RPC 回應遺失 | 查操作紀錄；其成功紀錄與資料同交易，因此可確認是否已提交 |
| 可證明尚未送出 Google 寫入 | 將原操作結案為失敗，重新取得最新狀態後才接受新的操作 |
| Google operation marker 相符，資料／結構／保護驗證皆符合預期 | 以原操作固定輸入完成 DB finalize，不再寫 Google |
| Google 回應遺失、回讀暫時失敗 | 維持結果未知，有限次唯讀重試；作用中操作保持阻擋 |
| marker 缺失、資料不同、受保護結構異常、或舊請求仍可能在途 | `reconcile_required`，停止新匯出，保留草稿與差異，交由明確的對帳／以 Google 為準復原 |

原始「以 Google 為準重新匯入」也須透過受控復原轉移：先確認舊 writer 已不會再執行、取得並顯示現況，必要時讓管理者確認作廢草稿，再原子完成匯入及原操作結案。不能讓一般 import 繞過作用中的未知操作。

不得只因時間過期就刪操作紀錄／釋放鎖並重跑 Google 寫入。資料庫 lease 或 fencing token 也不能撤銷已送到 Google 的在途請求。若無法證明安全，保留阻擋與可操作訊息，由維運核對平台執行狀態後恢復；不自動循環。

同一操作紀錄只能透過合法狀態轉移完成一次；finalize 重入必須回原結果，不重複增加版本或刪列。

## 11. 錯誤分類與觀測

不能把全部 409 顯示成「Google 有新修改」。至少區分：

| code | 意義／前端行為 |
|---|---|
| `settings_conflict` | 另一裝置更新排序，重新取得版本，保留本機意圖 |
| `data_version_conflict` | 資料／草稿版本改變，不覆蓋 |
| `google_data_conflict`／`google_structure_conflict` | Google 主檔改變，提示先匯入 |
| `draft_pending` | 沿用人工覆蓋草稿確認；cron 不覆蓋 |
| `sync_in_progress` | 同帳戶已有操作，查狀態，不重送 |
| `baseline_required` | 升級後先成功匯入建立結構基準 |
| `verification_failed`／`reconcile_required` | 說明是否可能已寫入 Google，停止新匯出 |
| `client_upgrade_required` | 舊前端寫入契約不安全，要求更新頁面 |

暫時服務錯誤依真實情況保留 HTTP／SQLSTATE，未預期錯誤保留 500。可用 202 表示已受理但尚未確認完成；202 不得當成成功終態。

每筆伺服器事件至少記錄 operation ID、action、stage、code、耗時、資料／設定版本、rowCount、是否需要移欄／刪列及三態 Google write state。失敗時保留經清理的外部 HTTP／SQLSTATE、預期／實際 hash 與精簡差異。

禁止記錄 Supabase URL、token、Google 私鑰、Authorization header、密碼、完整請求／回應 body 或完整持倉。Google 錯誤訊息也要清理後才寫 log，不能直接 dump 外部 payload。使用者畫面顯示短訊息與操作編號即可。

先加入會在原始碼失敗的 R1～R3 行為測試，再修改。不要只加正規表示式檢查函式名稱或 mock 掉被測的交易／排序功能。

### 12.1 前端測試

### 12.2 Edge／資料庫／整合測試

| ID | 案例 | 必須斷言 |
|---|---|---|
| B01 | 匯入交易在 rows／groups／settings／草稿任一步注入錯誤 | 全部業務資料、版本與草稿一起回滾 |
| B02 | 同 settings revision 的兩筆保存併發 | 只允許一筆有效提交，另一筆明確衝突 |
| B03 | 同帳戶 import／export／save-draft／cron 競爭 | 帳戶 guard 防止交錯寫入；cron 不覆蓋 pending |
| B04 | 同 ID 同參數重送／不同參數重送 | 回原結果或拒絕，不增加版本、不重刪列 |
| B05 | data hash 相同，但 Google 順序或同名族群位置變動 | 結構基準偵測衝突，零 Google 寫入 |
| B06 | 讀 metadata 與值之間移欄 | 不以混合讀取資料建立 active snapshot |
| B07 | 有草稿／無草稿；順序變／不變的四組匯出 | 資料、版本、D 與排序各依契約處理 |
| B08 | Google batch 已成功但回應丟失／DB finalize 暫時失敗 | 以 marker＋回讀復原；batch 最多執行一次 |
| B09 | Google 回讀失敗、持續資料差異或 marker 缺失 | 不重寫、不自動解除未知狀態、不清草稿 |
| B10 | 固定欄位置、48 個 UUID、重複名稱、插列刪列、清空模板 | 原有保護與 compaction 冪等全部保留 |
| B11 | 沒有營收、D 差異、月份切換 | 寫入前必要資料缺失會擋下；D mismatch 仍警告 |
| B12 | 未登入、非管理者、他帳戶、cron 偽造、直接 REST／RPC 寫入 | 按原授權邊界拒絕；沒有 anon 降級 |
| B13 | 新基準 null、舊前端契約、既有 cron 請求 | 前端明確要求升級／匯入；合法 cron 維持相容 |
| B14 | 狀態查詢與 finalize 併發、舊操作 finalize、未知操作回收 | 不錯誤解鎖、不重複提交；在途 Google 不被假定已取消 |
| B15 | 一致 read-state 與匯入提交併發 | 回完整舊版或新版，沒有 rows／settings 混版 |

RPC 原子性要用真實 PostgreSQL 驗證；兩個獨立 HTTP 請求不是同一個 BEGIN／ROLLBACK。故障注入及多連線競爭測試在測試資料庫或隔離環境執行，不在正式操作表寫測試資料。

48 欄排列測試改成固定 seed 的 permutation／property 測試，保證可重現；保留目前 39 項既有測試及原資料安全案例。

### 12.3 Google 試算表副本端到端

使用獨立測試設定指向副本，包含 48 個 UUID、同名族群、公式、checkbox、格式及凍結列；不要僅複製資料值。副本的 spreadsheet／sheet ID 不得覆蓋正式 secrets。

依序驗證「匯入 → 連續拖曳 → 立即匯出 → 再匯入」、資料新增／刪除與清空、兩分頁競爭、慢網路、同步成功後讀取失敗及中斷後對帳。逐 UUID 核對每檔勾選，不只比較標題或欄位數。以真實 Google API 確認 marker、公式參照與格式保留。

## 13. 實作順序與完成關卡

1. **基準與重現**：乾淨、最新的程式副本；加入 R1～R3 失敗案例，保存測試前證據。
2. **契約／migration**：完成 revision、基準、操作表、RLS 與 RPC；用測試資料庫驗證交易及競爭。
3. **後端**：先接原子匯入、固定匯出輸入及操作狀態，再接 Google marker／對帳；不能只修 happy path。
4. **前端**：保存控制器、屏障、read-state、結果分離、unknown／conflict UX 及世代保護。
5. **回歸及副本驗收**：完成第 12 節，確認沒有放寬原資料保護。
6. **文件與部署準備**：逐一列出 migration、Edge、前端相容與復原檢查結果；提交前同步狀態文件。
7. **正式部署與驗收**：依使用者當次授權及 repo 發布規則執行；未完成就保留「待正式驗收」。

初步功能名稱可沿用本文件；若接手發現更簡單、同等涵蓋所有驗收案例的設計，可先以證據比較後調整。不能因省略持久對帳、跨分頁版本或交易驗證而宣稱方案等價。

## 15. 部署、相容與回復

### 15.1 正式變更前

- 確認精確 repository、Supabase project、Edge function、正式 Google 操作表與發布目標；識別資料從環境／既有設定取得，不把 URL／密鑰貼進文件。
- schema migration 是獨立變更流程，先審閱並在測試環境驗證；不可混進一般 publish-only workflow 偷套。
- 依使用者授權執行正式 migration、Edge 部署、Git push 與 Actions；本文件本身不執行這些動作。

### 15.2 順序

1. 套 additive migration，核對 schema、函式簽名、索引、RLS／GRANT；舊欄位及快照保留。
2. 部署新版 Edge，保留原來的 JWT 設定及程式內身份驗證。舊瀏覽器寫入缺少新契約時明確回 `client_upgrade_required`，不能走繞過 revision／guard 的舊寫入路徑。
3. cron 的既有 secret 身份另有相容 adapter：由後端建立 operation ID、在 guard 下捕捉版本，維持 18:30 及不覆蓋草稿；瀏覽器不得偽裝此例外。
4. 將已測試的網站程式依授權推到 `main`，用既有 `daily-snapshot.yml`、`publish-only=true` 發布。短暫遇舊前端的使用者看到更新頁面提示，不能靜默接受不安全寫入。
5. 查核 Actions 的 success／headSha、正式 gh-pages 及公開 manifest／site.js 同版。不能只看綠燈。
6. 正式使用者先匯入建立結構基準，才做最小幅度族群移動及匯出／再匯入驗收；前端、Google、操作結果及資料庫版本一起核對。

若未取得正式試算表操作授權，交付副本驗收、正式唯讀檢查與具體待驗收步驟，不宣稱正式驗收完成。此修復不涉及 OCR，不需重建 OCR Worker。

### 15.3 回復策略

優先暫停同步寫入並保留查詢。若需回退前端／Edge，只回退到仍遵守新版 schema、guard 與 unknown 狀態的相容版本；不可重新開放舊 v25 的無版本寫入來繞過待對帳操作。

schema 採 additive，通常保留不用；不 drop 操作紀錄、不刪歷史快照、不用硬重設覆蓋資料。Google 已寫入的操作先對帳，不能因程式回退就自動反向移欄或把舊快照蓋回去。
