# 台股操作表雙向同步實作規格

## 目的與權威來源

- Google Sheet「操作(台)」是人工編輯主檔，保存 Buy、Stock、48 個族群及族群欄位順序；D 欄「營收創高」由網站匯出寫入（見下）；目前受控範圍是第 3 列標題下的 B:AZ。
- Supabase 是網站讀取、版本控制、草稿與對帳鏡像，不是另一份可獨立漂移的清單。
- 網站不把 Google service account 私鑰或 Supabase service role key 放進瀏覽器。
- `Buy`、`Stock`、48 個族群 checkbox、族群欄位順序與資料列順序可編輯／取代；匯入時網站族群欄順序跟隨 Google Sheet，匯出時 Google Sheet 的 E:AZ 族群欄順序跟隨網站。D 欄「營收創高」不從 Google 匯入，而是網站依 `revenue_latest` 計算後，在每次匯出時以 V／X／- 寫入（2026-10-06 起，取代 9/24「D 永遠不寫入」的契約）。
- 網頁顯示受控欄位共 52 欄（權重、Buy、Stock、D 欄唯讀結果、48 族群）；刪除按鈕只在編輯時放於 Stock 儲存格，不得新增「操作」資料欄。舊 `column_order` 的 `actions` 鍵會忽略並清除。
- 第 1、2 列統計公式、第 3 列標題、A 欄計算值、D 欄格式與 checkbox 驗證、凍結列與其他分頁都不在受控寫入範圍；D 欄只寫「值」，第 1、2 列的統計公式會自動重算。

## 資料流

```text
Google Sheet B:C、E:AZ --import--> Edge Function --RPC--> Supabase active snapshot / rows
Google Sheet E:AZ 族群欄順序 --import--> Supabase display_order + website column_order
網站編輯 --save-draft--> Edge Function --RPC--> Supabase pending snapshot
網站匯出 --export--> Google hash 檢查 --moveDimension 同步 E:AZ 族群欄順序
  ├─ 有草稿：batchUpdate B:C、D、E:AZ + deleteDimension 尾端多餘列 --> 讀回驗證 --> RPC --> Supabase active
  └─ 沒草稿：必要時移動 E:AZ + batchUpdate D 欄營收創高 --> 讀回驗證 --> 更新結構基準／操作紀錄（不改 rows／資料版本）
```

匯出是完整取代受控資料列，不是逐列 patch：網站刪除 2 筆後，Google Sheet 尾端多出的 2 個標的列會以 `deleteDimension` 實體整列刪除，兩邊標的數量相同；
網站刪到 0 筆時，保留第 4 列作為空白輸入模板，只清除該列 B:C、E:AZ，並刪除後續舊標的列。一般匯出不會刪除原本就空白的預留列。
整列刪除只作用於操作分頁的尾端，先確認 AZ 以外沒有值／公式／驗證／註記、也沒有跨越待刪列的合併儲存格；刪除後回讀驗證標的 hash／筆數、表頭、統計公式、保留列 A 欄與凍結列。
匯出會用隱藏 developer metadata 記錄已整理的快照 ID，避免重試時重複刪除空白列。若舊版已先清空標的值但留有殘列，受保護的 `repair-stale-tail` 會在狀態 clean、沒有 pending 草稿、目前 hash 相符，且快照歷史明確證明最近一次匯出少了標的時才修復一次。
若 Google Sheet 自上次匯入後已被人工修改，hash 不相同時回傳 HTTP 409，禁止覆蓋，使用者必須重新匯入。

## Google Sheet 欄位契約

- `Buy`：B 欄；整數且不可小於 0。
- `Stock`：C 欄；格式為「代號 空白 名稱」，代號不可重複。
- `營收創高`：D 欄只由匯出寫入，不匯入、不納入 hash，因此不影響 Google 衝突檢查。值與網站畫面完全相同：台北「上個月」`revenue_latest.high_months ≥ 13` 為勾選（V）、已公布未達為 `X`、尚未公布為 `-`；不退回上上個月，`high_months` 為 null 的已公布列與網站一樣算 `X`。後端 `revenueHighValue`／`eligibleRevenueMonthKey` 與 `site.js` 的 `assetExcelRevenueHighValue`／`eligibleMonthKey` 以測試逐案對照，改任一邊都要同步改另一邊。
- 族群：E:AZ 共 48 欄。每欄以 developer metadata `metadataKey=invest.asset-operation`、`metadataValue=group:<uuid>` 識別，不能只用標題文字（目前有重複的「導線架」）。
- 族群欄順序：匯入依 metadata 實際欄位位置更新 Supabase `display_order` 與網站 `column_order` 中的族群欄位置；匯出讀網站 `column_order`，以 `moveDimension` 移動整個 E:AZ 欄，讓標題、勾選值、格式、驗證與 developer metadata 一起移動。匯出前後驗證列資料 hash、族群 ID 順序與第 3 列標題；若 Google 資料版本已變更則回 HTTP 409，不移動欄位。
- `A` 欄與第 1、2 列不寫入；只更新 B:C、D、E:AZ 的 `userEnteredValue`（D 僅在匯出時寫營收創高值），保留格式、checkbox 驗證與凍結列。新增資料列先以 `copyPaste PASTE_NORMAL` 從第 4 列複製版型（A 欄公式跟著延伸），同一批次再由 D 欄值覆蓋。

## Supabase schema／權限

- `db/058_asset_operation_full_sheet_sync.sql`
  - 擴充 `asset_operation_rows`：`stock_code`、`stock_name`、`group_flags`、`snapshot_id`。
  - 新增 `asset_operation_group_columns`、`asset_operation_snapshots`、`asset_operation_sync_state`。
  - 建立 `replace_asset_operation_snapshot(...)`，以版本號與 transaction 一次取代 active rows。
- `db/059_asset_operation_sync_write_hardening.sql`
  - authenticated 只保留操作表、設定表的 SELECT；INSERT／UPDATE／DELETE 只能由 Edge Function 的 service role／RPC 執行。
- `db/060_asset_operation_sync_cron.sql`
  - UTC 10:30（台北 18:30）呼叫 import；有 dirty 草稿時不覆蓋。
  - 依賴 Vault secret `asset_operation_cron_secret`；未設定時 migration 會略過建立 job。
- `db/063_asset_operation_sync_reliability.sql`
  - 加入 settings revision、Google 結構基準、operation journal、RLS 與 service_role 專用 v2 RPC；匯入快照、族群排序、草稿作廢及版本更新在單一交易完成。
- `db/064_asset_operation_sync_policy_initplan.sql`
  - 將 operation journal 的管理者 JWT RLS 判斷包成 init-plan；authenticated 僅能讀 Frank／台股操作紀錄，寫入仍只由 service_role RPC 執行。

### v2 同步與結果不確定處理

匯出請求必須在欄序 flush 完成後附上完整 `columnOrder`（4 個固定欄＋48 個 group UUID），並使用保存後的 settings revision；無草稿與未移欄也不能省略。欄序陣列是該 operation ID 的固定輸入，重試不能換成另一份順序。缺少陣列時維持 422／`invalid_column_order`，不得用後端預設排序掩蓋前端漏傳。2026-10-17 已補齊此前漏傳的前端呼叫；`tests/asset-excel-export-contract.test.mjs` 驗證真實前端傳輸與 Edge 驗證，RPC／Google 仍使用隔離 fixture。

所有瀏覽器寫入都帶 `protocolVersion=2`、operation ID、資料版本、settings revision 及必要的 pending snapshot ID。舊版前端缺少這些欄位時回 `client_upgrade_required`，不可走舊版無版本寫入路徑。`asset_operation_read_state_v2` 以一個 `STABLE SECURITY INVOKER` RPC 一次取得 rows、groups、settings、sync state、pending 摘要與作用中 operation。

匯入／匯出先 claim 同帳戶操作，再由資料庫版本／部分唯一索引阻止另一分頁或 cron 交錯提交。匯入由一個 RPC 原子替換快照、rows、族群順序、設定 revision、Google 基準及操作結果。匯出固定 pending／排序輸入，在 Google batch 中寫入 operation marker；回讀驗證後才 finalize。前端排序保存序列化並可等待指定 generation；同步成功後的畫面重讀失敗只顯示刷新問題，不會把同步說成失敗。

Google 寫入回應不明時保留 `reconcile_required` 與 operation ID，先以唯讀狀態及 marker 對帳，沒有證據時不重送整批寫入，也不因逾時自動解除鎖。成功匯入／匯出與其後畫面重新讀取分開處理。受保護公式在欄位 UUID／固定欄身份下正規化 A1 參照語意比較，以容許合法移欄和尾列刪除造成的參照調整；正式 Google 試算表副本尚待端到端驗收。

### 筆記 #91：表頭公式與中斷對帳（2026-10-20）

- 第 3 列同時包含文字及 A3 SUM 公式；文字按原值、公式按欄位 UUID／固定欄身分及 A1 語意驗證。不能逐字比較公式，也不能略過 A3。
- 匯出前的 finalize JSON 保存精簡保護證據（前 3 列、後續 A 欄、欄位身分、凍結列、列數）與營收值；無草稿匯出可依同 operation marker／資料與結構 hash 重驗後 finalize，不重送 Google batch。草稿匯出未完成完整驗證仍不得自動恢復。
- 舊操作沒有證據時不能補造成功；提示維運依 Google 主檔復原。筆記 #91 已核對 36 筆／48 欄，將原操作保留為 recovered-from-google，並在同一交易使用既有 RPC 建立新匯入，版本 60、clean、作用中操作 0，未寫 Google。詳細操作與驗證見版本紀錄。
- 目前 Edge 為 v27 ACTIVE，無新 migration；網站發布狀態見版本紀錄最新 #91。

## Edge Function actions

檔案：`supabase/functions/asset-operation-sync/index.js`

- `bootstrap-metadata`：第一次使用時建立 Buy／Stock／D 與 48 個族群 metadata。正常 `import` 在 metadata 完全不存在時會自動 bootstrap；已有部分 metadata 時停止並要求修復，避免產生重複識別碼。
- `repair-metadata`：只刪除同一欄位的重複同步 metadata，並重新確認 Buy／Stock／D 與 48 個族群都完整。
- `import`：讀 metadata、只從 Sheet 讀 B:C 與 E:AZ，驗證列與 checkbox，建立 active snapshot，並以 Google Sheet 的族群欄順序更新網站排序設定。有 pending 草稿時回 HTTP 409／`code=draft_pending`；只有管理者 JWT 且 body 帶 `overwriteDraft:true`（網站確認視窗按「確定」）才會以 Google 為準匯入，並把 pending 草稿標為 `superseded`（保留紀錄）。cron 身分永不覆蓋草稿。
- `save-draft`：接收網站目前完整列集合，建立 pending snapshot；`expectedVersion` 不符回 409。
- `export`：讀最新 pending snapshot，檢查 base hash，先以 `moveDimension` 同步族群欄順序，再在同一批次寫 B:C、D、E:AZ 並實體刪除多出的尾端標的列，重新讀取並驗證列數、資料 hash、族群 ID 順序、統計公式、標題、保留列 A 與凍結列後才 active；D 欄回讀不一致只在回應的 `revenueHigh.mismatches` 回報，不讓匯出失敗。營收資料取不到時在任何 Google 寫入之前失敗。
- `export`（沒有 pending 草稿）：比對 Google hash 後，若網站族群順序與 Google 不同，先在同一個 batchUpdate 移動 E:AZ 整欄，再寫 D 欄營收創高；回讀比對列 hash、族群順序、標題與營收值（營收差異仍只回報）。不改 Buy／Stock／族群勾選值或 Supabase 版本；若寫入期間標的資料被改動則停止並要求重新匯入。回傳 `revenueOnly:true`、`groupOrderChanged` 與 `revenueHigh`（月份、V／X／- 數量）。
- `repair-stale-tail`：只接受 cron secret；僅依最近 `google_import`／`google_export` 快照差額、clean 狀態、無 pending 草稿與 Google hash 相符判斷舊版殘列，並以 Sheet metadata 防止重複修復。
- `save-column-order`：只保存目前 52 個顯示欄位的順序；`actions` 是舊版 UI 專用鍵，不再接受或寫回 `asset_operation_settings`。
- `status`：讀取同步狀態供網站顯示。

## 失敗與復原

- HTTP 409：Google 或網站版本衝突；不要重試 export，先 import 並確認差異。
- 寫入前的資料／欄位衝突：沒有作用中未知操作時，按「從 Google Sheet 匯入」並確認草稿覆蓋。寫入後結果未知則先「確認同步狀態」，不得用一般匯入繞過鎖；證據不足時由維運核對 Google 現況、原 handler 已結束的錯誤紀錄、原版本與草稿，再原子結案舊操作並建立 Google 主檔新基準。不得只因逾時而解鎖或重送 Google。
- 新增列的 A 欄公式以第 4 列為範本，正規化參照後比對；上方統計公式依欄位身份及參照語意驗證。寫入前就存在的保留列仍不得改動（`writeGoogle` 回傳 `appendedFromRow` 作分界）。
- Edge／Google secrets 未設定：前端只顯示錯誤，不退回直接 REST 寫入。
- migration 尚未套用：不可發布會查詢新表的正式前端；先完成 schema／function 部署。
- 雙向同步不涉及下單、投資建議或買賣訊號；任何擴充都必須另訂 schema 與權限審查。
