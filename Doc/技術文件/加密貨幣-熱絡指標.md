# 加密貨幣－熱絡指標

> 日期：2026-09-09
>
> 狀態：**修正規劃已整理，尚未改 Code、尚未發布**
>
> 範圍：市場切換頁 9 檔加密貨幣的熱絡分數、日期邊界與熱力圖權重；不延伸為交易訊號

## 一、結論

2026-09-09 查核的公開快照約 2.5 分，前端顯示與現行公式相符；主要問題在來源語意與公式。下一版必須：

1. Yahoo 加密貨幣 `volume` 直接視為報價貨幣成交額，不再乘收盤價。
2. 排除正在形成的 UTC 當日 K，只使用上一個完整 UTC 日。
3. 每個幣先和自己的前 20 個完整 UTC 日比較，再以中位數／等權方式聚合。
4. 熱絡分數只衡量相對成交額與絕對波動；漲跌方向另外顯示，平盤保持中性。

本文件是計畫，不代表網站已修正。Yahoo chart API 沒有正式文件，`volume` 語意屬目前數值交叉
比對所得的高可信判定；實作前仍要對 9 個 symbol 逐一驗證，不能把 BTC 單一樣本當永久契約。

## 二、目前實作與兩個確定問題

美股與加密貨幣目前共用 `YahooFinanceDailyQuoteClient`：

```text
TradingValue = close × volume
```

這對股票是「股價 × 股數」，但對加密幣不是同一語意。BTC-USD API 的 `volume` 約 343.6 億，
與 Yahoo 畫面上的 24 小時成交量數值同量級；目前因此高可信判定該欄已是 USD 等報價貨幣成交額。
再乘一次 BTC 價格等於重複換算，使 BTC 在現行 9 幣 weight 中失真到約 98.5%。因 Yahoo 端點沒有
官方 schema／SLA，文件不得把這項推論寫成資料商保證；落地前需保存各幣 API 原值與 Yahoo UI
交叉核對證據。

第二個問題是日界線。美股 workflow 排定 23:30 UTC 進場，再等到 20:30 ET 才下載；夏令時間約為
UTC 次日 00:30，冬令時間約為 01:30。加密市場 24/7，這時 Yahoo 的 UTC 當日 K 只形成約半小時至
一個半小時，現行程式卻會把它當完整日。結果是當日成交額異常小、漲跌幅也只涵蓋很短時間。

另外沿用美股公式還有共同問題：

- `change >= 0` 把平盤算上漲。
- 上漲家數占熱絡分數 50%，把多空方向混入活動程度。
- `TakeLast(20)` 包含目前日，當日極端值會壓低自己的相對倍率。
- 先加總絕對成交額再比較，BTC 的規模會支配總分。

## 三、日期與來源契約

下載時間記為 `downloadedAtUtc`，可接受的 target 必須滿足：

```text
targetDate < DateOnly.FromDateTime(downloadedAtUtc.UtcDateTime)
```

也就是永遠排除 UTC 今天，通常取 `UTC yesterday`。每個幣都必須有同一 target date；某幣缺 target
就標 warning／排除該幣，不能偷偷用該幣更早一天和其他幣的昨天混算。基準為 target 前 20 個完整
UTC 日，target 自己不在視窗內；至少需要 target、前一日 close 與 20 個基準點。

成交欄位需在 Domain 上分清語意：

- 美股：`EstimatedTurnover = close × share volume`。
- 加密幣：`QuoteTurnover = Yahoo volume`，不再乘價格。
- 不應繼續用一個模糊的 `TradingValue` 讓兩種市場暗中共用轉換。

若 9 幣交叉查核顯示某些 symbol 的 Yahoo `volume` 並非報價貨幣成交額，應把該幣標為不可比較，
或改接具有明確 schema 的資料源；不得為湊齊 9 幣自行猜單位。

## 四、新指標的語意與公式草案

固定原則：

- 0～10 分只代表相對近期的活動程度，不代表看多／看空。
- 每個幣先正規化，再做等權聚合；不使用原始 USD 規模作市場總分權重。
- 上漲、下跌、平盤比例與中位漲跌幅另列為方向資訊。
- 所有基準只用已完成的 UTC 日。

建議第一版：

```text
turnoverRatio(i,t)   = quoteTurnover(i,t)
                       / median(quoteTurnover(i,t-20 ... t-1))
absReturn(i,t)       = abs(close(i,t) / close(i,t-1) - 1)
volatilityRatio(i,t) = absReturn(i,t)
                       / median(absReturn(i,t-20 ... t-1))

scale(r)             = clamp((r - 0.5) / 1.0 × 10, 0, 10)
activity(i,t)        = 50% × scale(turnoverRatio) + 50% × scale(volatilityRatio)
heatScore(t)         = median(activity(i,t) for all valid coins)
```

中位數讓 BTC 或單一 meme coin 的事件日不會獨自把整體拉滿。若有效幣數太少，分數應為 `null`；
最低有效樣本數要在歷史回放後明訂，不能臨時用 1～2 個幣代表整個市場。`scale()` 暫沿用 0.5 倍＝
0 分、1 倍＝5 分、1.5 倍＝10 分，係數仍待回測。
任一歷史中位數分母小於或等於 0 時，該分量應回 `null` 並產生 warning，不用任意 epsilon
把資料缺陷轉成極端高分。

方向：

```text
return > 0  => advance
return < 0  => decline
return = 0  => flat
```

因此急跌爆量應顯示「高熱度、偏空」，無量小漲應顯示「低熱度、偏多」。

## 五、熱力圖大小

現行 raw `TradingValue` share 受錯誤乘價影響，會讓 BTC 約占 98.5%，也不是市值權重。修正
`volume` 單位後，絕對成交額仍然會自然由大型幣主導，因此不能直接把它包裝成「賽道權重」。

第一版建議使用**等尺寸 tile**，顏色只表現漲跌，tile 內另外顯示每幣 `turnoverRatio`／活動分數。
這是沒有可靠 market-cap source 時最誠實且最簡單的呈現。若未來要按市值分大小，應另接具有明確
市值定義、時間戳與供應 SLA 的來源；若要按相對活動分大小，標題必須明寫「相對活躍度」，不能叫
市場權重或市值權重。

## 六、必要測試與驗收

| 情境 | 預期 |
|---|---|
| UTC 00:30／01:30 下載含 UTC 今天 candle | 拒絕今天，只選上一個完整 UTC 日 |
| BTC `volume = 34.36B`、close 為正值 | QuoteTurnover 保持 34.36B，不再乘 close |
| 某幣缺 target date | 不往回拿舊日冒充，輸出 warning |
| target 日爆量 | target 不得進自己的 20 日基準 |
| 全幣爆量大跌 | 高熱度、方向偏空 |
| 多數幣無量小漲 | 低熱度、方向偏多 |
| 報酬率等於 0 | 計入 flat，不算 advance |
| BTC 絕對成交額遠大於其他幣 | 等權／中位數總分不被 BTC 規模支配 |
| 單一小幣異常暴量 | 中位數不被單一 outlier 拉滿 |
| 成交額或絕對波動的歷史中位數為 0 | 對應分量為 null 並輸出 warning，不除以 0 或自行補 epsilon |
| 少於 20 個完整基準日或有效幣數不足 | heatScore 為 null，不用不完整資料硬算 |

歷史回放至少涵蓋正常日、週末、UTC 跨日、全市場急跌、單幣事件與 Yahoo 缺值。另以 9 個 symbol
逐一保存一次 raw `volume`、Yahoo 畫面值與日期證據，確認單位後才改 Domain 契約。
