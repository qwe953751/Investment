## 備份格式與一致性

入口是 `python3 scripts/backup-bundle.py create data/snapshots`，需在 repo 根目錄執行。
`backup-supabase.sh` 是內部匯出器，直接呼叫會拒絕，避免誤存明文。

- `YYYY-MM-DD.backup.cms`：CMS AES-256-GCM 加密的 gzip JSON，含兩部分 SQL、來源列數與測試用 Auth UUID。
- `YYYY-MM-DD.backup.json`：schemaVersion 2，只有日期、時間、檔案大小／SHA256、逐表列數及排除清單。
- 清理後的舊歷史檔為 `YYYY-MM-DD.sql.gz.cms`，解密後是原來的 gzip SQL；它們沒有新格式完整性清單，
  不可冒充新格式的正式還原驗收結果。

先以 invest_writer 開啟唯讀 REPEATABLE READ 交易並匯出 snapshot；專用角色匯入同一個 snapshot。
兩份 pg_dump 與來源 count 都使用這個一致性時間點，避免同時修改資料造成跨表錯配。
保留原生資料的公開 schema／資料範圍，九張表的內容則由 `invest_backup_reader` 匯出。
這兩部分都只在 0700 暫存目錄／記憶體內存在，最後一起加密；全部匯出與驗證成功才寫入密文，manifest 最後替換。

`db/072_protected_backup.sql` 僅授予專用角色九張表的 SELECT 與 USING(true) SELECT policy：
沒有 BYPASSRLS、superuser、建表或寫入權，也沒有 private_notes／admin_bgm 的 SELECT。
密碼由獨立管理程序設定，migration 不含密碼。invest_writer 權限不變。
備份前對每張保留內容的表確認完整 SELECT policy，遇到無法證明完整可見、或額外 restrictive policy 即中止。
匯出後逐表比對 COPY 實際列數；零列不會被壓縮檔大小或結尾標記掩蓋。

日期以台北時間計算。GFS 最近 5 份、每週 4 份、每月 6 份按日期輪替，密文與 manifest 同步保留／刪除。
保留數量受可用日期影響，不保證一開始就有 15 份。

## 金鑰與環境

| 設定 | 位置／用途 |

| SUPABASE_DB_URL | 既有 invest_writer 連線；原生資料匯出與警報 |

| BACKUP_DECRYPT_KEY_FILE | 本機解密時指向受限私鑰檔，不是金鑰內容 |
| PG_DUMP／PSQL／OPENSSL | 選配的工具完整路徑；需支援來源 PG 版本與 CMS AES-GCM |

Mac 的私鑰與原始歷史封存放在 repository 外的 `~/.codex/private-backups/Investment/`，
目錄 0700、私鑰／連線設定 0600。其他電腦不會因 git pull 而取得解密能力。
私鑰遺失將無法解密歷史備份；需以受控方式另外保管，不能貼到 chat、log 或 commit。

## 排程與警報

daily-snapshot.yml 的 backup job 依賴 preflight／snapshot 終態，但使用 always 判斷；
排行 skipped／failure 都仍備份，取消或 publish-only 則不動備份及既有備份警報。
手動補備份指定 `backup-only=true`、`publish-only=false`，不回補行情、不同步行情、不發布網站。

只有提交並推送 data、重新 fetch、核對遠端檔案 blob 與本機一致、驗證 manifest 成功，才解除「原生資料備份」。
失敗保留獨立 error；純發布不能解除。其他行情 workflow 前進 data 時，允許 rebase 本次 snapshots 提交，
只要遠端包含此提交且兩個備份檔一致即可，不要求 data HEAD 永遠停在備份提交。

restore-test.yml 每週日台北 08:00 及手動執行，挑最新 manifest，96 小時以上或未來時間直接失敗。
它核對雜湊、解密、逐表數量，再還原到拋棄式 PostgreSQL 17 容器。正式連線僅交給分開的 alert job，
restore job 沒有正式庫連線。「備份還原驗證」僅在真正還原成功時解除；純發布不動。

## 隔離還原與正式還原邊界

測試環境提供 Auth UUID 表與 JWT helper，相依 UUID 從密文讀出，沒有 Auth 密碼或 token，不能用來登入。
SQL 按 pg_dump 的 pre-data → 全部 data → post-data 合併；九張表資料先載入，之後才建立／驗證原有外鍵與 trigger。
這避免恢復 OCR 列時誤發 Realtime 通知；不移除外鍵、不忽略 SQL 錯誤，也不把 Realtime 假成功當成驗收。
33 張原生／受保護表逐張比對來源列數，行情／裝置資料須空，私人筆記與 BGM 表須不存在。

正式庫仍只允許人工差異分析後補回缺少資料，不得 DROP／TRUNCATE／--clean。
本備份不是整個 Supabase 專案備份：Auth 登入憑證、Vault 設定、私人筆記、BGM 與 Storage 檔案不在範圍內。
換專案時必須另行設定身分、金鑰與 Vault；不可把測試 UUID 表當正式 Auth 還原方案。

遠端更新只針對 data ref，使用原 HEAD 的精確 force-with-lease，拒絕覆蓋新的行情提交。

## 外洩金鑰的替代與驗證

網站／Worker 使用 publishable key；Actions Storage 與雲端函式各用新的獨立 secret key。
後端 secret key 放 apikey header，不作 Bearer JWT；登入者的 Authorization JWT 照常轉送。
六支 Edge Function 優先讀 INVEST_SERVICE_ROLE_KEY，保留 legacy fallback 只供切換期間相容。

`db/073_watchlist_webhook_secret.sql` 從 Vault 讀取 webhook 專用 secret 與端點，函式定義不含值；
撤銷 PUBLIC／anon／authenticated 對 SECURITY DEFINER trigger function 的直接執行權。
us-watchlist-dispatch 自行以固定長度 SHA256 比對 webhook secret；拒絕只有 service_role claim 的 JWT。
只有驗證配對 secret 的 request 才能進入原有業務邏輯；不改股票名單、持倉或下單範圍。

先切換並驗證使用端，再停用 legacy API keys 並撤銷舊 HS256 signing key。現行 Auth 已使用 ES256；
仍須以實際 HTTP 測試舊 key 作 apikey、以及配新 publishable key 作 Bearer，都無法讀取受保護資料。
Mac 與 Windows Worker 均須更新安裝目錄的公開金鑰；兩台已完成重建與連線核對，Windows 現場執行證據見下節。

## Windows Worker 更新與驗收

本 chat 沒有公司 Windows 執行通道；2026-10-25 已由使用者在公司 Windows 現場執行，以下保留重建流程。
在公司 repo 根目錄開 PowerShell，先確認沒有未提交工作、目前在 main；只允許 fast-forward。
有未提交工作時先具名保留，完成 Worker 更新後另行比對；不要自動 stash pop 回舊版前端或設定。
這次不需重設 DPAPI 帳密；重新發布會帶入新版公開金鑰。不要只改排程狀態就視為更新成功。

```powershell
& {
    $ErrorActionPreference = 'Stop'
    git status --short --branch
    if ($LASTEXITCODE -ne 0) { throw '請先進入專案根目錄。' }
    if ((git branch --show-current).Trim() -ne 'main') { throw '請先確認分支。' }
    if (git status --porcelain) { throw '先保留工作並確認，再更新。' }
    git pull --ff-only origin main
    if ($LASTEXITCODE -ne 0) { throw '無法 fast-forward；保留工作並回報。' }
    $taskName = 'Invest D+ OCR Worker'
    $task = Get-ScheduledTask -TaskName $taskName
    $workerOutput = ($task.Actions | Select-Object -First 1).WorkingDirectory
    if ([string]::IsNullOrWhiteSpace($workerOutput)) { throw '無法辨識既有發布目錄。' }
    if (-not (Test-Path (Join-Path $workerOutput 'Invest.Web.exe'))) { throw '目錄沒有 Worker EXE。' }
    Disable-ScheduledTask -TaskName $taskName | Out-Null
    Stop-ScheduledTask -TaskName $taskName
    Start-Sleep -Seconds 2
    & .\scripts\publish-ocr-worker-windows.ps1 -OutputDirectory $workerOutput
    $settings = Get-Content (Join-Path $workerOutput 'appsettings.json') -Raw
    if ($settings -notmatch '"AnonKey"\s*:\s*"sb_publishable_') { throw '缺少新公開金鑰，保持停止。' }
    Enable-ScheduledTask -TaskName $taskName | Out-Null
    Start-ScheduledTask -TaskName $taskName
}
```

預期新 log 含「AI OCR v5」及「在線詢問：指名回應」，並能重新登入、送出心跳。
若 publish 失敗，保持停止以免誤用半成品；回報失敗步驟、exit code 與移除機密後的錯誤，
不要提供 DPAPI 檔、密碼、token 或整份 appsettings。自訂 Worker 發布目錄者須沿用既有路徑。
