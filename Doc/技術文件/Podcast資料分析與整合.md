## 一、執行摘要

目前使用者已完成：

```text
NotebookLM／Podcast 音檔分析
  → 透過對話整理出投資結論
```

接下來要解決的不是再次分析音檔，而是把已產生的結論轉成可長期使用的資料：

```text
分析結論
  → 結構化研究文件
  → 驗證與人工核准
  → 資料庫持久化
  → 網站「筆記 > 股癌」
  → 與族群、題材、個股及熱度資料交叉顯示
```

本次討論形成的核心結論如下：

1. UI 不新增最上層「研究」頁籤，保留既有「筆記」主頁籤。
2. 第一版直接新增第二層子頁籤：`我的筆記｜股癌`。
3. 「股癌」是導覽分類；底層資料不可直接混入目前的通用 `notes` 資料表。
4. NotebookLM 個人版不應依靠瀏覽器自動化作正式串接。自動化主線建議為 `GitHub Actions → Gemini API → JSON Schema 驗證 → Database`。
5. Claude Code 與 Codex 只需擇一作為開發／例外處理代理，不應同時成為核心資料管線的必要依賴。
6. Podcast 內容第一階段只作為研究脈絡，不改變目前族群熱度排行；研究權重維持 `0`。
7. 本次只建立 UI 比較原型，尚未修改正式網站或正式資料庫。

## 三、既有網站與筆記功能現況

### 3.1 網站架構

目前 `/admin888/` 是由 .NET 專案匯出的靜態 HTML／JavaScript 網站，主要前端檔案為：

- `src/Invest.Web/Infrastructure/StaticSite/Assets/index.html`
- `src/Invest.Web/Infrastructure/StaticSite/Assets/site.js`
- `src/Invest.Web/Infrastructure/StaticSite/Assets/site.css`

前端以 query string 控制畫面狀態，例如 `view=notes`，資料來源則包含靜態 JSON、Supabase view 與盤中快照。

### 3.2 現有「我的筆記」

目前筆記頁已具備：

- 新增、編輯與刪除筆記。
- 類型：全部、功能、Bug、待驗證。
- 狀態：全部、待處理、處理中、待確認、已完成。
- 標題與內容搜尋。
- 圖片附件。
- 左側清單、右側編輯器。
- Supabase 持久化與每 60 秒重新讀取。

這套功能的實際語意比較接近開發工作、Bug 與驗證事項管理，不是結構化的投資研究資料。

### 3.3 關鍵資料邊界

即使「股癌」在 UI 上放進「筆記」，底層仍不應直接沿用目前的 `notes` 表，原因包括：

- 現有 `notes` 欄位無法完整表達來源、節目、集數、發布日期與版本。
- 無法表達一項結論所關聯的股票、族群、立場、重要性與證據。
- 一般筆記的編輯權限與未來會影響投資判斷的研究資料，安全等級不同。
- Podcast 結論需要保留原始分析與人工補充的界線。

因此正確原則是：

> 導覽上歸在「筆記」，資料模型上仍是獨立的研究資料。

## 四、目前確認的 UI 資訊架構

### 4.1 第一版導覽

```text
筆記
├─ 我的筆記
│  └─ 沿用現有功能、Bug、待驗證與處理狀態
└─ 股癌
   ├─ 集數清單
   ├─ 研究內容
   └─ 我的補充／待追蹤
```

選擇直接顯示「股癌」的理由：

- 完全符合使用者指定的子頁籤呈現方式。
- 現階段只有少數來源，不需要先增加「研究筆記」中介頁。
- 從筆記進入股癌只需要一次點擊。
- 未來仍可由資料中的 `source_slug` 支援其他 Podcast，不必現在先把 UI 複雜化。

### 4.2 來源增加時的擴充規則

|來源數量|建議呈現|
|---:|---|
|1–4 個|直接顯示來源子頁籤，例如 `我的筆記｜股癌｜其他節目`|
|5–8 個|保留常用來源，其餘收入 `更多 ▾`|
|8 個以上且需要跨來源研究|再評估「Podcast 資料庫」或來源選擇器|

目前不要先為尚未出現的來源增加多層導覽。

### 4.3 第二層頁籤的視覺層級

最上層網站導覽目前使用膠囊按鈕。筆記子頁籤建議改用底線式頁籤，以免上下兩排看起來像同一層：

```text
[盤中] [盤後] [族群] [自訂] [資產] [筆記]    ← 主導覽膠囊

我的筆記    股癌                                    ← 子頁籤底線
            ━━━━
```

### 4.4 股癌列表頁

頁首應包含：

- 標題「股癌」。
- 最近同步時間。
- `＋ 匯入結論`，作為目前人工流程的入口。
- 搜尋框。
- 最小必要篩選：全部、偏多、偏空、待驗證。

每一集卡片顯示：

- 集數與發布日期。
- 標題。
- 一句話結論。
- 關聯族群或個股標籤。
- 節目觀點：偏多、偏空、中性或混合。
- 結論數量與待追蹤數量。
- `閱讀` 按鈕。

第一版不需要日期區間、重要性、信心程度、證據狀態等大量篩選。資料累積後再依實際使用情況增加。

### 4.5 單集閱讀頁

內容建議固定按以下順序呈現：

1. 來源、集數、節目發布日期。
2. 標題。
3. 一句話結論。
4. 核心觀點。
5. 關聯族群與個股。
6. 催化事件。
7. 風險與反方觀點。
8. 待驗證事項。
9. 我的補充。
10. 查看原始分析／加入待追蹤。

### 4.6 原始分析與個人補充

UI 必須明確分開：

- **原始分析：** NotebookLM／Gemini 產出並經確認的版本，發布後唯讀。
- **我的補充：** 使用者後續新增的判斷、追蹤結果與修正，不覆蓋原始分析。

這個區分可避免日後無法判斷某句話究竟來自節目、模型摘要或使用者自己的判斷。

### 4.7 網址與返回狀態

建議延續現有 query string 路由：

```text
?view=notes&notesTab=my
?view=notes&notesTab=gooaye
?view=notes&notesTab=gooaye&episode=<episode-id>
```

重新整理、分享網址及瀏覽器返回時，都能保留目前的子頁籤與單集。

### 4.8 手機版

- 子頁籤維持單排；來源變多時可左右滑動。
- 集數卡片改為單欄。
- 點擊閱讀後進入全頁內容，提供「返回股癌」。
- 不在窄螢幕強塞左右雙欄。
- 搜尋與篩選上下排列。

## 六、結構化資料與持久化方向

以下為先前架構研究形成的建議，目前尚未正式實作。

### 6.1 輸入資料

將每一集整理結果輸出成版本化 `research-note.v1.json`，主要包含：

- `source.slug`、`source.name`、`source.kind`
- `episode.key`、標題、發布時間、來源網址
- 分析工具、分析時間、摘要、人工核准狀態
- 多項獨立 claim
- 每項 claim 的類型、立場、確定程度、重要性與時間範圍
- 關聯 ticker、topic 與 direct／indirect／mentioned 關係
- 可選的時間碼與短證據摘錄

### 6.2 資料庫

第一版建議新增獨立的 `research_notes` revision 文件表，不先拆成大量關聯表。核心欄位包括：

- `source_slug`
- `episode_key`
- `revision`
- `title`
- `published_at`
- `source_url`
- `document jsonb`
- `document_hash`
- `status`
- `imported_at`

重要原則：

- 相同文件重複匯入不能產生重複資料。
- 修正版新增 revision，不覆蓋舊版。
- ticker 或 topic 無法唯一對應時，阻擋寫入並要求人工處理。
- 不對匿名前端開放研究資料寫入權限。
- 不保存完整音檔或完整逐字稿，只保留必要的可追溯資訊。

### 6.3 網站讀取

不必新增常駐後端 API。可沿用既有靜態匯出流程，由 C# 從資料庫讀取最新已發布版本，產生：

```text
data/research.json
```

前端只負責呈現、篩選與依 ID 交叉連結，不在 JavaScript 內重新判讀研究內容或計算投資分數。

## 七、GitHub Actions／Claude／Codex／Gemini NotebookLM 串接結論

### 7.1 建議的正式主線

```text
Podcast 音檔或來源
  → GitHub Actions
  → Gemini API 音訊理解
  → 按 JSON Schema 產生結構化結果
  → 程式驗證
  → 人工核准
  → Supabase
  → 靜態網站匯出
```

### 7.2 各工具的合理角色

|工具|建議角色|
|---|---|
|GitHub Actions|排程、接收輸入、執行驗證、匯入、發布與保存失敗紀錄|
|Gemini API|音訊理解與結構化輸出，是主要模型處理層|
|NotebookLM／Gemini Notebook|適合人工研究與探索；個人版不作正式 API 依賴|
|Codex|修改程式、建立 schema／測試、排查失敗，或作可選的非互動代理|
|Claude Code|可扮演與 Codex相同的可選代理角色，但不需兩者同時存在於正式流程|

### 7.3 不建議的方案

不建議用 GitHub Actions、Codex 或 Claude 去操作個人版 NotebookLM 網頁介面，原因包括：

- UI、登入流程與內部端點容易改變。
- 可能遇到驗證、速率限制與無法觀測的失敗。
- Notebook 對話結果難以穩定限制成固定資料契約。
- 長期維護成本會高於直接使用 Gemini API。

若未來 Google 提供正式且支援聊天／查詢的 Notebook API，再重新評估直接串接。

## 八、與族群／題材／熱度指標的整合原則

### 8.1 第一階段：只顯示脈絡

Podcast 研究先提供：

- 某族群近期有幾項研究結論。
- 最新研究日期。
- 相關集數與一句話結論。
- 關聯個股。
- 待驗證事件。
- 從股癌內容跳回族群頁，或從族群頁跳回相關研究。

第一階段不得：

- 因 Podcast 提到某公司，就修改 Topic membership。
- 把 Podcast 結論寫入代表 MOPS 官方資訊的 `material_events`。
- 直接改變盤中或盤後族群熱度。
- 把節目觀點呈現成網站買賣訊號。

### 8.2 現行熱度保持不變

現有新聞權重實際為 0，綜合熱度約為：

\[
M = 0.705882F + 0.294118B
\]

其中 `F` 為資金熱度，`B` 為廣度。第一版研究權重 `w_R=0`，不改現有排行。

### 8.3 後續才評估研究注意力

至少累積約 20–30 集或六個月資料後，才能評估獨立的 Research Attention 指標。即使建立，也應先獨立呈現並進行去重、來源偏差、族群大小偏差與時間衰減校正，不應直接覆蓋既有 `CompositeScore`。

## 九、建議實作順序

### Phase 0：確認 UI

- 確認採用 `我的筆記｜股癌`。
- 確認卡片欄位與單集內容順序。

- 加入筆記子頁籤狀態。
- 將現有筆記完整放進「我的筆記」。
- 建立股癌列表、閱讀頁、空狀態、載入失敗與手機版。
- 使用固定示意 JSON 驗證操作。

### Phase 2：建立研究資料契約與匯入器

- 定義 `research-note.v1`。
- 驗證必要欄位、enum、股票與族群對應。
- 先提供 dry-run，再允許 apply。

### Phase 3：資料庫與靜態投影

- 新增 revisioned `research_notes`。
- 輸出 `data/research.json`。
- 接入現有 cache-bust 與 GitHub Pages 發布。

### Phase 4：人工匯入流程

- 讓 `＋ 匯入結論` 接受目前已整理完成的資料。
- 匯入前預覽、驗證與人工確認。
- 原始分析發布後唯讀，個人補充獨立保存。

- 以 GitHub Actions 呼叫 Gemini API。
- 產生同一份 `research-note.v1`。
- 驗證失敗進人工審核，不直接污染正式資料。

### Phase 6：族群與個股交叉連結

- 在研究中顯示對應族群的當期市場資料。

### Phase 7：研究指標實驗

- 累積足夠資料後再離線回測。
- 通過書面驗收門檻後，才評估 `CompositeV2`。

## 十一、尚未確認的決策

下一次討論需要依優先順序確認：

1. `股癌` 子頁籤是否就是正式名稱，或要顯示節目全名／Logo。
2. 第一版是否需要 `＋ 匯入結論` UI，或只接受 GitHub／CLI 匯入。
3. 人工匯入接受結構化 JSON、Markdown，還是貼上一般文字後再轉換。
4. 原始分析內容是否可公開出現在 GitHub Pages。
5. 是否保存短證據摘錄與時間碼；是否完全不保存逐字稿。
6. 「我的補充」需要自由文字，還是同樣結構化成催化、風險與待驗證。

## 十二、風險與殘酷真相

1. **最難的不是把文字塞進資料庫，而是保留它的來源與可信程度。** 若沒有來源、版本、證據及人工核准，資料愈多只會讓錯誤看起來愈權威。
2. **Podcast 提及量不等於市場熱度。** 它最多先代表研究注意力，不能直接與成交資金及市場廣度混為一談。
3. **UI 放在筆記底下，不代表可以偷用現有 notes 表。** 導覽歸類與資料責任是兩回事。
4. **`/admin888/` 的隱藏網址不是安全登入。** 只要輸出成靜態 JSON，就應先視為可能公開讀取。
5. **同時把 GitHub Actions、NotebookLM、Gemini、Claude 與 Codex 全塞入正式流程，不會更智慧，只會增加故障點。** 核心管線保持 deterministic，模型代理只處理必要環節。
6. **現在就為十個 Podcast 設計三層導覽是過度設計。** 第一版先讓「我的筆記｜股癌」真的可用，再由真實資料量決定何時擴充。
