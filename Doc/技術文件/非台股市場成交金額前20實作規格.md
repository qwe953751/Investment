## 0. 決策前提、資料源評估與公開展示邊界

使用者已明確裁示：**先不管條款，先做出可以運作的東西，備案另尋。**

因此本規格採用 Yahoo Finance 的未公開 screener endpoint。這個選擇的授權風險尚未解決：
Yahoo 一般服務條款並未授權未經允許的複製、散布或衍生使用；Yahoo Finance 行情又包含多家
第三方資料供應商，其中部分內容另有明確禁止快取或再散布的限制。現有公開文件不足以證明
本案已取得 screener 排行的公開展示與再散布權。原始評估曾否決這類來源；這裡是
**在知情的前提下刻意接受風險**，
不是遺漏。接手者不需要再重新評估一次條款，也不要因為條款疑慮就自行改用別的來源或停工；
但**也不要在程式或文件裡宣稱本方案已取得授權**。

另外一個必須知道的事實：專案**現在就已經在用 Yahoo Finance** 供應美股四大指數、11 大類股 ETF、
加密貨幣、日經與 KOSPI（`YahooFinanceDailyQuoteClient`／`YahooFinanceIntradayQuoteClient`），
且結果已寫入公開的 `data/market-overview.json`。本規格沒有引入新的風險類別，只是沿用同一條。

### 0.1 原始需求與評估標準

本功能的原始限制是：美股只要盤後；日股／韓股要盤中與盤後；不付費；多裝置不能直接打來源
或放大 Supabase 流量；排行必須是全市場原幣成交金額前 20，不能以固定觀察名單、指數、產業代表
或單純成交量排行代替。資料不足、來源錯誤或品質證明不成立時，必須保留既有完整快照或顯示無資料，
不得補造排行。

理想 API 還必須同時滿足：

1. 免費提供需要的市場與時段；
2. 能取得完整候選集合或可證明等價的前 20，而不是只回成交量／交易筆數前 20；
3. 允許 derived ranking；
4. 允許公開網站、公開 `data` branch、public Storage bucket 或 CDN 向帳號持有人以外的人展示；
5. 條款明確涵蓋非商用親友使用，而不是只允許本人在私人裝置上使用。

截至 2026-09-15 的官方資料查核，沒有找到同時滿足以上全部條件的免費 API。這也是為何目前
Yahoo screener 只能被記為「使用者知情接受的運作方案」，不能被記為「已確認授權的免費來源」。

### 0.2 非商用、登入與公開 CDN 不會自動排除再散布問題

正式網站位於公開 GitHub Pages。即使實際使用者主要是本人、家人與朋友，只要其他人能取得行情，
就不能直接視為 API 帳號持有人的私人使用。下列行為都可能落入第三方展示或再散布範圍：

- 將來源回應加工成排行後放在公開網頁；
- 將 JSON 寫入公開 `data` branch；
- 將盤中排行放入 public Supabase Storage bucket 或 CDN；
- 改成登入後才顯示，但仍讓家人、朋友等其他使用者存取。

登入只是在技術上限制觀看者，不能取代來源授權；「沒有收費」也不等於自動獲得再散布權。
`MarketTurnoverCdn:Public=true` 只代表專案開啟公開傳輸，**不代表資料供應商授權已成立**。

most-actives 同樣只按 volume 或 trades 排名。Twelve Data 的個人方案則直接卡在再散布條款。

### 0.4 不能採用的近似與繞路

- **成交量前 20 × 價格：**只能得到成交量候選中的金額排序，不等價於全市場排行。本案的 Yahoo
  實作必須同時取量軸與價軸候選，並通過 §4.4 的 `bound < cutoff` 證明。
- **瀏覽器直呼免費 API：**會暴露金鑰、讓每台裝置重複消耗配額、造成不同裝置資料不一致，且完全
  不能解決再散布問題。
- **改成登入後顯示：**家人與朋友仍是第三方使用者；來源未明確允許封閉群組展示時，不能把登入
  當成授權替代品。
- **抓 Yahoo、交易所網站或其他未文件化 endpoint 再公開：**端點可能變更、封鎖或回 429，也不會
  因為資料是免費取得就自動取得公開展示權。現在使用 Yahoo 是使用者明確接受的風險例外。

## 3. 工項 A（P0）：讓未上線功能停止擋住已上線功能

## 4. 工項 B：新來源 `YahooScreenerMarketTurnoverClient`

新增檔案：`src/Invest.Web/Infrastructure/MarketData/Turnover/YahooScreenerMarketTurnoverClient.cs`

### 4.1 取得 cookie 與 crumb（必要，不可略過）

Yahoo screener 需要一組 cookie ＋ crumb，兩者缺一就回 `Unauthorized`。

```
步驟 1：GET https://fc.yahoo.com
        → 預期 HTTP 404，這是正常的；目的只是讓回應的 Set-Cookie 寫入 CookieContainer
        → 必須取得 .yahoo.com 網域的 A3 cookie
步驟 2：GET https://query1.finance.yahoo.com/v1/test/getcrumb
        → 帶上步驟 1 的 cookie
        → 回傳純文字 crumb，例如 tJ.8wope7I4
```

實作要點：
- `HttpClientHandler { CookieContainer = new(), UseCookies = true }`，或用 `IHttpClientFactory`
  註冊一個帶 `CookieContainer` 的 named client。
- **步驟 1 的 404 不可視為失敗**，只有「拿不到 cookie」才算失敗。
- 每次 collect 開始時取一次 crumb，整輪重用；收到 `Unauthorized` 時重取一次，再失敗才放棄。
- `User-Agent` 必須是一般瀏覽器字串，不能是預設的 .NET UA。

已實測：無 cookie 時 `getcrumb` 回
`{"finance":{"result":null,"error":{"code":"Unauthorized",...}}}`；有 cookie 時正常回 crumb。

### 4.4 演算法：雙軸候選池 ＋ 可證明的截斷

不能只抓「成交量前 N 檔再乘價格」——那會漏掉高價低量股，本文件 §0.4 已經點名這是錯的。
但也不需要把 20,175 檔全抓下來。正確做法是**抓兩個軸的極端值，然後證明沒抓到的不可能進前 20**：

```
1. 沿 sortField=dayvolume     DESC 分頁抓 N 頁 → 集合 A
2. 沿 sortField=intradayprice DESC 分頁抓 M 頁 → 集合 B
3. 候選池 = A ∪ B（用 symbol 去重）
4. 對候選池每一檔算 turnover = price × volume，由大到小取前 20
5. 安全性證明：
       V_min = A 之中最小的 volume
       P_min = B 之中最小的 price
       任何不在候選池的標的，volume < V_min 且 price < P_min
       → 它的 turnover < V_min × P_min =: bound
   若 bound < 第 20 名的 turnover，則這份前 20 與掃描全市場的結果完全相同。
6. 若 bound ≥ 第 20 名 turnover，加深 N 與 M 重跑；連續加深仍不成立就視為失敗，
   不得發布（見 §7）。
```

這一步是本規格的核心，**必須實作，而且 `bound < cutoff` 要當成硬性品質門檻**，
不能只當 log。使用者的既有規則是「排行榜要全市場算，不能只取前 N 檔」；
這個證明就是滿足該規則的方式——結果與全市場掃描等價，且可驗證。

建議起始頁數（已實測足夠，留有數百倍餘裕）：

| market | N（量軸頁數） | M（價軸頁數） | 請求數 |
|---|---|---|---|
| us | 12 | 2 | 14 |
| jp | 8 | 2 | 10 |
| kr | 8 | 2 | 10 |

每次請求之間 sleep 250ms。整輪三個市場約 34 次請求。

### 4.5 實測結果（2026-09-18，此演算法的實際輸出）

| market | 候選池 | 未掃到者上限 `bound` | 第 20 名 turnover | 安全 |
|---|---|---|---|---|
| us | 3,304（量 2,988 ∪ 價 486） | 0 USD | 2,091,969,357 USD | ✅ |
| jp | 2,180（量 2,000 ∪ 價 500） | 147,171,200 JPY | 74,640,646,500 JPY | ✅ 約 500 倍餘裕 |
| kr | 2,094（量 1,996 ∪ 價 500） | 0 KRW | 208,618,331,000 KRW | ✅ |

### 4.6 精度：必須誠實標示

`turnover = 最新價 × 當日成交量` 是**估算值**，不等於交易所公布的成交金額
（交易所是逐筆成交金額加總）。原本的 Massive 來源用 `volume × VWAP`，比本方案準。

因此：

- `Source` 欄位固定寫 `"yahoo-screener"`，不要寫成交易所名稱。
- 前端顯示成交金額的區塊要標示「估算值，依最新價×成交量計算」與資料延遲。
- **不要**把這個數字拿去跟台股的真實成交金額做同一套比較或加總。

可選的精度改善（不是必要工項）：對前 60 名候選另外呼叫 chart API 取當日
`(high + low + close) / 3` 當 VWAP 近似值重算。成本約 60 次請求。**第一版不要做**，
先讓功能上線。

## 7. 品質門檻與失敗行為

`MarketTurnoverQualityGate.EnsureComplete` 既有的四項檢查全部保留：
至少 20 列、代號不重複、名次 1..N 連續、金額與代號有效。

**新增第五項**：§4.4 的截斷證明 `bound < 第20名 turnover`。不成立就丟
`MarketTurnoverDataIncompleteException`，該市場算失敗。

失敗時的行為（重要，跟工項 A 是同一個原則）：

- 單一市場失敗 → 其餘市場照常發布；失敗市場**保留既有快照**，不發布部分資料。
- 前端在缺資料時維持現有文案：「目前快照尚未提供成交金額前 20；未以指數或產業代表標的代替。」
  （`site.js` 約 L26619）**不要**加入示意資料或回退到舊排行冒充當日。
- 全部市場失敗 → 指令仍 exit 0（見工項 A），但要留下清楚的 warning。

## 11. 已知限制

1. **授權**：見 §0。這是刻意接受的風險；TradingView 與正式書面授權備案見 §0.5～§0.6。
2. **精度**：成交金額是 `最新價 × 成交量` 估算值，非交易所公布值（§4.6）。
3. **沒有 SLA**：Yahoo 未公開端點隨時可能變更、擋 IP 或回 429。既有的
   `MarketOverview` 路徑就曾遇過 429。失敗時的行為已在 §7 定義，不要加重試風暴。
4. **cookie/crumb 機制可能改變**：這是最脆弱的一環。若哪天 `getcrumb` 開始要求
   JS 驗證（Stooq 今年就是這樣掛掉的），本方案會整個失效，屆時只能走備案。
5. **歷史回補做不到**：screener 只回傳「當下」的報價，沒有歷史交易日參數。
   所以排行只能從上線日開始往前累積，**無法回補過去兩年**。
   這點與既有 `market-overview` 的日期選擇器行為不同，前端的排行日期選擇器
   只能提供已累積的日子。
