## 五個自動流程

| Workflow | 何時跑 | 狀態 |
|---|---|---|
| `daily-snapshot.yml` | 交易日 16:07 進場、18:00 開抓 | 全綠（2026-08-17 首次） |
| `intraday.yml` | 交易日 07:33 進場，跑到 13:35 | 全綠 |
| `restore-test.yml` | 週日 08:00 | 有在跑 |
| `revenue.yml` | 每月 1–10 日每 2 小時、11 日後每天 19:00 | 新上線，等第一次排程 |
| `turnover-audit.yml` | 交易日 08:11 進場，跑到 13:35 | **暫時的**，收滿 6 個完整交易日就刪 |

`intraday.yml` 原本排 07:03，**每天都收不到收盤那幾分鐘**：
GitHub 對單一 job 有六小時硬上限，時間到直接 cancel，`timeout-minutes` 設多大都沒用。
07:03 排程、實際約 07:30 開跑，上限就落在 13:30～13:34，正好把收盤吃掉——
08-19、08-20、08-21 連三天都是 `cancelled`、歷時 6:00:1x。改排 07:33，上限推到 14:00 才解掉。
排程本身是盡力而為（實測誤點 28～31 分鐘、最糟 88 分鐘），所以另一頭也要留：
07:33 就算誤點 87 分鐘也還在 09:00 開盤前開跑。

`turnover-audit.yml` 是為了 [TODO 9](../TODO.md) 開的**暫時**工作：
每 5 分鐘同時問 MIS 與玩股網，把兩邊的成交金額差異寫進 Supabase，
用來確認換掉盤中成交值來源之前那個來源整場撐不撐得住。
它**不動任何現有行為**，前端也不讀它的表。
收滿 `TurnoverAuditStore.RequiredDays`（6 個完整交易日）、盤中來源換好之後，
連同 `db/011_turnover_audit.sql`、`Infrastructure/TurnoverAudit/`、`TurnoverAuditTests.cs`
與 `Program.cs` 的 `turnover-audit` 指令一起刪掉；那支 SQL 的檔頭有刪表的指令。
進度看 `dotnet run --project src/Invest.Web -- turnover-audit`（不加 `--loop`）。

## 踩過並且已經解掉的坑

這一節是給另一台裝置的：這些問題**已經修好了**，
但如果之後看到類似症狀，先回頭看這裡，不要重新debug一遍。

| 症狀 | 真正的原因 | 怎麼解的 |
|---|---|---|
| 排程說 18:00 卻 18:31 才動 | GitHub cron 是盡力而為，實測誤點 31（盤後）與 88（盤中）分鐘 | 提早排在非整點非半點卡住 runner，程式自己睡到目標時間 |
| 國定假日整條線紅燈 | 休市與「還沒公布」從 API 看起來一模一樣，都是空的 | 接官方休市日曆，**只用於降級** |
| 休市日曆把交易日判成休市 | 那份清單混著「春節前最後交易日」這種**照常開市**的日子 | 過濾掉名稱含「交易日」的列；拿 320 天快取交叉驗證過，零誤判 |
| 成交值跟玩股網差很多 | 官方成交金額含零股、盤後定價、鉅額交易 | 另抓七份報表逐檔扣除；台積電單日差過 59 億，足以改名次 |

| 匯出的整包撐不住 | 資料檔連顯示文字都先算好，單檔快 1 MB | 只留數字、顯示格式交給前端，單檔剩四分之一 |
