## 排程 Action

目前有 5 條會自動重複執行的 GitHub Actions，涵蓋台股盤中／盤後、美股、月營收、備份還原測試。
`intraday.yml` 跟其他四條不一樣：它不是單純的 cron，而是**自走鏈**——每一輪跑完自己呼叫
`workflow_dispatch` 排下一棒，YAML 裡的 `cron` 只是「萬一鏈斷了」的復原用火種，不是主要觸發方式
（原因見 `intraday.yml` 檔頭「為什麼是自走鏈而不是排程」一節：GitHub 原生 cron 實測誤點過
6～13 小時甚至完全沒觸發）。

| Workflow | 觸發方式 | 實際執行時間（台北） | 做什麼 |
|---|---|---|---|
| `intraday.yml`（台股盤中） | 自走鏈：每輪完成後自己叫下一輪；cron 只是斷鏈時的復原備援 | 交易日 08:40～13:35，每約 2 分鐘一輪 | 抓盤中報價寫 Supabase；18:00 後若當天 `daily-snapshot.yml` 還沒成功會自動叫醒它；另一個 job 監看盤中 CDN（Supabase Storage）健康度，掉回資料庫直連會發警報 |

## 踩過並且已經解掉的坑

這一節是給另一台裝置的：這些問題**已經修好了**，
但如果之後看到類似症狀，先回頭看這裡，不要重新debug一遍。

| 症狀 | 真正的原因 | 怎麼解的 |
|---|---|---|
| 排程說 18:00 卻 18:31 才動 | GitHub cron 是盡力而為，實測誤點 31（盤後）與 88（盤中）分鐘 | 提早排在非整點非半點卡住 runner，程式自己睡到目標時間 |
| 盤後整天沒更新，`imports/` 停在上一個交易日，Actions 看起來也「有跑而且成功」（2026-08-31） | 當天 cron 一發都沒送到，補位的 18:00 鬧鐘又只看 run 的 `conclusion`。`publish-only=true` 的純發布會跳過「回補行情」但 run 一樣 `success`，白天用 AI agent 發布過網站就會讓鬧鐘判定「今天已經收過盤後」 | 鬧鐘改看**步驟層級**：逐一翻開當天的 run，確認「回補行情」這一步真的 `success` 過。**run 成功不等於資料進來了**，判斷完成度要看做事的那一步，不是 run 的結論 |
| 國定假日整條線紅燈 | 休市與「還沒公布」從 API 看起來一模一樣，都是空的 | 接官方休市日曆，**只用於降級** |
| 休市日曆把交易日判成休市 | 那份清單混著「春節前最後交易日」這種**照常開市**的日子 | 過濾掉名稱含「交易日」的列；拿 320 天快取交叉驗證過，零誤判 |
| 成交值跟玩股網差很多 | 官方成交金額含零股、盤後定價、鉅額交易 | 另抓七份報表逐檔扣除；台積電單日差過 59 億，足以改名次 |
| 盤中收集器整天沒寫入卻不報錯 | HTTP timeout 太短，個股清單抓不到就整場停擺 | 加長 timeout 並補上清單備援 |
| 手機看到的還是舊資料 | Pages 快取十分鐘且無法改標頭 | 網址帶 `?v=發佈時間`，`manifest.json` 用 `no-store` 讀 |
| 匯出的整包撐不住 | 資料檔連顯示文字都先算好，單檔快 1 MB | 只留數字、顯示格式交給前端，單檔剩四分之一 |
| `pg_dump: server version mismatch` | runner 內建 16，Supabase 是 17.6，版本不合直接 exit 1 | 掛上 pgdg 套件庫裝 17 |
