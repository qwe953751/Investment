## 排程 Action

目前有 5 條會自動重複執行的 GitHub Actions，涵蓋台股盤中／盤後、美股、月營收、備份還原測試。
`intraday.yml` 跟其他四條不一樣：它不是單純的 cron，而是**自走鏈**——每一輪跑完自己呼叫
`workflow_dispatch` 排下一棒，YAML 裡的 `cron` 只是「萬一鏈斷了」的復原用火種，不是主要觸發方式
（原因見 `intraday.yml` 檔頭「為什麼是自走鏈而不是排程」一節：GitHub 原生 cron 實測誤點過
6～13 小時甚至完全沒觸發）。

|---|---|---|---|

### 截圖 OCR 自動填表

流程是「上傳券商未實現損益截圖 → 瀏覽器內辨識 → 自動填出校對表 → 按套用才寫進資料庫」。

- **引擎與字庫放在自己站上，不走 CDN。** tesseract.js 5.1.1 加 `chi_tra` 字庫共約 6.5 MB，
  跟著 `Assets/` 一起匯出（`tesseract.min.js`、`tesseract-worker.min.js`、
  `tesseract-core-simd-lstm.wasm.js`、`chi_tra.traineddata`）。頁面上寫著「截圖只在瀏覽器內
  辨識，不會上傳保存」，而 CDN 版的 worker 是從 jsdelivr 載進來執行的——那句話就變成
  「請相信 jsdelivr 不會碰你的財務截圖」。SRI 也蓋不住 worker 內部再去載的東西。
  多背 6.5 MB 換那句話是真的，值得。`eng` 字庫沒收，台股截圖用不到。
- 核心用**自帶 wasm 的 `tesseract-core-simd-lstm.wasm.js`**，不是小一 MB 的分開版。
  分開版在這裡會**無聲當在「準備辨識…」**：tesseract.js 的 worker 是 blob URL 起來的，
  emscripten 的 `scriptDirectory` 因此解不出旁邊那個 `.wasm`，瀏覽器沒有任何錯誤訊息。
  一 MB 不值得換一個查半天的當機。
- **欄位對應靠讀標題列，不靠位置猜。** OCR 會把中文標題拆成一個字一個 word
  （「成」「本」「價」各自一個），所以是把整列的字攤平、依 x 座標內插出每個字的位置，
  再用關鍵字長的優先比對。認不出標題列時**只填代號與名稱**，並明講原因——
  位置猜錯會把市值寫進成本欄，而且看起來完全合理。
- **「成本價」是每股單價，不是投入成本。** 直接照抄會讓一檔幾百萬的持倉顯示成幾百元。
  `costPrice`／`marketPrice` 當成偽欄位，乘上股數才寫進 `cost`／`market_value`。
- 數字解析踩到的：括號 `(1,234)` 是負數；OCR 常把千分位逗號看成句點；負號會被看成
  `~`、`一`，實測還出現過 `~-42,000` 這種前面多噴一個符號的。所以是「一串符號後面
  直接接數字」才當負數，`2330~2340` 這種範圍寫法不會被誤翻。
- 辨識期間只更新一行進度文字，不重畫整張校對表——進度每秒跳好幾次，重畫會把使用者
  剛打的字吃掉。第一次跑要載 6 MB，沒有那行字會像當掉。
- 實測：明暗兩種佈景、單價欄與總額欄兩種版面、以及沒有標題列的截圖各跑一次都正確；
  接真實 Supabase 從上傳到「已套用 2 筆持倉」全程走通，驗證用的假資料已刪乾淨
  （三張表都確認回到 0 列）。
