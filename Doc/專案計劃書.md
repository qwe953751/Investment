## 一句話

個人使用的台股研究網頁：找出**哪些標的正在吸收市場的成交值**，
每天自動更新，手機隨時打得開。

## 要解決什麼問題

看盤軟體給的是「今天成交值前幾名」，那份名單幾乎天天一樣——
台積電、鴻海、聯發科永遠在最上面，看不出**變化**。

真正想知道的是：

- 相較於前一段時間，**誰的成交值突然放大了**（資金開始進來）
- 一檔股票在**全市場**成交值裡佔的比重是往上還是往下（不受大盤整體量能影響）
- 盤中走到現在，這檔的市場佔比跟它平常的水準比起來是高還是低

這三件事都需要「本期 vs 前期」的比較，而不是單日排名，
所以必須自己留歷史行情、自己算。

## 誰在用、怎麼用

只有一個使用者（專案擁有者）。兩種使用情境：

| 情境 | 裝置 | 需要什麼 |
|---|---|---|
| 盤後看昨天發生了什麼 | 手機為主 | 打開網址就有最新資料，不必開電腦 |
| 盤中看今天正在發生什麼 | 手機或電腦 | 每 5 分鐘更新的累計成交額與市場佔比 |

「不必開電腦」是硬需求，直接決定了整個架構：
資料收集必須跑在雲端，畫面必須是靜態網站。

## 範圍

### 要做

- 台股上市＋上櫃**一般股票**的成交值排行（代號四位數字、不以 0 開頭）
- 盤後：本期 vs 前期的成交值、增減率、市場成交比、排名變化、期間漲跌
- 盤中：當日累計成交額、市場成交比、跟過去 N 日的比較、預估收盤
- 交易限制標記（處置、全額交割），提醒這一列的名次不能照字面讀
- 每個交易日自動更新，不需要人工介入
- 資料可追溯：每個數字都算得回原始行情

### 明確不做

| 不做 | 為什麼 |
|---|---|
| 下單、串接券商 | 這是研究工具，不碰錢 |
| 投資建議、買賣訊號 | 工具只呈現事實，判斷由人做 |
| 即時逐筆報價 | 5 分鐘一輪夠用，逐筆的成本與複雜度不成比例 |
| 技術指標（KD、MACD 等） | 看盤軟體已經做得很好，重做沒有意義 |
| 多使用者、開放註冊 | 只有一個人用；未來若要分享才談白名單（TODO 5） |
| ETF、權證、特別股 | 它們的成交值邏輯跟一般股票不同，混在一起排名沒有意義 |

## 設計原則

優先順序（衝突時照這個順序讓步）：

```
計算正確 > 資料可追溯 > 歷史結果穩定 > UI 可查詢 > 視覺效果
```

四條具體規則：

1. **行情資料只增不減。** 任何會刪掉既有交易日的動作都要先確認。
   官方 API 一次只給一天，漏掉的日子補回來的成本很高，某些情況下補不回來。
2. **公式只有一份。** 所有指標都在 C# 算，前端只做篩選、排序、套顯示格式。
   靜態網站的資料檔直接由同一個 `TradingValueRankingQueryService` 產出。
3. **歷史結果必須穩定。** 日後接上族群分類時，改今天的族群成分股
   不可以讓過去幾個月的排名跟著變。
4. **判斷錯了寧可紅燈。** 例如分不清「休市」與「還沒公布」時，一律當成還沒公布繼續重試——
   誤判成休市那一天就永遠補不回來，多一個紅燈只是多看一眼。

## 系統組成

```
證交所 / 櫃買中心 / MIS          官方資料來源
        │
        ├── 盤後收盤行情 ──► data 分支 imports/*.json   ← 盤後行情的權威
        │                          │
        │                          └──► Supabase（查詢副本，300 個交易日）
        │
        └── 盤中 5 分鐘報價 ──────────► Supabase（原生資料，每天重來）
                                       │
                                       ├──► 靜態網站 ──► gh-pages ──► 手機
                                       └──► 盤中頁直接讀（anon key，唯讀）
```

四層各自的角色與保留期在 [README.md](../README.md#資料放在哪裡)。
關鍵是**正確性的順序是 交易所 → imports → Supabase**：
兩邊對不起來時以 `imports` 為準，復原盤後行情一律從 `imports` 重灌，不從備份還原。

## 為什麼是這個架構

| 決策 | 選了什麼 | 為什麼 | 代價 |
|---|---|---|---|
| 畫面怎麼給手機看 | 預先算好的**靜態網站** | Blazor Interactive Server 每點一次按鈕都要回伺服器，本機不開就沒畫面 | 每次改資料都要重新匯出發佈 |
| 誰來跑每天的收集 | **GitHub Actions** | 公開 repo 不計費，不必養機器，也不必讓 Mac 每天開機 | 排程是盡力而為，實測誤點過 88 分鐘 |
| 行情快取放哪 | 同 repo 的 **`data` 分支** | 每天只需下載新增的那一天；不放 `main` 是因為它每天都在長，會讓 clone 越來越重 | 多一次 checkout |
| 資料庫 | **Supabase**（PostgreSQL 17） | 免費額度夠、有 RLS 可以安全地把 anon key 發到瀏覽器 | 免費專案閒置會被暫停 |
| 專案切分 | **單一 Solution、單一 Web Project**，用 `Features/` 分功能 | 一個人維護，多 `.csproj` 只是增加編譯與引用的麻煩 | 目錄紀律要自己守 |
| 資料表怎麼建 | `db/*.sql` 依編號手動貼，走 **Management API** | `invest_writer` 不該有 DDL 權限，給了等於讓 CI 能改結構 | 多一份 token 要顧到期 |
| 靜態站怎麼破快取 | 網址帶 `?v=發佈時間` | GitHub Pages 快取十分鐘且無法改標頭 | 每次發佈都要改寫 `index.html` |
| 排程時間定義在哪 | C# 的 `CollectionSchedule`，寫進 `manifest.json` | 前端也要知道這些時間，抄第二份就會漏改 | cron 讀不到 C#，只能靠註解指回來（TODO 8 未決） |

## 階段規劃

**階段一：計算引擎與互動網頁** — 已完成。
真實行情、公式有測試釘住、Blazor 互動頁可查詢。

**階段二：自動化與手機可看** — 已完成。
靜態網站輸出、GitHub Actions 每日自動更新、Supabase 同步、備份與還原測試。

**階段三：盤中** — 已完成主體，還在調整。
5 分鐘收集、盤中排行、跟過去期間對照。
成交額預估的分母還是線性時間比例，換成量能曲線 `f(t)` 在等資料（TODO 1）。

**階段四：族群分類** — 未開始（TODO 3）。
從 Google Sheets 讀族群定義，讓排行可以按族群聚合。
這一階段會第一次出現「資料庫裡有、行情裡沒有」的原生資料，
歷史結果穩定原則在這裡才真正被考驗。

**階段五：多人可看** — 未開始（TODO 5）。
Google 登入 + 白名單。只有真的要分享給別人才做。

階段順序不是承諾。這個專案的做法是**需求出現才蓋**，
不預先蓋還沒用到的東西——所以上面每一階段的內容都可能被之後的實際需要改寫。

## 每天的自動節奏

| 台北時間 | 誰 | 做什麼 |
|---|---|---|
| 07:03 | `intraday.yml` | 卡住 runner，等開盤 |
| 07:00 起 | 收集器 | 每 5 分鐘寫一輪報價（盤前 MIS 給的是上一個交易日，認得出來） |
| 13:35 | 收集器 | 收工 |
| 16:07 | `daily-snapshot.yml` | 卡住 runner，睡到 18:00 |
| 18:00 | 盤後流程 | 回補 → 同步 → 對帳 → 備份 → 匯出 → 發佈 → 心跳 |
| 最晚 21:00 | 盤後流程 | 抓不到今天的行情就每 10 分鐘重試，撐到 21:00 才放棄 |
| 週日 08:00 | `restore-test.yml` | 把最新備份真的還原一次到臨時容器 |

排程一律**提早卡住 runner、再由程式自己等到該動的時間**。
直接排 18:00 會變成 18:31 才動，因為 GitHub 的 cron 是盡力而為。

## 成本

| 項目 | 費用 |
|---|---|
| GitHub Actions（公開 repo） | 0 |
| GitHub Pages | 0 |
| Supabase 免費專案 | 0 |
| 行情資料 | 0（證交所與櫃買中心公開 API） |

全部為零是刻意的：這是個人工具，只要開始付月費就會有「值不值得」的壓力。
代價是每一層都有免費額度的限制，例如 Supabase 閒置會被暫停、Pages 快取改不了標頭。

## 風險與已知弱點

| 風險 | 現在怎麼擋 |
|---|---|
| 官方 API 改格式或擋爬 | 每次請求帶 `User-Agent` 與 3 秒延遲；抓不到會重試到 21:00；紅燈會留線索在 job summary |
| 排程被 GitHub 自動停用（公開 repo 閒置 60 天） | `data/STATUS.md` 的心跳日期停住就看得出來，這是唯一的偵測方式 |
| Supabase 專案被暫停或密碼變更 | 同步／對帳／心跳會紅燈；盤後行情的權威在 `imports`，重灌得回來 |
| 備份看起來像 SQL 但還原不了 | 每週真的還原一次到臨時容器，並檢查行情表是不是空的 |
| `imports` 與資料庫算出來的數字不一致 | 每天 `verify` 逐日比對檔數與總和，不符就紅燈 |
| 誤判休市導致某天永遠補不回來 | 只有官方休市日曆明講不開市才敢判定，日曆讀不到就繼續重試 |
| Management API token 到期（約 2026-09-15） | TODO 6 追蹤；到期只影響貼新的 `db/*.sql`，不影響日常運作 |

最大的單點是**只有一個人知道這套怎麼運作**。
這也是這幾份文件存在的理由。

## 驗收標準

一個交易日算是成功，需要同時成立：

1. `data` 分支有當天的 `imports/yyyy-MM-dd.json`
2. `verify` 沒有回報不符
3. `data/snapshots/` 有當天的備份
4. `https://qwe953751.github.io/Investment/` 上的「資料截至」是當天
5. `data/STATUS.md` 的心跳日期是當天
6. `dotnet test` 全綠

第 4 項是使用者真正在意的那一項，其他五項是為了讓第 4 項可信。
