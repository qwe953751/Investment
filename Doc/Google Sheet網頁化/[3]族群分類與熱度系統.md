## 2. 主題與最終目標

本功能不是單純建立「公司產業別」，而是要在既有 TradingValueRanking 上增加一套可追溯的族群歸因系統，用來回答：

1. 一檔股票長期屬於哪些供應鏈或固定族群？
2. 市場目前正在用什麼題材交易這檔股票？
3. 這個題材近期受到哪些催化事件推動？
4. 相關族群是否真的獲得成交值與族群廣度確認？
5. AI如何自動分類、更新，人工又如何修正與鎖定？

系統核心由四個互相分離、但可交叉連結的概念組成：

- 固定族群／供應鏈：公司實際做什麼。
- 當前題材：市場目前用什麼理由交易它。
- 催化事件：為什麼題材現在發動。
- 市場熱度：資金是否真的進入族群。

## 3. 既有 TradingValueRanking

### 3.1 已確認規格

- 統計期間：1／5／10／20個交易日。
- 每日先取上市櫃成交值前50名個股。
- 1日：依當日成交值排名。
- 5／10／20日：以「個股當日市場成交占比 × 線性時間權重」累加。
- 越接近統計截止日，時間權重越高。
- 重複上榜透過每日分數自然累積。
- 族群熱度只讀取既有 TradingValueRanking 結果，不另造第二套成交值公式。
- 一檔股票可完整計入所有所屬族群，不要求各族群歸因占比合計100%。

### 3.2 專案技術原則

- .NET 10。
- 靜態網站輸出至 GitHub Pages。
- Supabase PostgreSQL＋Npgsql，不使用 SQLite。
- C# 計算服務是公式唯一來源；前端只負責篩選、排序、格式化與互動。
- 歷史結果原則上必須可追溯與可重現。
- 公開網站使用靜態快照；需要寫入的管理功能再串接後端與權限。

## 4. 使用者已確認的產品架構

### 4.1 成交值排行榜

在「股票代號／名稱」旁插入一欄：

```text
族群
```

欄位內以兩行呈現：

|股票代號／名稱|族群|
|---|---|
|某公司|PCB<br>玻纖布|
|某公司|散熱<br>AI伺服器液冷|
|某公司|半導體<br>CoWoS擴產|

顯示邏輯：

- 第一行：大題材／固定族群。
- 第二行：當前題材。
- 大題材與當前題材是兩個獨立連結。
- 點擊「PCB」跳至PCB族群。
- 點擊「玻纖布」跳至玻纖布族群。
- 滑鼠移入、鍵盤聚焦或手機點擊題材儲存格時，顯示催化事件泡泡。
- 排行主畫面維持精簡，不增加來源、信心、更新時間等大量欄位。
- 證據、判斷理由與最後更新時間放在題材詳情或事件詳情。

目前正式網站已實作「大／現」兩個題材按鈕，並能顯示「待分類／待確認」狀態。

### 4.2 族群主頁

保留四個子頁籤：

1. 族群熱度排行
2. 族群列表
3. 催化事件
4. 人工編輯

這四項全部都要做，不是互斥方案，也不是因Phase順序而刪減其中任何一項。

### 4.3 AI與人工的分工

最新且有效的決定：

- AI必須自動蒐集、判斷、分類及更新。
- AI不是只能產生候選、等待每筆人工核准。
- 有錯誤、低信心或結構衝突時，使用者再進行修正。
- 人工可以覆寫、拒絕、失效或鎖定分類。
- 不能把「AI只能建議，人工確認後才生效」當成目前需求。

合理的治理區分建議：

- 一般股票題材歸屬：AI可直接套用，並留下判斷記錄。
- 合併節點、刪除節點、搬移整個分支等高影響結構操作：顯示影響範圍後再執行，避免一次改動大量股票及歷史資料。

後者是設計建議，尚未由使用者最終拍板。

## 5. 族群熱度排行

### 5.1 綜合熱度公式

使用者同意保留：

\[
綜合熱度
=60\%\times資金熱度
+25\%\times族群廣度
+15\%\times新聞熱度
\]

但三個分數必須補上明確定義。

### 5.2 建議定義

#### 資金熱度

回答「相關股票是否真的獲得成交值資金」。

目前實作方向：

- 讀取 TradingValueRanking 中各成員股票的期間分數。
- 同族群內成員分數加總。
- 再正規化為0～100。
- 同一檔股票可完整計入所有所屬族群。
- 同一個族群內不可因多條分類路徑而重複計入同一檔股票。

目前程式將最高熱度族群正規化為100；這仍屬候選口徑，需要在UI中說明。

#### 族群廣度

回答「是整個族群擴散，還是只有少數股票拉動」。

目前候選公式：

\[
族群廣度
=50\%\times參與率
+30\%\times上漲率
+20\%\times分散度
\]

並乘上單一個股集中懲罰。

可使用指標：

- 參與率：族群中進入成交值觀察範圍的成員比例。
- 上漲率：有效成員中上漲股票比例。
- 分散度：資金是否分散在多檔股票，而非只集中於一檔。
- 單一個股懲罰：若大部分資金由單一股票貢獻，降低廣度分數。

#### 新聞熱度

回答「近期是否存在新的市場催化與討論」。

不得直接用新聞篇數計分，至少需要考慮：

- 新聞去重後的事件數。
- 事件與公司／族群的直接性。
- 來源可信度。
- 發布時間與時間衰減。
- 是否存在官方公告、法說或公司直接證據。
- 多篇文章是否只是描述同一件事件。

### 5.3 新聞尚未串接時的分數口徑

目前網站新聞權重為0，並將原本60／25依比例改為約71／29。這個做法透明，但會使新聞上線前後的分數不可直接比較。

建議同時保留：

\[
市場熱度
=70.6\%\times資金熱度
+29.4\%\times族群廣度
\]

以及：

\[
綜合熱度
=60\%\times資金熱度
+25\%\times族群廣度
+15\%\times新聞熱度
\]

- 新聞尚未完成時，正常顯示「市場熱度」。
- 「綜合熱度」標示新聞資料未完整，或暫不作跨時期比較。
- 新聞上線前後不可把不同權重版本當成同一口徑。

此為建議，尚待最終確認。

### 5.4 排行層級混合問題

目前榜單同時混入：

- 大族群：半導體、PCB、儲存。
- 子族群：記憶體、IC載板。
- 葉節點：DRAM、ABF、玻纖布。
- 市場敘事：AI、AI PC。

因成員由子節點往上繼承，容易出現：

- 儲存與記憶體數值相同。
- IC載板與ABF數值相同。
- 硬板與CCL數值相同或非常接近。

這不代表完整計數公式錯誤，而是不同層級不適合混在同一張榜單比較。

建議增加排行範圍切換：

```text
[大族群] [當前題材] [市場敘事] [全部節點]
```

|模式|內容|用途|
|---|---|---|
|大族群|伺服器、PCB、散熱、半導體、儲存|判斷主流資金方向|
|當前題材|玻纖布、液冷、CoWoS、DRAM漲價|判斷市場目前交易理由|
|市場敘事|AI、AI PC、低軌衛星|觀察跨供應鏈題材|
|全部節點|完整族群節點|研究與除錯|

這項為改版建議，尚待使用者確認。

### 5.5 族群排行點擊行為

- 族群熱度主表先列族群，不直接把所有股票全部攤開。
- 點擊族群後顯示該族群所有標的。
- 可使用右側詳情、抽屜或跳至族群列表的穩定連結。
- 使用者已明確表示資料量不是問題，因為詳細成員只在點擊後載入／顯示。

全部成員預設直接顯示，但可提供：


## 7. 催化事件／新聞資料

### 7.1 AI工作內容

- 定時取得合法新聞、重大訊息及公司公告。
- 股票名稱／代號辨識。
- 新聞去重。
- 題材與催化事件抽取。
- 判斷新聞直接性。
- 判斷關聯族群與股票。
- 舊證據時間衰減。
- 自動建立或更新事件。
- 將低信心、衝突與異常項目送至人工待處理。

### 7.2 事件與證據必須分開

- 催化事件 Event：真實世界發生的事情，例如「玻纖布供應商調漲報價」。
- 證據 Evidence：支持這個事件的新聞、公告、法說或其他來源。

同一事件可能有多篇新聞。不能直接把每篇新聞各算一次，否則新聞篇數會錯誤膨脹新聞熱度。

### 7.3 催化事件頁建議

上方篩選：

```text
[日期] [催化類型] [族群] [個股] [生效狀態] [直接性] [可信度]
```

主表：

|日期|事件|族群|狀態|資金驗證|
|---|---|---|---|---|
|08/24|玻纖布報價調漲|玻纖布、CCL|生效中|5日熱度上升|
|08/23|CoWoS擴產|先進封裝、設備|生效中|族群擴散|
|08/20|雲端客戶增加資本支出|AI伺服器|待驗證|資金集中少數股|

點擊事件後顯示：

- AI摘要。
- AI為何連結這些族群。
- 直接受惠股與一般族群成員。
- 新聞／公告來源連結。
- 去重後來源數。
- 直接性與可信度。
- 生效、衰減、失效時間。
- 事件前後1／5日族群熱度變化。
- 修正、失效、拒絕、鎖定操作。

### 7.4 事件狀態

```text
新事件 → 生效中 → 衰減中 → 已失效
              ↘ 已否決
```

歷史事件要保留，不是永久刪除；過期後不應繼續影響當前新聞熱度。

## 8. 人工編輯

### 8.1 目前問題

目前網站的「人工編輯」主要呈現修改紀錄與待處理問題，尚未形成真正的編輯流程。

人工編輯實際包含三種不同工作：

1. 處理AI例外。
2. 直接修改分類資料。
3. 查看歷史版本與稽核紀錄。

### 8.2 建議保留一個主頁籤，內部分成

```text
[待處理] [分類編輯] [版本紀錄]
```

#### 待處理

只收真正需要人工介入的例外：

- AI低可信度分類。
- 證據互相矛盾。
- 無法辨識的股票。
- 新題材尚不存在。
- 疑似重複節點。
- 過期事件仍有資金熱度。
- 人工鎖定內容被新證據挑戰。

審核卡範例：

```text
聯茂（6213）

目前：PCB → CCL
AI新增：玻纖布漲價
可信度：82%

理由：
- 公司產品與高階CCL直接相關
- 近期三筆玻纖布漲價證據
- 5日PCB資金熱度上升

影響：
- 玻纖布成員 8 → 9
- 聯茂當前題材改為「玻纖布漲價」

[接受] [修改] [拒絕] [人工鎖定]
```

#### 分類編輯

需要支援：

- 從股票或族群搜尋。
- 新增／移除股票族群關係。
- 設定主要題材。
- 設定直接、繼承或市場敘事關係。
- 修改父節點。
- 新增別名。
- 設定生效／失效日期。
- 附加來源與理由。
- 人工鎖定，避免AI自動覆蓋。

人工是否能修改「所有資料」需要再細分：

- 可以修改正式分類與狀態。
- 原始新聞／官方公告應保留原文，不直接覆寫。
- 錯誤證據以失效、否決或補充說明處理，避免破壞稽核軌跡。

#### 版本紀錄

- 依股票／族群／事件篩選。
- 顯示修改前後。
- 顯示AI或人工操作者。
- 顯示修改理由。
- 支援單筆失效或回復。
- 顯示受影響的族群成員與熱度結果。

## 9. 分類資料模型

### 9.1 題材節點

現有 Topic 模型方向正確，應保留：

- 穩定 Topic ID。
- 名稱與別名分離。
- 多個 ParentIds。
- Fixed／Narrative／Group／Ecosystem 類型。
- DirectTickers。
- NeedsReview。
- 完整 Paths。

題材重新命名時：

- Topic ID不變。
- 舊名稱轉為Alias。
- 不能用名稱作資料庫永久主鍵。

### 9.2 股票－題材關係

目前 `StockTopicLink` 主要只有 `TopicId + Ticker`，不足以支援AI、人工編輯與版本管理。

建議關聯實體至少包含：

|欄位|用途|
|---|---|
|relation_id|關聯識別碼|
|ticker|股票代號|
|topic_id|題材／族群ID|
|relation_type|直接、繼承、敘事、候選等|
|is_primary|是否為目前主要題材|
|source_id|證據或人工來源|
|confidence|AI可信度|
|effective_from|開始生效|
|effective_to|失效時間|
|status|有效、失效、否決|
|manual_lock|人工鎖定|
|revision_id|所屬版本|

### 9.3 催化事件關係

建議分表／分實體：

- `catalyst_event`
- `evidence_item`
- `event_topic`
- `event_stock`
- `classification_revision`
- `ai_decision_log`

不要把新聞文字直接塞進股票－族群關係。

## 10. 歷史版本：尚待解決的核心矛盾

目前文件存在兩種互相衝突的方向：

1. 專案原則與使用者需求：分類關係可新增、可失效、可回溯；歷史結果應穩定。
2. TODO中的方向：不建立版本表，分類改動後歷史熱度也套用最新分類。

若今天把某股票從PCB移至散熱，而去年的PCB熱度也跟著改變，回測與歷史研究將無法重現。

建議：

- 股票－族群關係有 `effective_from`／`effective_to`。
- 每次熱度快照記錄 `revision_id`。
- 歷史頁預設使用當時有效的分類版本。
- 額外提供「依目前族群架構重算」模式。
- 不得因今天的人工修改，靜默改寫過去已發布結果。

這是實作人工編輯前最需要拍板的資料語意。

## 11. 權限與安全

正式人工編輯建議：

- Google登入。
- `editors` 白名單。
- Supabase Row Level Security。
- 公開網站維持唯讀。
- 寫入要求使用者已登入且位於編輯者白名單。
- URL query、前端 admin/viewer 模式只能控制UI，不是安全邊界。
- 前端不得暴露 `service_role`／secret key。

目前真正的寫入位置、資料表、OAuth整合與RLS規則尚未完成。

### 12.3 已知需要整理的結構問題

- 「導軌」同時存在根節點與「伺服器 → 伺服器代工 → 伺服器機櫃 → 滑軌/導軌」。需決定是別名、交叉關聯或保留兩個不同節點。

- 「紅字＝目前漲價題材」應轉成催化事件或動態標記，不應成為固定分類階層。
- PureStorage屬客戶／產品生態系，不等同一般固定產品分類。

## 13. 驗證與校正

- 主要題材命中率。

- 是否把新聞中提到的客戶誤判成公司實際業務。
- 是否只有單一股票上漲，卻被判斷成整個族群發動。

- 歷史資料能否重現當時分類與熱度。

- 成交值較高的100檔股票。
- 至少20個交易日。
- 每日人工標記主要題材作為標準答案。

## 15. 已明確推翻的舊結論

後續Agent不可再採用以下說法：

1. 「AI不應直接做正式分類，只能提出候選，等待人工逐筆確認。」  
   最新決策：AI直接判斷及更新，人工處理錯誤與例外。

2. 「應依Phase先後逐步決定哪些功能先不做。」  
   最新決策：四個模組全部要做；Phase只是工作拆分，不代表取消項目。

3. 「靜態網站會因完整族群資料量而無法承受。」  
   使用者已否決；資料只加在排行與點擊後的詳情，不視為當前問題。

4. 「族群詳情應拆成概覽／成員／關聯／證據四個分頁。」  
   最新決策：選到族群後直接顯示近期事件與所有標的。

5. 「次要題材一定要顯示在成交值排行榜。」  
   目前排行榜只需大題材＋當前題材；底層仍可保留多標籤，不必全部塞進主表。
