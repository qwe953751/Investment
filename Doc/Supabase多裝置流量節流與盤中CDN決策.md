# Supabase 多裝置流量節流與盤中 CDN 決策

最後更新：2026-08-29

這份文件整理「10 位使用者、每人最多 3 台裝置，合計最多 30 台裝置」的流量問題、
取捨、已採用方案與驗證方式。30 台是容量假設，不代表會同時在線；設計目標是即使
同時使用，也不要讓每台裝置把同一份盤中全市場資料重複打進 Supabase。

## 1. 先記錄看到的現象

Supabase Free Plan 使用量截圖曾顯示：

| 項目 | 截圖數值 | 解讀 |
|---|---:|---|
| Egress | 6.522 / 5 GB（130%） | 已超過包含額度；超額時專案可能受限制或變得無回應 |
| Database Size | 0.179 / 0.5 GB（36%） | 當時不是資料庫容量先滿，而是讀取流量先成為風險 |
| Realtime concurrent connections | 0 / 200 | 目前問題不是 Realtime 連線數 |
| Monthly Active Users | 0 / 50,000 | 目前問題不是 Auth MAU |

使用量儀表板可能延遲刷新，因此單次畫面不是完整的計費證據；但它足以證明原本的
「每台瀏覽器直接輪詢全市場 REST」不適合當成 30 台裝置的長期方案。

## 2. 發生原因

### 2.1 每台裝置重複下載同一份全市場資料

舊流程在盤中頁直接讀 `intraday_latest`。這個 view 每列都重複帶著交易日、指數、
熱絡指標等輪次欄位，約 1,973 列、24 欄，單次未壓縮回應約 2.1 MB，其中約 1.76 MB
是重複內容。頁面每 2 分鐘更新一次時，同一份輪次會被每台裝置各下載一次。

用最壞情境估算（台股盤中約 270 分鐘、每 2 分鐘 135 次、30 台裝置）：

```text
2.1 MB × 135 次 × 30 台 ≈ 8.5 GB／盤中日
```

這是估算，不是當時帳單的精確歸因；實際值會因頁面是否開啟、快取、壓縮與同時在線
人數而不同，但量級已足以解釋為何 Egress 會快速增加。

### 2.2 查詢拆分只能減少單次回應，不能消除資料庫來源流量

曾把重複 view 拆成「個股列」與「一列摘要」兩次查詢，約降到 339 KB。這是必要的
資料形狀修正，但在 30 台裝置各自輪詢時，仍會把相同資料重複送過 Supabase REST；
它是中間優化，不是最後解法。

### 2.3 同一瀏覽器的多分頁各自輪詢

同一位使用者若同時開三個分頁，舊版每個分頁都有自己的計時器，會把一人的流量放大
三倍。手機切到背景、鎖屏或收盤後仍可能保留輪詢，也會產生沒有使用價值的請求。

### 2.4 盤中與非盤中資料沒有清楚的入口邊界

「盤中」不只是一個主頁籤：還包括自訂資料瀏覽選盤中、族群熱度選盤中，以及
「族群 → 族群列表 → 盤中」和列表中展開的盤中個股 K 線。若每個頁面自己列舉
要不要走 CDN，新增入口時很容易漏掉，導致某個頁面仍打全市場 REST。

## 3. 方案比較與選擇

| 方案 | 優點 | 問題 | 結論 |
|---|---|---|---|
| 每台裝置繼續輪詢 REST | 改動最少 | 流量按裝置數線性增加；30 台時不可預期 | 不採用 |
| 只縮小 SQL／拆 view | 單次回應變小 | 仍是每台裝置讀資料庫；30 台仍重複 | 作為中間優化，不能單獨解決 |
| Realtime 廣播全市場資料 | 可減少輪詢 | 會增加 Realtime 訊息與連線管理；仍需處理斷線、重播與完整快照 | 不作主路徑 |
| 伺服端集中輪詢再由網站轉送 | 可集中來源 | 需要長駐伺服器或額外 API；目前靜態 GitHub Pages 架構不適合 | 不採用 |
| 版本化完整快照 + CDN + 小指標 | 同一份公開資料可由 CDN 共用；可驗證輪次一致；仍保留完整資料準確性 | 需要 Storage bucket、發佈器、失敗監控與版本清理 | **採用** |

選擇最後一案的關鍵不是只追求「少幾次 SQL」，而是把盤中全市場讀取從 Supabase
Database REST 移到可快取的公開 Storage；30 台裝置讀到的是同一份 CDN 物件，而不是
30 份資料庫回應。

## 4. 已採用的最終資料流

### 4.1 收集器與 Supabase Storage

每一輪盤中行情成功寫入資料庫後：

1. 產生不可覆寫的完整檔案，例如 `intraday-20260828-1334-run123.json`。
2. 先上傳完整檔案，再更新很小的 `latest.json` 指標。
3. `latest.json` 包含 `runId`、交易日、收集時間、檔名、列數與內容雜湊；前端可驗證
   指標與完整檔案是否為同一輪。
4. Storage 只保留最近 30 份版本（約 60 分鐘），避免每兩分鐘累積檔案耗盡 Storage；
   `latest.json` 與未知檔案不清理。

完整檔名永不覆寫、可長期快取；只有 `latest.json` 需要短快取（約 10 秒）。先完成
完整檔案再更新指標，避免瀏覽器拿到新指標卻找不到對應檔案。

`SUPABASE_STORAGE_SECRET_KEY` 只存在 GitHub Actions／伺服端環境，用來上傳與清理；
不寫入 manifest、JavaScript、log 或瀏覽器。公開 bucket 只放公開行情、指數與同一輪
推導出的族群熱度，不能放筆記、資產、使用者資料、備份或任何權杖。

### 4.2 前端只輪詢小指標

前端在盤中資料流中只輪詢 `latest.json`。`runId` 沒變時不下載完整快照；變更時才
下載一次不可變的完整檔案，並使用瀏覽器／CDN 快取。完整檔案包含全市場所有個股，
前端才依門檻與排序顯示畫面上的前 100 檔；**不是拿一開始產生的前 100 檔作比較**。
因此排行的候選資料仍是當輪完整快照，沒有因節流而犧牲準確性或自訂篩選能力。

若 CDN 暫時失敗，畫面保留上一輪已驗證資料並顯示稍後重試；不拿半套檔案或不同輪次
族群資料拼成新結果。舊 manifest 沒有 CDN 設定時才走原本的 Supabase 相容路徑，這是
部署／回滾保護，不是新版本的預期主路徑。

### 4.3 同瀏覽器多分頁共用

同一瀏覽器分頁透過 `BroadcastChannel` 傳送已取得的完整快照，並以短租約選出一個
leader 負責輪詢；其他分頁不再對 CDN（更不會對 Supabase）各打一輪。若瀏覽器不支援
`BroadcastChannel` 或封鎖 `localStorage`，各分頁仍只讀 CDN，不退回資料庫輪詢，最差
是增加 CDN 命中而不是把資料庫流量放大。

### 4.4 只在真正的盤中入口啟用

所有入口集中由一個 `usesIntradaySnapshot()` flag 判斷，現行涵蓋：

- 盤中排行
- 自訂資料瀏覽 → 盤中
- 族群 → 熱度排行 → 盤中
- 族群 → 族群列表 → 盤中
- 上述盤中列表中展開的個股 K 線

以下維持原本資料流，不因 CDN 改變：

- 盤後排行與非盤中的族群頁
- 筆記、資產、提醒、營收
- 其他不需要即時行情的功能

因此「有選到盤中」才走版本化 CDN；不是整個網站一律改走 CDN。

### 4.5 只有必要時間才更新

- 只在台股盤中 09:00–13:35 嘗試更新。
- 只有頁面在前景時更新；背景、鎖屏、收盤後停止輪詢。
- 使用牆上時鐘與可喚醒的 `visibilitychange`、`focus`、`pageshow`、`online` 事件，
  避免手機計時器凍結後補打一串過期請求。
- 每 10 分鐘檢查網站版本；舊分頁發現版本不同時強制重新載入，避免舊 JavaScript
  長時間執行錯誤的資料流。

## 5. 流量改善的量級理解

以下只作容量推估，不當作帳單承諾：

| 流程 | 單次主要讀取 | 30 台、135 輪的資料庫來源量級 |
|---|---:|---:|
| 舊版完整 view | 約 2.1 MB | 約 8.5 GB／盤中日 |
| 拆分查詢後 | 約 339 KB | 約 1.37 GB／盤中日 |
| 版本化 CDN | 每輪每台只看數百 bytes 的 `latest.json`；完整檔案由 CDN 快取 | 資料庫不再承擔每台裝置的全市場快照回應 |

CDN 不是「完全沒有網路流量」：Storage 的快取流量仍要監看，且不同 CDN edge 可能
各自回源一次；但這個回源次數不再與每台瀏覽器、每個分頁、每次 REST 輪詢線性相乘。

## 6. 準確性、權限與隱私的邊界

1. **完整快照而非前 100 快照**：顯示前 100 只是 UI 分頁／排行結果；計算候選仍是
   當輪全市場資料。
2. **同一輪一致性**：前端驗證 `runId`、列數、交易日、收集時間與族群熱度時間戳，
   不接受互相不一致的檔案。
3. **C# 仍是公式唯一來源**：前端只做篩選、排序、編號與格式化，不因搬到 CDN 而
   在瀏覽器重算市場熱度或補造行情。
4. **公開與私有分流**：CDN 只服務公開行情；筆記、資產與使用者資料不進 CDN。
   CDN 也不等於登入或 RLS；目前資產／筆記的 anon 權限取捨仍記在 `TODO.md`，
   後續若要真正隔離使用者，必須另做 Auth + RLS。
5. **資料庫權威不變**：交易所 → `data` branch `imports/` → Supabase 查詢副本；CDN
   是盤中公開讀取快照，不改變原始資料權威順序。

## 7. 啟用與驗證清單

### 啟用前

- Supabase Storage 建立 public bucket `intraday-snapshots`。
- 限制內容類型為 `application/json`，單檔上限至少 10 MB。
- GitHub Actions 設定 repository secret `SUPABASE_STORAGE_SECRET_KEY`；值不可寫入
  repo 或貼到終端輸出。
- 確認收集器、靜態匯出與 workflow 都使用最新 `main`；未設定 secret 時，manifest
  不應宣告 CDN URL。

### 每次發布後

- Actions 的 `publish-only=true` 成功，且 `headSha` 等於剛推送的 `main`。
- 目標 `gh-pages` 的 `admin888/manifest.json` 版本與公開 URL 最終一致；剛發布時
  若公開 URL 還是舊版，先視為 Pages／CDN 傳播延遲，等待後重試。
- 瀏覽器 Network 檢查盤中頁：新版本應看到 `latest.json` 與版本化
  `intraday-*.json`，不應每兩分鐘看到 `rest/v1/intraday_latest` 全市場回應。
- 確認非盤中頁仍使用原本的資料來源，且資產／筆記沒有任何 CDN 請求。
- Supabase 監看 origin egress、cached egress、Storage size、API 錯誤；使用量儀表板
  可能延遲，不能只用一個瞬間數字判斷。

### 故障時

- 先看 Actions 第一個失敗步驟與 HTTP 狀態碼，不要直接刪 bucket 或清空資料。
- 若是 CDN 上傳失敗，原始盤中資料仍可能已寫入資料庫；保留上一個有效指標，修復
  secret／bucket／權限後再重試，不補假資料。
- 若網站只有舊版，先比對 `gh-pages` manifest 與公開 manifest；不要用本機舊的
  `publish/site` 手動覆蓋 `gh-pages`。
- 若出現資料不一致，檢查 `runId`、`capturedAt` 與族群熱度時間戳；寧可顯示上一輪
  並報錯，也不要把不同輪次混在一起。

## 8. 最終結論

以 10 人 × 3 台裝置的容量假設，採用「**每兩分鐘產生版本化完整盤中快照、前端只輪詢
小型 `latest.json`、完整檔案交給 CDN、同瀏覽器分頁共用輪詢者、只在盤中前景更新**」
是目前最符合準確性、流量與既有靜態架構的方案。

這個方案同時滿足：

- 不讓 Supabase Database 為 30 台裝置重複回應同一份全市場資料。
- 不以固定前 100 筆代替完整資料，排行與自訂篩選仍以當輪全市場快照為準。
- 只有真正需要盤中即時資料的入口走 CDN；其他功能維持原樣。
- 不把筆記、資產、權限資訊、access token 或 service role key 放到公開快照。
- 以不可變檔名、指標驗證、保留 30 份與發布後監控，控制快取延遲、版本混用與 Storage
  無限成長風險。

目前程式與網站已完成此方案的實作與發布；若日後要改 Auth／RLS、私有資料 CDN 或
Realtime，必須另立決策，不可把它們偷偷混入盤中公開快照路徑。
