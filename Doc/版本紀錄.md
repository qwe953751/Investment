## 2026-08-29：盤中收集改成自走鏈，不再依賴 GitHub 的排程準時

**接手的人先看這一段**：`intraday.yml` 的啟動方式整個換掉了。
它現在是一條**長期運行的接力鏈**，不是「每天被 cron 叫醒幾次」。
Actions 頁面上會**一直**看到一場 `盤中報價收集` 在跑、一場在排隊——那是正常狀態，不是卡住。

### 為什麼換

08-27、08-28 連兩天 GitHub 的 `schedule` 事件晚到 6～13 小時或整天沒送達
（詳細證據見 [TODO 14](../TODO.md#todo-14)）。結果是開盤了網站還停在昨天，
只能靠人遠端叫 AI agent 手動補跑。加更多 cron 沒有用：那天三個 cron 全都晚到。

關鍵是推翻了一個原本的錯誤判斷——`workflow_dispatch` 與 `repository_dispatch`
是 Actions 遞迴保護的**例外**，`GITHUB_TOKEN` 觸發得動。
實測：拋棄式 workflow 自我接力三棒（run 33177347324 → 33177357163 → 33177365236），
三場全成功、間隔 6 秒。實測完那支已刪除。

### 怎麼運作

- 每一棒開跑的**第一件事**是 dispatch 下一棒去排隊，然後才 checkout。
  放第一是因為這一棒可能撞到 6 小時硬上限、runner 可能掛掉、可能被 cancel，
  那些情況都輪不到最後一步執行。
- 接著自己算出下一次開盤（跳過週六日）睡過去。一棒預算 5 小時 30 分（離硬上限留 30 分）。
- 開盤時若剩餘時間不足 4 小時 55 分就不硬收，改當**佔位棒**，
  提早 10 分鐘退場，把 checkout 與 .NET 安裝的暖機時間讓給下一棒。
- `concurrency: intraday-daemon` 保證同時只有一棒在跑、只有一棒在排隊
  （新的 pending 會取代舊的 pending，所以不會愈叫愈多）。
  **排程與手動共用同一組鎖**——分開就等於允許兩個收集器並行寫同一輪。
- 每一棒至少活 3 分鐘，防止哪天每棒都秒失敗變成一天上千個 run。
- cron 保留但降級成**復原火種**（多加一發週末的）。事件晚到多久都沒關係，
  新的一棒會自己重算下一次開盤。原本的 `preflight` 已移除——它會**丟掉**晚到的事件，
  那正是 08-28 沒資料的原因之一。
- 順便兼任每日快照的鬧鐘：平日過了 18:00 而當天還沒有成功的快照就叫它起來。

### 維運要知道的兩件事

1. **要立刻重跑一輪時不要另外觸發**——那會排到 5 個多小時後。
   直接把正在睡的那一棒 **cancel** 掉：下一棒已經排在後面，會馬上頂上並重新判斷。
2. **代價是長期佔著一個 runner。** repo 是公開的、Actions 不計費、
   併發上限 20 個 job 只用 1 個，所以可以接受。

### 上線時踩到的坑

Actions 的預設 shell 是 `bash -e`，errexit 是**命令列**給的，
步驟裡寫 `set -uo pipefail` 關不掉它。等待迴圈用「條件不成立就 return」的寫法，
裸 `return` 會把上一個判斷的狀態 1 傳出去，整個步驟被 errexit 打掉，每一棒 20 秒內失敗。
「每棒至少 3 分鐘」的下限剛好把暴衝擋在一小時 20 棒，沒有失控。
已明確 `set +e`，所有「現在不必做這件事」的 return 釘成 `return 0`，並補測試釘住。

### 驗證

- 本機假時鐘（**用 `bash -e` 跑**，重現 runner 環境）把「週五收盤 → 週一開盤」
  整條鏈一棒一棒推過：第 13 棒在週一 08:30 起跑、08:40 開始收集。
  平日夜間、週末、晚到火種的情境都會收斂到開盤。
- 線上確認鏈子進入穩定狀態：一棒在「等到開盤」睡著、一棒 pending。
- 單元測試 267 個全綠。
- **待驗收**：8/31（週一）開盤後盤中資料應自動更新，不需要任何人介入。

## 2026-08-28：`db/022` 修好從 08-23 起就壞掉的備份

補跑當天缺的每日快照時，「備份原生資料」這一步紅掉才發現的，跟筆記 #27 無關。

- `db/012` 建 `site_alerts` 時 grant 了表，卻沒 grant 它 `generated always as identity`
  隱含的那條 sequence。**寫入完全正常**——identity 的 sequence 由欄位擁有，`insert` 不另外
  檢查 sequence 權限——所以鈴鐺一直好好的，一個症狀都沒有。
- 壞掉的是備份：`scripts/backup-supabase.sh` 以 `invest_writer` 連線，`pg_dump` 會對每一條
  sequence 打一次 `SELECT last_value, is_called`，那個才要權限：
  `permission denied for sequence site_alerts_id_seq`。
- **自 2026-08-23 起每一次完整快照的備份都失敗，最後一份成功的備份是 `2026-08-21.sql.gz`。**
  沒被發現是因為紅掉的那幾次剛好也有別的步驟紅，其餘多數是 `publish-only`（會略過備份）。
  也就是說 08-24～08-27 這四個交易日完全沒有備份，而畫面上一切正常。
- 這是同一個坑第二次（`db/018` 漏了 `notes_note_number_seq`，`db/020` 才補）。`db/022` 除了補上
  這一條，另外 `grant ... on all sequences` 收齊現有的，並設 `alter default privileges`
  讓之後新建的 sequence 自動帶上 `invest_writer` 權限。**不含 `anon`**——anon 該拿什麼要一條一條
  想清楚（像 `db/020` 那樣明講），不能靠預設值發下去。
- 已套用並驗證 `has_sequence_privilege('invest_writer', 'site_alerts_id_seq', ...)` 為 true。
